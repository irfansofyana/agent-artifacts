A self-hosted-first field guide

Evaluate the MCP,
not the demo.

How to test OAuth-protected MCP servers, compare behavior across Cursor, Claude Code and Open WebUI, trace failures end to end, and drive down tool-call cost—without sending company data or model traffic to a SaaS control plane.

THE SHORT ANSWER

Do not buy one “MCP eval platform.” Build a small stack: official conformance + deterministic behavioral evals + an observable gateway. Use real clients only as compatibility probes.

Public-safe note: this guide intentionally uses a generic private OpenAI-compatible endpoint. It contains no internal server names, credentials, datasets, or architecture identifiers.

01 / DECISION

The stack I would deploy

MCPJam is useful, especially for OAuth diagnosis. It is not the right center of gravity when production eval features, team history, or hosted results create login/licensing pressure and your model endpoint exists only inside a VPN.

Baseline · mandatory

Official MCP Conformance + Inspector

Protocol correctness, OAuth debugging, raw JSON-RPC inspection, reproducible CI artifacts. These tell you whether the server speaks MCP correctly—not whether agents use it well.

Primary eval engine

Promptfoo OSS + a thin MCP runner

Golden cases, assertions, red teaming, model comparisons, CI thresholds and a local viewer. Point its OpenAI-compatible provider at the private VPN endpoint.

Observability plane

ContextForge + OpenTelemetry + Phoenix

One MCP endpoint for all clients, user-scoped OAuth forwarding, policy and OTLP traces. Phoenix gives self-hosted trace inspection, datasets, experiments, tool-call evals and cost rollups.

!

Keep MCPJam, but narrow its job. Its local CLI/SDK can run OAuth checks and test cases; the SDK documents custom OpenAI-compatible providers. However, MCPJam’s repository uses mixed licensing: most code is Apache-2.0, while server-side eval services are under an Enterprise Edition license for production use. Uploading results and hosted project views require an MCPJam API key. That directly explains the friction you noticed.

04 / CLIENT REALITY

Cross-client testing without fooling yourself

Cursor, Claude Code and Open WebUI are not interchangeable test runners. Their prompts, tool naming, approval behavior and model routing differ. Run the same scenarios, but do not pretend their scores isolate MCP-server quality.

Use a two-tier suite

  1. Canonical runner: execute every golden case through your own agent loop, private model endpoint and MCP client. This is where you compare versions, models, prompts and cost.
  2. Host adapters: run 10–20 representative smoke cases through each real client. Assert final answer and gateway-observed tool calls. Use these to find host incompatibilities—not to calculate a universal quality score.
  3. Normalize evidence: each run emits run_id, client, model alias, server commit, tool schema hash, expected/actual calls, latency, token usage if visible, and trace ID.

Cursor

  • Supports local and remote MCP configurations and OAuth-protected servers according to official MCP docs.
  • Use the headless CLI where available for repeatable prompts and structured output, but treat Cursor’s hidden system prompt and model behavior as a host variable.
  • Capture authoritative server-side tool calls at the gateway. Do not infer tool usage only from the final text.
  • Provider/model cost may not be observable end to end when Cursor owns the model call.

Claude Code

  • Supports OAuth 2.0 for remote MCP servers; its -p mode and JSON/stream-JSON output are automation-friendly.
  • Use an isolated project, explicit allowed tools and a fixed prompt packet. Record session usage metadata where exposed.
  • Claude Code hooks can add client-side evidence, but gateway traces remain the neutral source for MCP calls.
  • Do not compare a Claude Code result against your private model runner as if only the MCP changed.

Open WebUI

  • Native Streamable HTTP MCP supports OAuth 2.1 DCR and static-client modes.
  • Its API accepts tool_ids, enabling repeatable server-side tool tests after the test user has completed OAuth in the UI.
  • Keep WEBUI_SECRET_KEY stable: OAuth client/session tokens are encrypted from it.
  • Open WebUI exports OTel traces, making it the easiest of the three clients to connect to your observability plane.
≠

Important limitation: proprietary hosts cannot guarantee full LLM→MCP trace continuity. The MCP 2026-07-28/OpenTelemetry conventions define propagation through _meta, but the host must implement it. If it does not, correlate gateway calls by user, session window and a test-run marker. Never claim exact per-task token cost for Cursor or Claude Code unless their APIs actually expose it.

05 / SCORECARD

Optimize cost per successful task

Raw token cost rewards uselessly cheap failures. Your north-star metric must include correctness and recovery.

Task success

successful_cases / total_cases

Deterministic state assertions first; LLM judges only where exact assertions cannot express quality.

Tool selection precision

correct_calls / all_calls

Penalize irrelevant calls, omitted required calls, wrong arguments, and unsafe write calls.

Cost per successful task

total_model_cost / successful_cases

Include retries and judge cost. Report failure cost separately so regressions cannot hide.

P95 end-to-end latency

prompt → final verified state

Split model thinking, MCP gateway, server handler and downstream dependency latency.

Schema efficiency

tool_schema_tokens / input_tokens

Track tool-description growth. Large catalogs and verbose schemas can dominate every request.

Call amplification

actual_calls / minimum_required_calls

Find chatty tools, missing bulk APIs, weak descriptions and loops.

Reliability

success after 0 retries; after ≤1 retry

Separate clean success from recovered success. Retries cost money and hide brittle interfaces.

Safety & auth

unauthorized writes = 0

Scope enforcement, token audience, expiry/refresh, prompt-injection resistance and least privilege are release gates.

$

Cost-improvement order: remove redundant tools → shorten descriptions/schemas → improve tool names and argument constraints → add bulk/read-efficient operations → cache read-only results → route simple cases to a smaller model → reduce retries. Model switching comes after interface cleanup, not before.

06 / DELIVERY

A right-sized 90-day rollout

Start with evidence that changes engineering decisions. Do not build a platform team around dashboards before the first 30 golden cases exist.

Weeks 1–2
Make it testable

  • Seeded staging tenant
  • 30 golden cases: read, write, abstain, auth
  • Conformance + schema snapshot in CI
  • Stable model aliases and pricing table

Gate: deterministic server state is assertable

Weeks 3–4
Add behavior

  • Promptfoo canonical runner
  • 3 repeats for stochastic cases
  • Tool-call and cost assertions
  • Failure taxonomy stored with cases

Gate: regression report on every PR

Month 2
Trace the system

  • Gateway pilot for one server
  • OTel Collector + Phoenix
  • Redacted attributes by default
  • Open WebUI API adapter; Claude/Cursor smoke adapters

Gate: one trace links eval → MCP → dependency

Month 3
Optimize

  • Cost/success baseline
  • Schema and call-amplification fixes
  • Canary model routing
  • Nightly security and OAuth lifecycle suite

Gate: measurable quality-neutral cost reduction
