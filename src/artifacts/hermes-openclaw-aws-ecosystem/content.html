Yes, and it is mostly first-party now. AWS ships a campaign page, an official Lightsail quick start, one-click CloudFormation samples for both agents, Marketplace listings, and four Builder Center write-ups. The community layer is thin: a handful of Terraform modules, only one of which looks maintained.

2. The deployment options, honestly compared

OptionBest forReality check
Lightsail One personal assistant, fast Fixed instance bundle, no IAM role plumbing for Bedrock beyond what the image ships. Cheapest way to stop babysitting a VPS.
EC2 (single instance) Personal or small-team gateway with real IAM The defaults everyone actually lands on. Attach an IAM role, run it under systemd or Docker, keep it off the public internet behind SSM or a tailnet.
EKS + Helm Multi-tenant fleets, isolation per user Only worth it with OpenClaw Enterprise (MIT-licensed control plane, Helm charts, EKS deploy guides). Real operational surface: node groups, IRSA, ingress.
Bedrock AgentCore Serverless, per-session microVMs The Hermes AgentCore sample is the most interesting architecture here (Firecracker microVM per session, CDK stacks, S3-backed workspace). Not available in every region yet.
Fargate / Lambda Nothing you should copy A long-lived agent with a local workspace and channel sockets fights both models. The AgentCore sample uses Fargate only as an edge gateway for long-lived connections.

3. The deployable samples worth cloning

aws-samples/sample-OpenClaw-on-AWS-with-Bedrock

AWS sampleMIT-0418 stars

Single CloudFormation stack that stands up OpenClaw on a Graviton instance with Bedrock for model access, SSM Session Manager instead of open SSH, VPC endpoints and CloudTrail. Claimed deploy time is about 8 minutes; the README prices it from roughly $30/month. Messaging plugins arrive pre-installed, and the launch buttons cover us-west-2, us-east-1, eu-west-1 and ap-northeast-1.

  • Bedrock model access is handled by the stack, no API keys in the instance.
  • Access is through SSM, so no inbound ports and no SSH key.
  • Caveat: the one-click template lives in a single S3 bucket, so a region outside those four means uploading the template yourself.

aws-samples/sample-host-hermesagent-on-amazon-bedrock-agentcore

AWS sampleMIT-045 stars

The most architecturally interesting option for Hermes: per-user Firecracker microVMs on AgentCore Runtime, 9 CDK stacks, API Gateway plus a router Lambda in front of inbound webhooks, and an ECS Fargate gateway for channels that need long-lived connections. State is S3-backed so memory and sessions survive the microVM.

  • Integration is a monkey-patch that swaps anthropic.Anthropic for anthropic.AnthropicBedrock, so all inference goes through Bedrock with SigV4 and IAM. Upstream Hermes source stays unmodified.
  • Channels covered: Telegram, Slack, Discord, Feishu via webhook; WeChat through the Fargate gateway.
  • Caveat: region-gated, see the Jakarta note below.

JiaDe-Wu/sample-hermes-agent-on-aws-with-bedrock

MIT19 stars

The sample the Hermes docs themselves link to: CloudFormation creates the VPC, IAM role, EC2 instance and Bedrock configuration in one click. Its native Bedrock provider work has been merged into upstream Hermes, so the deployment installs from the official PyPI release instead of a fork. This is the shortest path from zero to a working Hermes on EC2.

There is also aws-samples/sample-hermes-agents-on-agentcore, younger and thinner, but useful if you want more than one Hermes agent in the same AgentCore account.

4. Both agents speak Bedrock natively

This is the part that makes the whole AWS story work, because it removes API keys from the picture. Auth is the AWS SDK credential chain, so an instance role is enough.

OpenClaw ships a Bedrock Converse streaming provider plus a separate Bedrock Mantle provider for the OpenAI-compatible endpoint that serves open models.

# OpenClaw: provider metadata
# provider: amazon-bedrock
# api:      bedrock-converse-stream
# auth:     aws-sdk  (env vars, shared config, or instance role)

# On EC2 the instance role is invisible to env-marker detection,
# so discovery has to be turned on explicitly:
openclaw config set plugins.entries.amazon-bedrock.config.discovery.enabled true
openclaw config set plugins.entries.amazon-bedrock.config.discovery.region ap-southeast-3
openclaw models list

Discovery uses bedrock:ListFoundationModels and bedrock:ListInferenceProfiles and caches for an hour. Bare foundation-model IDs are only listed when Bedrock reports on-demand support; models that are profile-only get listed as their us. / global. profiles instead, since the profiles carry different data-residency behaviour. You can still add a hidden model by hand under models.providers["amazon-bedrock"].models.

Hermes Agent routes each model family through the API that serves it best rather than forcing everything down one path.

# Hermes Agent: Bedrock provider
cd ~/.hermes/hermes-agent && python -c "import pm; pm.sync_venv(['bedrock'], explicit=True)"
hermes model        # More providers... -> AWS Bedrock -> region -> model

# config.yaml afterwards
# model:
#   default: us.anthropic.claude-sonnet-4-6
#   provider: bedrock
# bedrock:
#   region: ap-southeast-3
Model familyRouteWhy it matters
Anthropic ClaudeAnthropic SDK (AnthropicBedrock)Prompt caching, thinking budgets and adaptive thinking are not exposed through Converse.
OpenAI models with a bare openai.* IDBedrock Mantle OpenAI Responses endpointMantle serves the bare in-region ID; bedrock-runtime rejects it.
The same models with a us. or global. profile IDNative Converse APICross-region profiles only exist on bedrock-runtime.
Nova, DeepSeek, Llama, GPT-OSS and the restNative Converse APIGuardrails, inference profiles and streaming all supported.

Minimum IAM for either agent: bedrock:InvokeModel, bedrock:InvokeModelWithResponseStream, bedrock:ListFoundationModels, bedrock:ListInferenceProfiles.

6. Community Terraform: read before trusting

  • infrahouse/terraform-aws-openclaw — Apache-2.0, the only one that reads like a real module: ALB, Cognito authentication, EFS persistence, multi-provider LLM support. 20 stars, last touched November 2026.
  • qodex-ai/openclaw-worker — MIT, one-command deploy with HTTPS, Route 53 DNS and encrypted S3 backups. 4 stars, September 2026.
  • janobarnard/openclaw-aws and mamonaco1973/aws-openclaw — single-author examples (Terraform, and Terraform plus Packer against Bedrock). Useful as references, not as dependencies.

OpenClaw Enterprise is the scale path

openclaw/openclaw-enterprise is MIT-licensed, actively developed, and ships EKS deployment guides for its Helm installation, including private-only cluster API access and cleanup procedures. That is the only route to per-user isolation that is not hand-rolled.

7. Jakarta reality check

ap-southeast-3 covers EC2 and Lightsail, not AgentCore

Checked against AWS regional availability data on 18 November 2026: Amazon Bedrock and Amazon Lightsail both report available in ap-southeast-3. Amazon Bedrock AgentCore reports planned, not available.

So the EC2 and Lightsail paths run in Jakarta today, with Bedrock as the model back end. The AgentCore-based Hermes sample needs a neighbouring region until AgentCore lands, which makes it an explicit cross-region data-processing decision rather than a default.

One more Jakarta-shaped detail: the CloudFormation launch buttons in both aws-samples repositories point at fixed regions and a single template bucket. For ap-southeast-3 you re-host the template in your own bucket and launch from there, and you should verify model availability in-region before picking default model IDs.

8. What I would actually do

  1. Jakarta, EC2, Bedrock. Launch a Graviton instance from the aws-samples CloudFormation sample, re-hosted for ap-southeast-3. IAM role for Bedrock, SSM for access, no inbound ports. This is the shortest path that satisfies a Jakarta-only constraint today.
  2. Keep the AgentCore sample on the shelf. It is the better long-term architecture for per-user isolation, but it is not deployable in Jakarta yet, and porting the CDK stacks to a neighbouring region is a data-residency decision, not a config change.
  3. Skip EKS unless multi-tenancy is the actual requirement. One agent per person on its own instance is cheaper and easier to reason about than a cluster with per-user cells, and OpenClaw's own security guidance says a shared gateway is not a trust boundary.
  4. Use the Terraform module only if you need the AWS-native edge. infrahouse/terraform-aws-openclaw is worth reading for the ALB plus Cognito pattern, but a personal gateway behind SSM does not need an ALB.
