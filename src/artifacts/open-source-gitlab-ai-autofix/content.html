Open-source projects that use AI to fix GitLab vulnerabilities

Short answer: no open-source project is both widely used and built to fix GitLab findings with AI. The most-starred AI fixers are generic or GitHub-first. The GitLab-native ones are new and have almost no adoption yet.

Verdict

If you need a GitLab fix loop today, use Semgrep for findings and fix suggestions, and GitLab Duo's agentic resolution if you are on Ultimate. Both are trusted by many teams. Neither is a fully open AI fix pipeline.

If you need an open, self-hosted AI fix loop, none of the projects below is a safe default yet. SecureFix is the closest match for GitLab, but it has no licence and no adoption. OpenHands has the adoption, but its vulnerability-fixer is a GitHub-only prototype.

Stars measure attention, not whether a fix is correct. I ran none of these tools against a GitLab project. Treat this as a shortlist to test, not a verdict on quality.

If the requirement is a draft MR from CI, Codex Security is the one whose docs describe that job. Pixee and Aikido also open GitLab MRs, from their own service, not from a template you import.

Decision, 19 November 2026

The goal is a fixer other teams can adopt, as a CI job, that stops at a draft merge request.

Possible, in a job you write. codex-security scan --patch --create-pr can scan, patch, and open a draft MR. The official GitLab pipeline cannot do that without an OpenAI key that already has Codex Security access.

Without that program, the CLI still accepts OpenRouter, Fireworks, and Bedrock. LiteLLM is not a --provider value. Point the CLI at it with a Codex override, and the alias must list /v1/responses in supported_endpoints. A bridged route drops the fields the scan needs.

The MR opens only for a verified patch. The push is local: glab plus a project token with api and write_repository. CI_JOB_TOKEN cannot create the MR. Daybreak models stay behind Trusted Access, so some finding classes can be refused by whatever model sits behind the gateway. This combination has not been run.

The open-source table still has no widely used project that does this loop. The Codex Security notes are at https://artifacts.irfansp.dev/codex-security-gitlab/.

Vendor features (not open source)

  • GitLab Duo Agentic SAST Vulnerability Resolution. Generally available since GitLab 18.11. Opens an MR with a fix for High and Critical SAST findings on the default branch. Needs GitLab Ultimate, GitLab Duo Agent Platform, and the flows turned on.
  • GitLab Duo Vulnerability Resolution (non-agentic). Creates an MR suggestion comment on a SAST finding. Ultimate tier, default model Anthropic Claude Sonnet 4.6, and the output needs review.

Opening a merge request

The open-source table has no widely used tool that opens a GitLab fix MR from CI. Shannon's open-source GitLab component does not include remediation. Fix pull requests are a paid Shannon feature, and those docs do not say the MR lands on GitLab.

Of the tools below, only Codex Security documents the path as a GitLab CI job, and that job is YAML you paste, not a CI/CD Catalog component. Pixee and Aikido open the MR from their platform. GitLab Duo's agentic flow, in the vendor list above, also opens an MR on Ultimate.

  • Codex Security. OpenAI, research preview. The official GitLab CI example opens a draft MR when CODEX_SECURITY_CREATE_MR is true, on branch codex-security/fix-<finding-hash>, and never merges. You paste the YAML. It is not an include. Needs an OpenAI key with Codex Security access. SARIF ingestion needs GitLab Ultimate 19.2 or later. The example pins the CLI at 0.8.1.
  • Pixee. Commercial. Opens GitLab merge requests for SAST and dependency findings through a service-account token and webhooks. Their docs say no change to .gitlab-ci.yml is required. Works with GitLab.com and self-hosted GitLab. Not an importable CI template.
  • Aikido AutoFix. Commercial. Opens GitLab merge requests, and a setting can mark them draft. Configuration is the Aikido UI plus an optional .aikido file, not a CI include.

How this was checked

Star counts, licences, last push dates and descriptions came from the GitHub REST API on 18 November 2026. READMEs were read from raw.githubusercontent.com. Claims about GitLab support come from README text and GitLab's own docs, not from running the tools.

Not verified by running them: whether Strix or Shannon open fix MRs on GitLab. Renovate's docs say it creates GitLab merge requests; this run did not execute Renovate. VulnHunter's licence is Apache-2.0, read from the repo LICENSE file.

Star counts change daily. Re-check before you decide.
