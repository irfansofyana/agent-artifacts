Headroom / context compression

Context, with the waste squeezed out.

A practical guide to how Headroom reduces the repetitive bulk in an agent’s prompt—without throwing the source material into a black hole.

Agent workloads are token-hungry. A single coding task can inject shell output, test logs, JSON responses, search results, source files, configuration, retrieved documents, and repeated history. Headroom sits between the application and the model provider, finds the bulky parts, compresses them, and forwards a smaller request.

The thesis: keep the instructions and stable context intact; squeeze redundancy out of the data the agent is reading.

The pipeline

Headroom can run as a proxy, an SDK call, or an MCP server. All three routes feed the same basic idea: inspect content, choose a compressor, preserve the original, and send the optimized request upstream.

01 / INTERCEPTReceive messages through the proxy, SDK, or integration.
02 / ROUTEDetect JSON, logs, search, code, diffs, tables, or prose.
03 / COMPRESSRemove repeated structure and keep a compact view.
04 / PRESERVEStore the original under a content hash/key.
05 / FORWARDSend the optimized request to the provider.
06 / RECOVERRetrieve the original or search within it when needed.

These are the project’s typical ranges, not a promise. Repetitive structured data is the sweet spot; unique prose and exact code are much harder targets.

The live zone

The current architecture uses live-zone-only compression: the newest user content and latest tool result are eligible for compression, while the system prompt, tool definitions, and older turns remain unchanged.

That is a deliberate cache decision. Providers can reuse a stable prompt prefix. Rewriting the old history on every turn would create prefix drift and reduce cache hits. Current docs also say older rolling-window and intelligent-context scoring components were removed, so older explanations of Headroom may describe behavior that no longer exists.

Your agent → [system + tools + older turns] unchanged
          → [latest tool output] type-aware compression
          → LLM provider

Reversible by design

After compression, Headroom can keep the original in a local store and return a compact representation plus a hash. Through the MCP interface, headroom_compress reports the compressed content, token counts, savings, and transforms; headroom_retrieve can return the full original or matching excerpts.

Important: reversibility helps only if the model knows when it needs the missing detail and actually retrieves it. It reduces risk; it does not eliminate the need for evaluation.

The trade-offs

Quality

Compression may hide a detail the model needs. Treat exact code, security-sensitive instructions, and critical structured data conservatively.

Latency

Compression costs CPU time. Compare the full request path—compression plus the smaller model call—rather than looking at token savings alone.

Economics

A 90% reduction in one tool output does not automatically mean a 90% production-cost reduction. Measure provider caching, output tokens, retries, retrievals, and task completion.

A sensible pilot

  1. Choose 20–50 representative tasks: repository search, test debugging, API investigation, RAG, and multi-turn coding.
  2. Record baseline tokens, latency, cache hits, cost, and task success.
  3. Enable proxy mode in default cache mode.
  4. Compare savings by content type, not only in aggregate.
  5. Track retrieval calls and cases where the agent needed to recover hidden detail.
  6. Keep Headroom only if the end-to-end win survives the correctness check.

My recommendation: start at the tool-output boundary—logs, search results, JSON, and database responses—before applying compression broadly to conversation history or source code. The benefit is measurable and the semantic-risk surface is smaller.
