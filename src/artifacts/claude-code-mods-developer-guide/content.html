Bottom line: a Claude Code mod is a JavaScript or TypeScript module inside a plugin that intercepts Claude Code events. It can observe, rewrite, or replace behavior and render parts of the interface. Use one when you need control inside the agent loop; use a skill, settings hook, or MCP server when those simpler mechanisms suffice.[7]

Scope: Claude Code v2.1.287+, as documented on 3 October 2026. Mods are new and the API may change; inspect the type declarations your installed version generates, not only an online example.[8][11]

The mental model

Claude Code emits events when a prompt is submitted, a tool is called, a turn advances, or UI is drawn. Your plugin's register(on) function attaches handlers. Each gets ($, e, next): the mods API, immutable event data, and the continuation. return next(e) observes and passes through; next({...e, field: changed}) rewrites; returning a valid result without next handles the event instead. Mods form an ordered middleware chain, so ordering and short-circuiting matter.[10]

export function register(on) {
  on('tool.call', { tool: 'Bash' }, async ($, e, next) => {
    // Observe only: ordinary permission checks and the tool still run.
    $.ui.log('About to run a Bash tool call')
    return next(e)
  })
}

The hook module has no direct Node.js APIs or DOM; file, process, HTTP, model, state, and UI access go through the $ API. This is not a security sandbox: those API calls operate with the installing user's access.[9][7]

Using Mods through LiteLLM or another gateway

Yes, in the local Claude Code CLI. Mods are local plugin code, while ANTHROPIC_BASE_URL directs Claude Code's Anthropic Messages API requests to an LLM gateway. Anthropic lists local plugins among the features available across model providers, and LiteLLM documents serving Claude Code through its /v1/messages endpoint. The mod does not need a direct Anthropic subscription just to load; it still needs Claude Code v2.1.287+ and must not be disabled by local or managed policy.[18][17][12]

Mod behaviorGateway implication
Draw UI, count tool calls, add a local command, intercept a tool or promptRuns in Claude Code locally when the plugin loads. The ordinary agent's model requests still go through the configured gateway.
Call $.model.complete or $.model.forkUses session credentials and consumes model usage. Test the model alias, request fields, and response on the exact gateway/upstream route; do not assume an Anthropic-shaped endpoint gives every Anthropic feature.

Those boundaries follow from the Mods API's session-credential model calls, the gateway protocol's required/optional endpoints, and Anthropic's provider-availability table. In particular, gateway translation can drop or change request features, streaming events, or model capabilities even though a local mod loaded successfully.[9][19][18]

Minimum check: with a LiteLLM route and credential already configured, start claude --plugin-dir ./example-mod, run /status to confirm the gateway base URL and credential source, then check /plugin for the mod and try /pulse. This verifies local loading separately from inference. If your own mod calls $.model.complete, also run one real request against each intended model and verify the response and gateway logs. Do not put gateway keys in a committed project settings file; prefer a managed credential or a private environment/settings source.[20][9]

Verification boundary: this compatibility guidance is based on Anthropic and LiteLLM documentation. The downloadable Tool Pulse test does not make a live inference request, and this guide does not claim an end-to-end test against any particular LiteLLM deployment or non-Anthropic model.

Build your first mod: Tool Pulse

This original, deliberately low-risk example counts observed tool calls, shows the count beside the terminal spinner, and adds /pulse. It does not modify the tool's input, bypass a permission, or call a model. Download the three plugin files and test below; keep their directory layout.[8]

example-mod/
├── .claude-plugin/plugin.json
├── hooks/hooks.json
├── hooks/register.js
└── tests/tool-pulse.test.ts

Download the complete Tool Pulse example (.zip), then extract it so example-mod/ contains the layout above. You can also inspect the source and test separately. The plugin manifest lives in the ZIP under .claude-plugin/; GitHub Pages may not serve dot-directories as standalone files.

Step 1 — prerequisite: install or update Claude Code using the official quickstart, then check claude --version is at least 2.1.287. Use a trusted disposable project directory for your first session. The native installation and sign-in are separate from this mod example.[8]

Step 2 — inspect the source. The manifest names the plugin; hooks/hooks.json points to register.js. This is the complete behavior:

let calls = 0
export function register(on) {
  on('session.start', async ($, e, next) => {
    await $.command.register({ name: 'pulse', description: 'Show tool calls observed since this mod loaded' })
    return next(e)
  })
  on('tool.call', async ($, e, next) => {
    calls += 1
    $.ui.invalidate('ui.render')
    return next(e)
  })
  on('command.run', { command: 'pulse' }, async () => ({
    text: 'Tool Pulse observed ' + calls + ' tool calls since this mod loaded.'
  }))
  on('ui.render', { component: 'Spinner' }, async ($, e, next) =>
    next({ ...e, props: { ...e.props, suffix: ' · tools: ' + calls } })
  )
}

Step 3 — validate and test from your shell (replace the path with where you saved example-mod):

claude plugin validate ./example-mod --strict
claude plugin test ./example-mod

Validation reports the handled events and API calls; tests use claude-code/testing and stub the real tool so no shell command or file read occurs.[11][16] If tests say hooks modules are turned off, follow the message's rollout/network guidance rather than treating validation as a test pass.

Step 4 — load for one session:

claude --plugin-dir ./example-mod

In the Claude Code prompt, ask list the files in this project, then type /pulse. Expect a tool count in the command response and, where UI drawing is supported, beside the spinner while Claude works. Use /plugin to check that Tool Pulse loaded; if it does not, consult Mods troubleshooting. A one-session --plugin-dir load is a safer first experiment than installing a marketplace plugin globally.[8]

Step 5 — iterate: try a turn.complete count, a status line, or a pane. Add tests for each new behavior. Module variables reset on reload; use $.state for reload-safe session state or $.store when data must persist between sessions.[15]

Limits that change your design

  • UI is surface-dependent. Hooks run in terminal, Desktop Code tab, VS Code chat panel, and claude -p when the plugin loads; custom drawing appears in terminal and supported Desktop surfaces, not VS Code chat or print mode. Desktop WSL sessions do not load plugins. Provide a text/status fallback if your feature must work headlessly.[7]
  • Mod events have contracts. Event data is frozen; pass a copy to next. Returning the wrong shape may skip your hook. One handler per event/matcher combination within a module; consult generated types for exact fields and supported UI elements.[10][11]
  • Guards are not automatically fail-closed. A hook that throws before next can be skipped; use a .catch denial handler for a safety-critical guard and test failure cases. A user-installed mod can affect approval behavior; managed organization policy is a separate layer.[10][7]
  • Hot reload resets ordinary module state. Tests and interactive reloads should cover your state strategy; persistent store writes across sessions are not atomic read-modify-write transactions.[15]

Review, then distribute

Treat every mod as executable code you install as yourself. It may read secrets, see prompts and tool calls, start processes, access the network, submit prompts, and use your model allowance. The module's restricted JavaScript globals do not make the host effects safe. Review source and dependencies before loading another author's mod; run claude plugin validate ./some-mod to inspect declared hooks and calls, but do not mistake this inventory or passing tests for a security audit.[7]

Start with --plugin-dir, keep a versioned manifest and tests, then share a plugin directory or publish it through a marketplace if other developers need it. Installed plugins can be disabled in /plugin; --safe-mode disables installed mods for a session along with other customizations, but built-in mods have separate behavior.[8][7]

The downloadable Tool Pulse plugin passed claude plugin validate ./example-mod --strict and claude plugin test ./example-mod on Claude Code 2.1.288 (1 test passed, 0 failed).
