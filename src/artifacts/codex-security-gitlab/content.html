Codex Security on GitLab: what actually works, and where it stops

Research notes on OpenAI's Codex Security for a GitLab workflow: what is usable today, the facts that decide the design, the limits not to promise, and the assumptions still unverified.

English·Bahasa Indonesia

Summary

Codex Security is OpenAI's application security agent, still in research preview. It ships as a CLI (@openai/codex-security, binaries cs and codex-security), a TypeScript SDK, one GitHub Action, and a Codex plugin. What separates it from an ordinary scanner: it reasons over source rather than matching signatures, so on internal platform code it produces far less noise.

The genuinely useful part today is narrower than that. validate, patch and verify-fix accept a finding as literal text or a file path, so a GitLab SAST or DAST finding can be handed to the agent without running Codex Security's own scanner at all. That is what flips the order of work: the backlog GitLab already produced is the immediate problem, while scanning for unreported vulnerabilities can wait until the fix loop is trusted.

Fix-first. Take findings that were already reported, assess them, then patch. Scanning for vulnerabilities nobody has reported still matters, but it depends on two things that are not proven yet: a Responses-native gateway alias and a model behind it that can honour a schema. Both have to close first.

Decision, 19 November 2026

Rechecked against the current CLI docs. Not from running the job.

  • The official GitLab pipeline cannot be used without Codex Security access. A job you write can still call the CLI.
  • scan --patch --create-pr is the loop that ends in a draft MR. That flag is not locked to the official YAML. LiteLLM is not a --provider value. Reach it with --codex overrides and wire_api = "responses". The alias must serve /v1/responses natively.
  • The MR appears only when the patch is verified. Without Trusted Access, Daybreak models are unavailable, and some finding classes can be refused. Not run on a real runner.
  • The open-source comparison is on the companion page.

Two jobs that are easy to confuse

Mixing these two up costs weeks of work in the wrong direction: one job scans a repository for vulnerabilities nobody has reported, the other assesses and fixes a finding somebody already reported. The second one does not need the first one to run.

Job What it does
Scan Hunts for vulnerabilities nobody has reported yet. Needs a repo-specific threat model, analysis, then sandboxed validation.
Assess & fix Assesses and fixes a finding another scanner already reported. It does not need its own scanner to run: the finding arrives as literal text or a file path.

CLI capability map

7 commands matter here. The top four carry the fix-first flow; the rest are workbench operations on saved results.

Command Purpose
scan Scans the repository, selected paths, or a diff. Modes standard and deep.
validate Assesses one candidate finding against source, in a read-only sandbox.
patch Generates and verifies a fix, optionally opening a draft PR or MR.
verify-fix Independent check of whether an issue is actually fixed.
scan import Loads findings already in the Codex Security schema, as CSV or JSON.
publish findings Imports an external scanner report into the workbench.
findings, scans, export,
dedupe, classify-severity,
suggest-owners		 Workbench operations on saved results.

The fix-first flow

  1. Take the finding from any source. GitLab SAST/DAST, the vulnerability report, GitHub code scanning, Sonar, Snyk, Semgrep, all of them work.
  2. Write one statement per finding naming the rule, the location and the observation, for example [sast 101, severity high] SQL injection in report filter at src/reports/query.py:42.
  3. validate first. Read-only: it does not build, run tests, execute the application, or contact services. Gate the next step on its verdict.
  4. patch --create-pr --assess-patch-risk only for the findings that validated.
  5. verify-fix when a fix already landed and you want an independent read.

Keep assess and patch as two reviewable stages. Validation costs model calls and nothing else; patching touches a branch. A person still decides what gets patched.

Facts that decide the design

  • validate has no --json. To gate it mechanically, force structure with --output-schema and a small JSON Schema. If the model's output does not match the schema the command exits 2 and writes nothing. Without this a pipeline can only guess.
  • patch returns verified, no_change, blocked or failed. Only verified results are committed. SANDBOX_UNAVAILABLE and NO_PATCH_APPLIED are operational outcomes, not security judgements, and file changes alone are not proof of a fix.
  • Patching a supplied finding requires a clean tree. Work in a temp directory outside the checkout and copy artifacts out only after patching finishes. If a selected file already has local edits, the CLI leaves the patch in the working tree for review instead of publishing it.
  • --create-pr opens a draft PR or MR through gh or glab and never merges. A failed push prints a patch --resume-pr BRANCH command to rerun from the same checkout.
  • Exit codes: 0 pass, 1 findings, 2 error, 130 / 143 interrupted. A gate that treats every non-zero as a finding misreports errors as vulnerabilities.
Exit code Meaning
0 Pass, no findings at or above the threshold.
1 Findings at or above the threshold.
2 Input, runtime, or result-integrity error.
130 / 143 Interrupted.
  • --provider is a closed enum (openai, openrouter, fireworks, amazon-bedrock, plus one cheaper-inference path). There is no generic OpenAI-compatible option, so a self-hosted gateway is reachable only through native Codex config overrides.
  • Routing inference through your own gateway does not confer entitlement. Runs that use OpenAI inference still need Codex Security access on the account behind the key.
  • Supplied-issue patching needs a clean tree, while GitLab artifacts have to live inside the project directory. Those two constraints collide, so the order is: work outside the checkout, patch first, copy artifacts in afterwards.

Limits not to promise

  • Never promise DAST auto-fix. validate reasons over source evidence and does not run the application, so a runtime finding with no source location cannot be assessed until somebody maps the endpoint to its handler. Dynamic validation exists through --validation-prompt-file, with setup, authorized targets, expected results and cleanup, but treat that as its own project.
  • --max-cost is an estimated guardrail, not a billing cap. In-flight requests can exceed it.
  • --external-sandbox disables the agent's own filesystem and network enforcement. Only use it inside a container that provides that isolation, never as a workaround for a runner that cannot sandbox.
  • Some vulnerability classes and protected findings need Trusted Access for Cyber. Check before promising coverage, not after.
  • Research preview: pin the CLI version deliberately instead of tracking latest, and retest authentication, artifacts and report ingestion on every bump. The published version moves faster than the vendor's own examples.
  • A 200 on /responses proves nothing about a gateway route. A bridged LiteLLM deployment answers that path and drops Responses-only fields, including tool declarations, which surfaces as an unexplained failure mid-run.
  • Read coverage and exclusions before calling anything clean. Completion is not certification, and a diff scan says nothing about the rest of the repository.

Reaching a self-hosted gateway

The agent runs from an isolated Codex home, so a custom provider has to be defined inside it. Put the settings in a profile file named after the profile, then select it with --codex "profile='<profile>'".

# $CODEX_HOME/<profile>.config.toml
model = "<alias the gateway exposes>"
model_reasoning_effort = "high"
model_provider = "<provider-id>"

[model_providers.<provider-id>]
name = "<display name>"
base_url = "https://<gateway>/v1"
wire_api = "responses"           # required; the agent speaks the Responses API
env_key = "<ENV_VAR_HOLDING_THE_KEY>"
requires_openai_auth = false     # never attempt ChatGPT or OpenAI account auth

The route must be Responses-native. A deployment with no native Responses configuration bridges /v1/responses through /v1/chat/completions, converting the request and approximating or dropping Responses-only fields. Verify the deployment, not the route:

curl -s "$BASE/model/info" -H "Authorization: Bearer $ADMIN_KEY" \
| jq '.data[] | {name: .model_name, model: .litellm_params.model,
                 endpoints: .model_info.supported_endpoints}'

/v1/responses must appear in model_info.supported_endpoints. That opt-in is read per deployment, is independent of the provider prefix, and applies to new requests without a restart. For a custom native provider, --auth auto and --auth api-key use the environment variable named by model_providers.<id>.env_key, while --auth chatgpt selects stored account auth and omits the provider key, so a provider that needs its own key cannot use it.

Wiring into GitLab CI

Split credentials so that no job can read another job's secret. Three secrets, three scopes:

Credential Scope Used by
Model key Gateway virtual key Both stages, through the provider profile.
Read token read_api The validate stage only, to pull the findings list.
Write token api, write_repository The publish stage only, to push a branch and open a draft MR.
  • Copy each secret into a shell variable, unset the original, and launch the agent with env -i plus an explicit minimal environment (PATH, HOME, LANG, CI, CI_PROJECT_DIR, CODEX_HOME, CODEX_SECURITY_STATE_DIR, and the provider key). The agent runs repository-controlled commands and must not inherit the job environment.
  • Keep the whole run outside the checkout (WORK_DIR=/tmp/...) and copy results into the project directory at the end. Work files under $CI_PROJECT_DIR dirty the tree and make patch refuse to run.
  • The job needs git, python3, ripgrep, util-linux for the sandbox check, curl, and glab for --create-pr. Bake them into a pinned runner image instead of installing at job time.
  • Fail early and loudly: unshare -Ur true (the agent sandboxes itself with user namespaces), then --version, then a --dry-run --verbose pass that prints the resolved provider, model and effort without starting a paid run.
  • --setup-git-credential-helper on glab auth login lets the branch push reuse the same token. CI_JOB_TOKEN cannot create a merge request, so the write path needs its own project access token.
  • GitLab's findings API needs scope=all, because it defaults to dismissed findings only. The vulnerabilities and vulnerability-findings endpoints are marked deprecated in favour of GraphQL, and responses are paginated (20 by default), so a large backlog needs its own paging.

Running it under a CI time budget

A GitLab job cannot run forever, and a timeout is a hard kill rather than a pause button. Nothing in the agent resumes a batch, so the design has to make the kill both unnecessary and cheap: keep the work unit small, let the loop own its own clock, and publish every finding the moment it verifies.

The inversion that makes this work is boring and easy to get wrong: the script's budget has to expire before the job timeout, which has to expire before the project maximum. A 45 minute budget inside a 50 minute job inside a 60 minute project ceiling means the pipeline stops itself at a point it chose, prints what it did, and leaves the rest for the next run. GitLab never gets to kill a push that is in flight.

Every iteration starts from a clean clone at the base commit, because the patch command refuses to run against a dirty tree. One finding, one call, one decision:

while IFS=$'\t' read -r id statement; do
  remaining=$(( BUDGET - ( $(date +%s) - started ) ))
  [ "$remaining" -lt "$P90" ] && { echo "budget stop: $remaining left"; break; }

  git -C "$WORK" checkout -f -q "$BASE_SHA"      # patch refuses a dirty tree
  git -C "$WORK" reset --hard -q "$BASE_SHA"
  git -C "$WORK" clean -qfd

  ( cd "$WORK" && env -i PATH="$PATH" HOME="$AGENT_HOME" CI=true \
      LITELLM_API_KEY="$key" \
      timeout "$CALL_TIMEOUT" codex-security patch "$statement" \
      --assess-patch-risk --json > "$OUT/patch-$id.json" 2> "$OUT/patch-$id.err" )
  rc=$?

  case "$(classify "$id" "$rc")" in
    verified)                          publish_patch.sh "$id" "$files" ;;
    timeout|error|sandbox_unavailable) retry_once "$id" ;;
    *)                                 record_terminal "$id" ;;   # a judgement
  esac
done < "$WORKLIST"

Every outcome is classified, because an exit code is not a security judgement. Exit 124 is our own ceiling firing, exit 2 is a runtime error, and a clean exit with no_change is a decision the agent made. Only verified is published, and only the infrastructure classes are retried. 7 statuses, three different responses:

Outcome What it means What the pipeline does
verified A fix was produced and the agent's own verification passed. The only class that gets committed and opened as a draft MR.
no_change The agent judged that nothing needs changing. Recorded. Never retried: it is a judgement, not a failure.
blocked The agent needs a decision it is not allowed to make. Recorded. A human decides; the loop does not guess.
failed A fix was produced but did not verify. Recorded. Read the reasoning rather than rerunning it unchanged.
timeout Our own per-call ceiling fired (exit 124). Infrastructure. One retry if the budget still allows it.
sandbox_unavailable, error, interrupted Operational failure, not a security judgement. One retry, capped by the attempt limit; then it stays recorded.
no_patch_applied The statement was too vague for the agent to act on. Recorded. Sharpen the statement; a rerun changes nothing.

Who holds the credential

The agent is the least trustworthy process in the pipeline, because it runs repository-controlled commands. So it gets no repository credential at all: it is launched with env -i, a HOME that holds no glab or git configuration, and exactly one secret, the model key. A separate publisher step holds the only write_repository token, stages exactly the files the CLI reported as changed, commits, pushes a branch named after the finding, and opens a draft MR.

That split pays for itself twice. The agent cannot leak a credential it never had, and because the branch name comes from the finding id, the remote becomes a second idempotency source: a run that lost its progress file still refuses to publish a finding that already has a branch. It is also why this pipeline does not use patch --create-pr, even though the command supports it: that flag puts the write credential inside the agent's own process, which is the one place it should never be.

Two traps worth knowing before you start

A loop that always starts from the same ordered list starves its own tail. If the budget runs out at finding seven of thirty, the next run has to continue at eight. That comes free from a stable ordering plus a recorded marker, but only if the marker is consulted before the agent is called.

The other trap is social. One change per merge request is excellent for review, while thirty draft merge requests are thirty notifications. Run the first week without publishing, read the diffs as artifacts, and let the team agree the volume is worth the review time before the notifications start.

Proof of concept

Four steps, each with an exit criterion that has to hold before the next one starts. The order matters: sizing a budget before measuring anything is how a pilot turns into a story about timeouts.

Step 1, half a day: measure instead of guessing

Run validate over five hand-picked findings in a clone, one call at a time, with a 600s ceiling. Log wall time, cost, and whether schema-constrained JSON comes back at all.

Exit criteria. A p50 and p90 seconds per finding, and a yes or no on the gateway schema question. Without those numbers any budget you set is a guess.

Step 2, week 1: patch without publishing

Same five findings, patch with assess-patch-risk and JSON, publishing off. Results stay artifacts and a reviewer reads the diffs.

Exit criteria. A security reviewer agrees the fixes are worth review time, and you have a patch p90 to put in CS_PER_FINDING_P90.

Step 3, week 2: publish a small seed

Turn on branch, push and draft MR for eight to ten confirmed findings, with a 45 minute budget inside a 50 minute job ceiling.

Exit criteria. The number of merge requests equals the number of verified results, no secret appears in the job log, and a rejected fix produces no branch.

Step 4, week 3 and after: put it on a schedule

Nightly validate, then the budgeted patch loop, then the report job that reads the merge requests back from the API.

Exit criteria. Two consecutive runs work on disjoint sets of findings, and a run that hits the budget loses nothing.

Deliberately out of scope for the pilot:

  • A deep scan of the whole repository inside the pilot budget.
  • Auto-fixing DAST findings. They have no source location to reason about.
  • One job for the entire backlog. Its blast radius is the whole backlog.
  • Disabling the sandbox to make a runner work. Fix the runner instead.

Where findings come from in GitLab

Source How to get it Best for
Vulnerability report GET /projects/:id/vulnerability_findings with a read token. The backlog view: what is open right now, after human triage.
SAST artifact The gl-sast-report.json artifact from the scanner job. The whole raw output, including findings GitLab did not promote to records.
DAST artifact The report artifact from the DAST job. Runtime findings. Most of them need triage before anything can be patched.

The scanner's own payload arrives as a JSON string in finding.raw_metadata. For SAST the location lives there as location.file and location.start_line. DAST locations describe a request (hostname, path, method, param), which is why a DAST finding cannot go straight into validate: there is no source line to reason about.

Open risks

Everything below comes from OpenAI's, LiteLLM's and GitLab's published documentation rather than from execution. None of it has run on a real runner yet. There are 8 items to close before this is taken seriously, and the first one is deliberately at the top because it is the most likely place the design has to change.

Assumption How to close it
--auth api-key accepts the custom provider's environment key. The preflight run. This is the most likely place the design needs a change.
The gateway alias is Responses-native, not bridged. Check model_info.supported_endpoints. If it is bridged, that becomes a gateway ticket before anything starts.
The model behind the alias can produce schema-constrained JSON. Run validate on a single finding and inspect the output. Without it, the confirm-then-patch gate needs another mechanism.
Supplied-issue patching can run unattended in a CI checkout, and the files the CLI reports are the files that changed. One real run, then git status and git diff --stat in the clone. The branch is cut from exactly those reported paths.
Field paths in the vulnerability response match what the mapping script expects. Dump one real response and compare. The endpoints are marked deprecated in favour of GraphQL.
Findings with no source location can be mapped reliably. For DAST, assume they cannot in the first iteration and plan triage as its own step.
Entitlement semantics hold when inference is routed through the gateway. Confirm with the account owner whether Codex Security access follows the key that reaches the model.
Fix quality holds on whatever model sits behind the alias. Compare a few agent-authored fixes against a hosted frontier model. If the gateway fronts a smaller model, expect validated-fix behaviour to degrade.

Verification status

What was actually exercised on this machine:

  • The CI pipeline parses as YAML, and every shell block inside it passes bash -n.
  • The three helper scripts ran against synthetic GitLab payloads: a SAST finding with a location in raw_metadata became a statement, a DAST finding without one went to the triage list, a finding with broken metadata was handled without crashing, a confirmed verdict produced a patch candidate, and not_applicable did not.
  • The time-budgeted loops ran end to end against stub binaries and a real local git remote, 36 checks: a budget stop before any call, a killed call classified as timeout, one retry for infrastructure only, branch-based idempotency proven with the progress file deleted, and the write token proven absent from the agent's environment.
  • Every shell block in the pipeline passes bash -n, the include parses as YAML, and the report script exits 2 when a published finding carries no merge request link.

What has not happened, and this matters: the pipeline has never run on anyone's GitLab runner, has never touched a real gateway alias, and its fix quality has never been compared against human-authored fixes. The timings in the budget variables are placeholders, not measurements. Treat the gateway, CI and budget sections as a harness-tested design, not a proven recipe.
