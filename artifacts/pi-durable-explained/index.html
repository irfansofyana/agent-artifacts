Pi Durable: when a saved chat is not enough

Research snapshot: 5 October 2026. Pi Durable launched alongside Pi 1.0 on 1 October 2026 as the separate, experimental @earendil-works/pi-durable package; it is not a switch you enable in the ordinary Pi coding-agent CLI. Its package changelog starts at 1.0.0, and the README warns that its API can change between releases.[4][5][2]

The short answer

Pi sessions save history; Pi Durable saves work in progress. The normal Pi CLI already saves sessions by default, lets you reopen one with pi --continue or pi --resume, branches history, and compacts old context. That is excellent for a human returning to a coding task. Pi Durable is a library for building a host application whose model calls, tool calls, queues, conversation state and application tasks are checkpointed to storage and can resume after its process dies. It does not replace the standard Pi CLI.[3][1][2]

A useful mental model: a Pi session is a recoverable notebook; Pi Durable is a recoverable job engine with that notebook attached. This analogy describes the distinction, not a claim that every external side effect can be rolled back.[1][2]

The problem it solves

Suppose an agent is fixing a test in a remote container, researching several issues in parallel, and receiving messages from a browser and a chat bot. With a saved CLI session, you can reopen the transcript and manually tell Pi to continue after a crash. The old shell process, pending job queue and half-executed operation do not thereby become an automatically resumed application workflow. Earendil explicitly describes that human-driven resume as the existing coding-agent model, and positions Durable for long runs, multiple surfaces and multiple people steering an agent.[1][3]

Durable commits state before showing it to clients and models work as tasks with checkpoints. After a restart, reopen the same SQLite/JSONL storage and call harness.resume(); unfinished work continues from a checkpoint. Interrupted model requests may be sent again, while only tools declared replay-safe rerun automatically. Unsafe or unknown side-effecting tool calls instead report interruption to the model for reconciliation. A stable requestId deduplicates a retried submission, not arbitrary external side effects.[1][2]

What is inside the box

  • Harness + storage: a host owns a storage backend and a scheduler; MemoryStorage is for ephemeral experiments, SQLite or JSONL for restarts. One process owns a storage at a time; the library does not provide cross-process locking.[1][2]
  • Conversations + tasks: a root conversation can create/fork others, and each model generation, tool call and custom task has durable state. A conversation may use its own model, tools, instructions and execution directory.[1][2]
  • Extensions: named bundles of tools, prompt sections, hooks and tasks. The built-in CodingTools extension provides read, write, edit, bash; a Node execution environment connects them to local files/processes. These are not automatically your existing CLI extensions or settings.[1][2]
  • Live clients: subscribers can join or reconnect to committed state, view streamed work and queued inputs, then steer or queue follow-ups. Your application still has to build the web/chat transport, auth and UI.[1][2]
  • Context management: automatic/background compaction and forks help keep long conversations inside model context windows; this is context management, not infinite literal recall.[1][2]

How to try it safely

First: do not modify your daily Pi installation. Make a disposable Node project; the package needs Node >=22.19.0 according to its manifest and the npm registry queried on 5 October 2026. The documented install is:[2][6]

mkdir pi-durable-lab && cd pi-durable-lab
npm init -y
npm install @earendil-works/pi-durable @earendil-works/pi-ai @earendil-works/chord

The quickest upstream demos are in the Pi source checkout; after building the monorepo, launch its experimental durable coding-agent TUI or vacation-planner TUI. These are demos, not a pi --durable mode:[1]

npm install && npm run build
node packages/coding-agent/src/experimental/durable/main.ts
node packages/coding-agent/src/experimental/vacation/main.ts

Run those two commands from a Pi source checkout, not inside pi-durable-lab. Inspect the demo before giving it access to a valuable working directory.[1]

For your own host, follow this minimal lifecycle (adapt provider/model and credentials to an account you control): register CodingTools, supply a NodeExecutionEnv, open persistent SQLite storage, create a root conversation, submit input, and wait. On a later process start, open the same database, reinstall the same extensions, reacquire the root and resume. The upstream README and announcement contain the complete imports and API examples.[1][2]

import { BACKGROUND_CONTEXT } from "@earendil-works/chord/context";
import { createModels } from "@earendil-works/pi-ai/models";
import { openaiProvider } from "@earendil-works/pi-ai/providers/openai";
import { createRegistry, Harness } from "@earendil-works/pi-durable";
import { NodeExecutionEnv } from "@earendil-works/pi-durable/env/node";
import { openNodeSqliteStorage } from "@earendil-works/pi-durable/storage/sqlite/node";
import { CodingTools } from "@earendil-works/pi-durable/tools";

const ctx = BACKGROUND_CONTEXT;
const models = createModels();
models.setProvider(openaiProvider()); // uses OPENAI_API_KEY
const registry = createRegistry();
registry.install(CodingTools);
const harness = await Harness.open(
  await openNodeSqliteStorage("./agent.sqlite"),
  { models, registry, env: ({ cwd }) => new NodeExecutionEnv({ cwd: cwd ?? process.cwd() }) },
  ctx,
);
const root = await harness.root(ctx, {
  agent: { model: { provider: "openai", modelId: "gpt-6-sol" }, cwd: process.cwd() },
});
harness.resume();
const submitted = await root.submit(
  { type: "input", content: "Inspect this repository and suggest a small test improvement", requestId: "lab-task-1" },
  ctx,
);
console.log((await submitted.wait(ctx)).status);
await harness.close(ctx);

Run this example as an ESM TypeScript file on a supported Node runtime, with a valid OPENAI_API_KEY and a model ID your provider actually offers; the displayed model ID follows upstream's documentation rather than a verified entitlement on your account. This guide has not run a paid model request. A deliberate restart test is to submit a longer task, terminate the host during it, restart the same script against the same database, and inspect whether work resumes; do not delete the database or alter the requestId for that test. Do not use side-effecting tools to prove replay safety.[1][2]

Where this improves a coding-agent workflow

  1. Unattended overnight CI repair/review batches: store each issue or review in a conversation/task; after a container restart the host resumes outstanding work. Use separate checkouts for concurrent agents, and require explicit approval before pushes or deploys. This is an architectural use case, not built-in CI integration.[1][2]
  2. A browser + Telegram/Slack front end for the same agent: one host owns storage; clients reconnect to the committed view and steer an active conversation without restarting its task. You must implement transport, identity and authorization yourself.[1][2]
  3. Parallel reviewer and implementer: fork or create separate conversations with a cheaper/read-only reviewer, its own checkout and instructions, while the main coding task runs. Upstream includes a reviewer example; sharing one mutable checkout would still risk conflicts.[1][2]
  4. Durable research/subagent work: child conversations and custom tasks can survive a restart; a replay-safe parent tool can reconnect to its existing child instead of spawning a duplicate. Subagents are assembled from primitives rather than enabled by one built-in flag.[1][2]

For your current one-person terminal Pi use, I would not adopt Durable yet. Keep pi --continue / /resume for ordinary interruptions. Prototype Durable only if you are building an always-on coding service, multi-client interface, or overnight batch orchestrator and are willing to maintain a small host application. It is experimental and adds persistence, lifecycle, replay-policy and operational responsibilities.[1][2][3]

Guardrails and non-goals

  • Not magic exactly-once execution: requestId protects input deduplication; a deploy, payment, push or mutable shell command may have completed outside the database before a crash. Give safe read-only tools replay: "safe"; leave side-effecting calls non-replayable and reconcile outcome explicitly, ideally with an external idempotency key. Do not infer that bash is automatically safe to retry.[1][2]
  • Not a multi-writer database service: use one owner process per storage, connect remote clients to that host, and back up persistent state. SQLite's documented WAL synchronous = NORMAL survives process crashes but may lose the newest commits on power/host failure; JSONL offers { fsync: true } for stronger flush behavior.[1][2]
  • Not a hosted product or CLI extension: you provide auth, ingress, UI, process supervision, execution isolation and permissions. NodeExecutionEnv lets tools touch files and processes with the host's privileges, so start with a disposable checkout and an isolated runtime. Existing Pi CLI sessions are not documented as automatically migrated into Durable storage.[1][2]
  • Not an API stability promise: the package itself says experimental, with breaking changes possible between releases. Pin a version for anything beyond a spike.[2][5]
