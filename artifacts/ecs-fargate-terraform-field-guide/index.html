1. The mental model

Do not memorize services first. Track the unit of work from image to network identity.

Build
Container image
Immutable application package in ECR.
→
Declare
Task definition
Image, CPU/RAM, ports, roles, logs, health checks.
→
Run
Task
One running copy of that definition.
→
Maintain
Service
Keeps a desired task count healthy and deploys revisions.

Fargate lets ECS run containers without you managing EC2 capacity. Each Fargate task has its own kernel, CPU/memory resources, and elastic network interface (ENI). That is a useful workload boundary, not a replacement for application authorization.[1]

ECS

The scheduler and control plane. It registers task definitions, starts/stops tasks, replaces unhealthy service tasks, and integrates with load balancers.

Fargate

The serverless compute launch type. You pay for requested task CPU/memory while it runs instead of managing a worker-node fleet.

Cluster

A logical ECS boundary. With Fargate it is not a pool of servers you administer; it groups services, tasks, capacity-provider policy, and observability.

Task definition

A versioned deployment contract. Changing the image or environment produces a new revision; a service must be updated to roll it out.[2]

2. Tasks vs services: pick the right lifecycle

UsePrimitiveExamplesFailure model
Always-on HTTP/APIECS serviceChat API, model gateway, MCP serverMaintain desired count; ALB health checks; rolling deployment
Finite background workRunTaskPDF conversion, report generation, document ingestionCaller/queue owns retry, timeout, idempotency and result state
Scheduled workScheduled taskNightly index refresh, cleanup, cost reportEventBridge triggers task; alarms detect misses

The expensive beginner mistake

Putting a long-running background job inside an HTTP request. The load balancer timeout, deploy, or task replacement will eventually teach you why that was a bad idea. Put durable job state in RDS/DynamoDB/S3, enqueue work, and make workers restartable.

For the company-agent architecture

Use services for the trusted shared plane: web/API, chat orchestration, model gateway, retrieval, and private MCP tools. Use short-lived tasks only for a bounded executor job. Never make a task's local disk your conversation database.

3. Networking: every Fargate task is a VPC citizen

Fargate requires awsvpc network mode. A task receives a private IP through its ENI; containers inside the same task share localhost. Put application tasks in private subnets. An ALB belongs in public subnets and forwards to task IP targets.[2][3]

Inbound

Internet → CloudFront/WAF (optional) → ALB → service security group → task security group. Allow task ingress only from the ALB or a known internal security group.

Outbound

Prefer VPC endpoints for ECR, CloudWatch Logs, S3, Secrets Manager and Bedrock when available. Use NAT only for approved internet egress; it is not a security policy by itself.[3]

Task ENI limits

Every task consumes VPC addresses. Plan subnet CIDR capacity for peak task count, deployment overlap, and worker bursts—not just today's desired count.

Load balancer target type

Fargate services behind an ALB/NLB use target type ip, not instance.[1]

4. IAM, secrets and logs: the separation that matters

Execution role

Used by the ECS/Fargate agent to pull ECR images, emit awslogs, and retrieve injected secrets. It is not the permission set your application should use.[2]

Task role

Credentials delivered to application containers for their own AWS calls—e.g. an S3 prefix or Bedrock invocation. Keep it least-privilege and specific to the workload.[4]

# Rule of thumb
execution role = "can ECS start the container?"
task role      = "what may the application do after it starts?"

Use Secrets Manager/Parameter Store for sensitive configuration. Do not bake secrets into images or Terraform variables committed to source control. Task roles make CloudTrail attribution include the task context, which is useful for audit.[4]

5. Terraform: provision the boring, important substrate

Terraform describes desired infrastructure, tracks it in state, and plans changes before applying them.[5] Start with a small module boundary: networking is owned separately; the ECS service module receives subnet and security-group IDs.

Minimal service module skeleton

terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = ">= 6.0, < 7.0" }
  }
}

provider "aws" { region = "ap-southeast-3" }

resource "aws_ecs_cluster" "this" {
  name = "company-ai"
}

resource "aws_cloudwatch_log_group" "app" {
  name              = "/ecs/company-ai-api"
  retention_in_days = 30
}

resource "aws_ecs_task_definition" "api" {
  family                   = "company-ai-api"
  requires_compatibilities = ["FARGATE"]
  network_mode             = "awsvpc"
  cpu                      = 512
  memory                   = 1024
  execution_role_arn       = aws_iam_role.execution.arn
  task_role_arn            = aws_iam_role.app.arn

  container_definitions = jsonencode([{
    name      = "api"
    image     = "${aws_ecr_repository.api.repository_url}@${var.image_digest}"
    essential = true
    portMappings = [{ containerPort = 8080, protocol = "tcp" }]
    logConfiguration = {
      logDriver = "awslogs"
      options = {
        awslogs-group         = aws_cloudwatch_log_group.app.name
        awslogs-region        = "ap-southeast-3"
        awslogs-stream-prefix = "api"
      }
    }
    healthCheck = {
      command     = ["CMD-SHELL", "curl -f http://localhost:8080/health || exit 1"]
      interval    = 30
      timeout     = 5
      retries     = 3
      startPeriod = 20
    }
  }])
}

resource "aws_ecs_service" "api" {
  name            = "company-ai-api"
  cluster         = aws_ecs_cluster.this.id
  task_definition = aws_ecs_task_definition.api.arn
  desired_count   = 2
  launch_type     = "FARGATE"

  network_configuration {
    subnets          = var.private_subnet_ids
    security_groups  = [aws_security_group.api.id]
    assign_public_ip = false
  }

  load_balancer {
    target_group_arn = aws_lb_target_group.api.arn
    container_name   = "api"
    container_port   = 8080
  }
}

Do not copy this blindly

This is a teaching skeleton, not an apply-ready production stack. You still need a VPC, ECR repository, private subnets, ALB/target group, security groups, roles, CI image pipeline, remote Terraform state and variables. The point is to recognize the boundaries before hiding them in a module.

Terraform workflow that does not cause drama

terraform fmt -recursive
terraform init
terraform validate
terraform plan -out=tfplan
# review the plan with a human who owns the AWS account
terraform apply tfplan

Keep state remote, encrypted, and locked; do not use local state for a shared production account. Use separate environments/accounts or at least isolated state per environment. Pin provider versions, and promote an image by digest—not a mutable latest tag.

8. Check yourself

Question: Your container needs to read one S3 prefix after startup. Where should that permission live?
B — task role. The execution role lets ECS/Fargate perform startup work such as pulling images and sending logs. The task role is what the application container receives for AWS API calls.[4]
Question: Why is assign_public_ip = false the normal setting for an API task behind an ALB?
Because the ALB is the public ingress point. The task should live in private subnets and accept traffic only from the ALB security group. It still needs an intentional egress route—VPC endpoints and/or a controlled NAT path—for the dependencies it uses.[3]

Sources and scope

This guide is deliberately focused on ECS on Fargate and Terraform infrastructure. It does not teach Docker fundamentals, a full VPC design, Kubernetes, or an AI-agent framework. Learn those separately when the product requires them.
