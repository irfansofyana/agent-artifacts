How to read this guide

This guide teaches LangChain Deep Agents for JavaScript/TypeScript (deepagents on npm) by building one agent, chapter by chapter, until it is a production service on AWS. Each chapter opens with a problem the previous version of the agent ran into, introduces the concept that fixes it, and closes with the next problem.

Running example: IncidentScout. An on-call assistant that investigates production incidents. It starts as a single tool call ("fetch logs for service X"), then learns to keep notes in files, remember past incidents across conversations (Postgres on Aurora), run analysis scripts in a sandbox, call observability tools over MCP, read dashboard screenshots, survive long investigations, split work across specialist subagents, and ask a human before it posts to the incident channel.

Source rules used throughout.

  • Every claim is sourced and every chapter ends with a Sources line. Official docs come first: docs.langchain.com (Deep Agents JS pages, plus the LangGraph/LangChain JS pages and the JS API reference they link to). Where the official docs are silent, the guide also draws on GitHub (langchain-ai/deepagentsjs, langchain-ai/langchainjs, langchain-ai/langchain-aws, community repos, open issues/PRs) and community blogs/tutorials — always named and linked, and always marked by kind: [GitHub] for an issue/PR/repo, [community] for a blog or tutorial. A claim that is my own synthesis rather than something a source states is marked Composition, and a claim I could not source anywhere, official or community, is marked Not covered anywhere I could find.
  • AWS-specific deployment steps come from docs.aws.amazon.com and are marked with the label [AWS docs]. LangChain's Deep Agents docs do not describe deploying backends or sandboxes on AWS, so every AWS recipe here is an AWS-docs recipe, not a LangChain one.
  • Where you asked about something the docs do not cover, the guide says Not covered in the docs instead of filling the gap.
  • Glue code that combines documented APIs (for example wiring a documented Postgres checkpointer into a documented createDeepAgent parameter) is marked Composition so you know it is assembled from documented parts rather than copied from one page.

Versions. The docs reference feature gates such as deepagents>=1.9.1 (permissions, Runtime-based namespace factories), >=1.9.0 (multimodal backends, V2 backend protocol), >=1.8.4 (subagent structured output), and >=1.6.0 (current summarization). Starting in v0.7 task planning is opt-in. Pin a recent version and check the JS changelog before upgrading.

Chapter 1 — What a Deep Agent is (and isn't)

The problem

You already know the basic tool-calling loop: send messages plus tool schemas to an LLM, execute whatever tool calls come back, append the results, repeat until the model answers without calling a tool. That loop is fine for "what's the weather in Tokyo". It breaks down for an incident investigation, which is long, multi-step, produces huge intermediate outputs (log dumps), needs a plan, and may need delegation and human sign-off. You end up hand-building planning, scratch storage, context trimming, delegation, and approvals around the loop.

The concept: an agent harness

The docs position LangChain's three packages as layers:

Layer Package What it adds
Runtime LangGraph Durable execution, streaming, human-in-the-loop, persistence
Framework LangChain (createAgent) Abstractions: content blocks, the agent loop, middleware, integrations
Harness Deep Agents (createDeepAgent) Predefined tools, prompts, subagents, filesystem, context management

A Deep Agent is the same core tool-calling loop as other agent frameworks, with built-in capabilities layered on: a virtual filesystem, automatic summarization and offloading of large results, subagent spawning through a task tool, optional planning, skills, memory, human-in-the-loop, and prompt caching for Anthropic and Bedrock models. deepagents is built on LangChain's building blocks and uses LangGraph to run agents in production. If you want the loop without these capabilities, the docs point you to LangChain's createAgent or a custom LangGraph workflow.

Analogy: createAgent is an engine; createDeepAgent is the engine already mounted in a car with a boot (filesystem), a sat-nav (planning), a crew (subagents), and a driver who can radio base for approval (HITL).

IncidentScout v1

// src/v1.ts — based on the Deep Agents quickstart (overview page)
import * as z from "zod";
import { createDeepAgent } from "deepagents";
import { tool } from "langchain";

// A plain LangChain tool: name + description + Zod schema.
// The description tells the model WHEN to use it.
const fetchLogs = tool(
  async ({ service, minutes }) =>
    `[stub] last ${minutes}m of logs for ${service}: ERROR timeout calling payments-db ...`,
  {
    name: "fetch_logs",
    description:
      "Fetch recent error logs for one service. Use when investigating an incident.",
    schema: z.object({
      service: z.string().describe("Service name, e.g. checkout-api"),
      minutes: z.number().default(15).describe("Look-back window in minutes"),
    }),
  },
);

const agent = createDeepAgent({
  // provider:model string; the docs show "bedrock:..." for Amazon Bedrock Converse
  model: "bedrock:anthropic.claude-sonnet-4-6",
  tools: [fetchLogs],
  systemPrompt: "You are IncidentScout, an on-call incident investigator.",
});

const result = await agent.invoke({
  messages: [{ role: "user", content: "checkout-api is throwing 500s. What's going on?" }],
});
console.log(result.messages.at(-1)?.content);

Even this minimal agent already has more than fetch_logs: it can call ls, read_file, write_file, edit_file, glob, grep, and task (delegate to the auto-added general-purpose subagent). You did not wire any of that.

Gotchas

  • Model strings. Use provider:model to switch models quickly, or pass an initialized chat model (for example new ChatBedrockConverse({ model, region })) when you need parameters. Bedrock credentials follow AWS's Bedrock getting-started setup, which the LangChain page links to.
  • Task planning is opt-in since v0.7. Older tutorials that expect a write_todos tool by default are out of date (Ch10).
  • await or not. The docs show createDeepAgent(...) both with and without await; invoke is always async.

Next problem

Our stub returns one line. Real log fetches return tens of thousands of tokens. Before we feed that into the loop, we need to understand what the loop actually is and where state lives.

Chapter 2 — Architecture: the loop, the stack, and where state lives

The problem

IncidentScout v1 forgets everything between invoke calls, and we cannot tell which user is asking. Before adding features we need a mental model of what createDeepAgent actually builds.

The loop

LangChain describes the core agent loop as two steps repeated until the model stops calling tools: (1) model call — the LLM gets the prompt and tool schemas and returns either an answer or tool-call requests; (2) tool execution — the requested tools run and their results are appended. createAgent compiles this loop into a LangGraph graph; middleware is not a separate runtime, its hooks run inside that compiled graph. createDeepAgent is that same loop with a pre-assembled middleware stack.

flowchart TD
    IN([invoke: messages + config.thread_id + context]) --> BA[beforeAgent hooks]
    BA --> BM[beforeModel hooks]
    BM --> WM[wrapModelCall hooks<br/>summarization, prompt caching]
    WM --> LLM[(Chat model)]
    LLM --> AM[afterModel hooks]
    AM -->|tool calls?| TC{any tool calls?}
    TC -->|yes| WT[wrapToolCall hooks<br/>HITL, logging, retries]
    WT --> TOOLS[Tools: yours + ls/read_file/.../task]
    TOOLS --> BM
    TC -->|no| AA[afterAgent hooks]
    AA --> OUT([final state: messages, files, ...])
    CP[(Checkpointer)] -. saves state every step .- TOOLS

Middleware hooks (from the AgentMiddleware reference): beforeAgent and afterAgent run once per invocation; beforeModel / afterModel run around each model call; wrapModelCall and wrapToolCall wrap each individual model or tool call. Node-style hooks return partial state updates that are merged into agent state.

The Deep Agents stack

With only a model, the main agent typically includes, in order: FilesystemMiddleware → SubAgentMiddleware (because the general-purpose subagent is auto-added) → SummarizationMiddleware → PatchToolCallsMiddleware → prompt caching (for supported providers) → harness-profile extras and excluded-tool filtering.

The full order, adding optional slots as you pass parameters:

  1. SkillsMiddleware (only with skills)
  2. FilesystemMiddleware (permissions enforcement lives here when you pass permissions)
  3. SubAgentMiddleware (when at least one synchronous subagent exists)
  4. SummarizationMiddleware
  5. PatchToolCallsMiddleware (repairs dangling tool calls after interrupts/cancellation)
  6. AsyncSubAgentMiddleware (only with async subagents)
  7. Your middleware argument
  8. Harness profile extras
  9. Excluded-tool filtering
  10. Prompt caching (AnthropicPromptCachingMiddleware / BedrockPromptCachingMiddleware)
  11. MemoryMiddleware (only with memory; placed late so memory edits don't invalidate the cache prefix)
  12. HumanInTheLoopMiddleware (only with interruptOn)

You cannot remove FilesystemMiddleware or SubAgentMiddleware via excluded_middleware; the docs say that is intentionally rejected. Hide tools with a harness profile's excluded_tools instead.

How state flows

Think of three separate channels:

Channel What it holds Lifetime How you pass it
Graph state messages, the files of the default filesystem, custom middleware state (and todos if you enable planning) One thread, persisted by a checkpointer invoke(input, { configurable: { thread_id } })
Runtime context Per-run data: user id, org id, feature flags, API keys One run; propagates to subagents invoke(input, { context: {...} }), typed by contextSchema
Store Long-term key/value data across threads Until you delete it store parameter + StoreBackend (Ch4)

Runtime context is not automatically shown to the model; a tool, middleware, or dynamic prompt must read it. The final system prompt is assembled from: your systemPrompt, the base agent prompt, the memory prompt, the skills prompt, the filesystem prompt, the subagent (task) prompt, your middleware prompts, and the HITL prompt.

IncidentScout v2: threads and users

// src/v2.ts — threads + runtime context (Going to production, Context engineering pages)
import { createDeepAgent } from "deepagents";
import { MemorySaver } from "@langchain/langgraph";
import { tool } from "langchain";
import type { ToolRuntime } from "@langchain/core/tools";
import * as z from "zod";

const contextSchema = z.object({ userId: z.string(), orgId: z.string() });

const fetchLogs = tool(
  async ({ service }, runtime: ToolRuntime<unknown, typeof contextSchema>) => {
    // Tools read per-run context directly; the model never sees it unless you return it.
    const org = runtime.context?.orgId;
    return `[stub] logs for ${service} in org ${org}`;
  },
  { name: "fetch_logs", description: "Fetch recent error logs for a service.",
    schema: z.object({ service: z.string() }) },
);

const agent = createDeepAgent({
  model: "bedrock:anthropic.claude-sonnet-4-6",
  tools: [fetchLogs],
  contextSchema,
  checkpointer: new MemorySaver(), // dev only: RAM, lost on restart (Ch4 swaps in Postgres)
});

const config = { configurable: { thread_id: crypto.randomUUID() } };
const ctx = { userId: "u-42", orgId: "acme" };

await agent.invoke({ messages: [{ role: "user", content: "Investigate checkout-api 500s" }] },
  { ...config, context: ctx });
// Same thread_id => same conversation, message history is restored from the checkpointer
await agent.invoke({ messages: [{ role: "user", content: "Was it the DB?" }] },
  { ...config, context: ctx });

Gotchas

  • thread_id and context are independent. One scopes the conversation; the other carries per-run data. Pass both on every production call.
  • MemorySaver loses everything on restart. Use a persistent checkpointer (Postgres) in production.
  • Don't mutate variables captured by middleware. Subagents, parallel tools, and concurrent threads run at the same time; keep counters in graph state instead.
  • Checkpointer is required for human-in-the-loop and for skills/memory examples that rely on thread state.

Next problem

Now fetch_logs returns real data — 60,000 tokens of it. Where should that go so it doesn't drown the conversation?

Chapter 3 — The virtual filesystem

The problem

A real fetch_logs call returns a 60k-token dump. In a plain loop that dump sits in messages forever: every later model call pays for it, and a few such calls overflow the context window. The agent also has nowhere to keep a running hypothesis list or a draft postmortem except its own chat history.

The concept

The harness gives every agent a virtual filesystem: a set of file tools that operate through a pluggable backend (Ch4). The model sees ordinary file operations; you decide where the bytes actually live.

Tool What it does
ls List a directory with metadata (size, modified time)
read_file Read with line numbers; offset/limit paging for large files; returns multimodal content blocks for images, audio, video, PDFs (Ch7)
write_file Create new files
edit_file Exact string replacement (with a replace-all mode)
glob Find files by pattern, e.g. **/*.py
grep Search contents (files-only, content with context, or counts)
execute Shell commands — only with sandbox backends (Ch5)

Why it exists: the filesystem is the substrate for several other harness features — skills, memory, code execution, and context management all read and write files. It lets the agent move bulk out of the conversation and pull fragments back with read_file and grep when needed.

Automatic offloading. When a tool result exceeds a token threshold (default 20,000), the harness writes it to the backend and replaces it in the conversation with a file-path reference plus a preview of the first 10 lines. When large tool inputs (for example the full content of a write_file call) are redundant because the content is already on disk, older ones are truncated to a pointer once context crosses 85% of the window. Internally the harness writes offloaded results under /large_tool_results/ and conversation history under /conversation_history/.

In the default setup (StateBackend) files live in graph state for the current thread and are checkpointed with it. That backend is also shared between the supervisor and its subagents: files a subagent writes remain visible to the supervisor after the subagent finishes.

IncidentScout v3: notes on disk, a seeded runbook

// src/v3.ts — seeding files uses the StateBackend pattern from the Customization page
import { createDeepAgent, type FileData } from "deepagents";
import { MemorySaver } from "@langchain/langgraph";

function fileData(content: string): FileData {
  const now = new Date().toISOString();
  return { content, mimeType: "text/plain", created_at: now, modified_at: now };
}

const agent = createDeepAgent({
  model: "bedrock:anthropic.claude-sonnet-4-6",
  tools: [fetchLogs], // from Ch2; now returns large dumps
  checkpointer: new MemorySaver(),
  systemPrompt: `You are IncidentScout.
Keep a running investigation log in /notes/timeline.md and hypotheses in /notes/hypotheses.md.
When a tool result is saved to a file, use grep and read_file with offset/limit instead of re-fetching.
Consult /runbooks/ before proposing remediation.`,
});

const config = { configurable: { thread_id: "inc-2026-0912" } };
await agent.invoke(
  {
    messages: [{ role: "user", content: "checkout-api 500s since 09:12 UTC. Investigate." }],
    // Seed the default StateBackend's filesystem; virtual paths must start with "/"
    files: { "/runbooks/checkout-api.md": fileData("# checkout-api\n1. Check payments-db pool...") },
  },
  config,
);

Gotchas

  • StateBackend is checkpointed at every step, so avoid writing large files there in production (Going to production).
  • Calling StateBackend methods outside a graph run (for example uploading files from app code) won't take effect until the graph executes. Seed through the files input or use a different backend.
  • Offloading measures text tokens only. An image-only message is not offloaded by size (Ch7).
  • To hide the file tools (for example a read-only agent), use a harness profile's excluded_tools; unused tool schemas are otherwise sent on every turn.

Next problem

Close the thread and the notes are gone. Tomorrow's incident on the same service starts from zero. We need storage that outlives a thread — and we need to choose where it physically lives.

Chapter 4 — Backends: deciding where files actually live

The problem

IncidentScout's notes vanish with the thread, and in a multi-user service we also need to say whose data a file is. The filesystem tools are fine; the storage behind them is the problem.

The concept

A backend implements the storage behind the file tools. You pass one instance to createDeepAgent({ backend }); if you omit it you get new StateBackend(). Backends implement BackendProtocolV2 (ls, read, readRaw, write, edit, glob, grep, optionally uploadFiles/downloadFiles); sandbox backends add execute. V1 backends are auto-adapted.

graph LR

4.1 StateBackend (default) — made durable with Postgres

Files live in LangGraph state for the current thread and persist across turns via your checkpointer. So "deploying StateBackend" really means deploying a persistent checkpointer. The LangGraph docs name PostgresSaver as the production choice.

// src/persistence.ts — Composition: PostgresSaver API (LangGraph JS reference) + createDeepAgent checkpointer param
import { PostgresSaver } from "@langchain/langgraph-checkpoint-postgres";

export const checkpointer = PostgresSaver.fromConnString(process.env.DATABASE_URL!, {
  schema: "agent_checkpoints", // optional; defaults to "public"
});
await checkpointer.setup(); // MUST be called the first time (creates tables/migrations)

import { createDeepAgent, StateBackend } from "deepagents";
import { checkpointer } from "./persistence";

const agent = createDeepAgent({
  model: "bedrock:anthropic.claude-sonnet-4-6",
  backend: new StateBackend(), // same as omitting it
  checkpointer,               // thread state (messages + files) now survives restarts
});

When: per-conversation scratch space; the target of automatic offloading. When not: data another thread must read; big binary artifacts.

Gotchas: keep thread_id under 255 characters with PostgresSaver (use a UUID or hash); checkpoints grow over long conversations, so prune periodically; files written by subagents stay in state after they finish.

4.2 StoreBackend — cross-thread storage on Postgres

StoreBackend stores files in a LangGraph BaseStore. Locally you use InMemoryStore; the docs list a PostgreSQL store in @langchain/langgraph-checkpoint-postgres/store.

// Composition: PostgresStore (LangChain long-term memory page + API reference) + StoreBackend (Backends page)
import { createDeepAgent, StoreBackend } from "deepagents";
import { PostgresStore } from "@langchain/langgraph-checkpoint-postgres/store";

export const store = PostgresStore.fromConnString(process.env.DATABASE_URL!, {
  schema: "agent_store", // optional; PostgresStoreConfig also has ttl, index (pgvector), ensureTables
});
await store.setup();

const agent = createDeepAgent({
  model: "bedrock:anthropic.claude-sonnet-4-6",
  backend: new StoreBackend({
    // Namespace factory: receives a LangGraph Runtime, returns a tuple of strings
    namespace: (rt) => [rt.context.orgId, rt.context.userId, "filesystem"],
  }),
  store,
  contextSchema, // from Ch2: { userId, orgId }
});

Namespace factories control isolation. The Runtime exposes rt.context (your context schema), rt.serverInfo (assistant id, graph id, authenticated user — only when running on LangGraph Server / LangSmith Deployment), and rt.executionInfo (thread id, run id, checkpoint id). Documented patterns: per-user [rt.serverInfo.user.identity], per-assistant [rt.serverInfo.assistantId], per-thread [rt.executionInfo.threadId], per-org [rt.context.orgId].

When: you already run a LangGraph store (Postgres, Redis, etc.), or you deploy on LangSmith (store provisioned automatically — omit store there). When not: without a namespace in multi-user apps — the legacy default namespaces by assistant id, so all users of one assistant share files.

Gotchas:

  • If you self-host on your own LangGraph Server (not LangSmith Cloud), rt.serverInfo is still populated once requests go through the Agent Protocol — the docs' own namespace examples default to rt.serverInfo.user.identity / rt.serverInfo.assistantId (deepagents>=1.9.0; older versions read getConfig().metadata.assistantId instead). Building namespaces from rt.context instead, as this guide does, is for when you call agent.invoke directly from your own process — no LangGraph Server in front of it — which is exactly IncidentScout's ECS setup in Ch11.
  • Namespace components allow only alphanumerics, -, _, ., @, +, :, ~; wildcards are rejected.
  • The docs warn namespace will be required; always set it.
  • Namespace factories receive Runtime in deepagents>=1.9.1; older BackendContext accessors (ctx.runtime, ctx.state) are deprecated.

4.3 CompositeBackend — IncidentScout v4

CompositeBackend(default, routes) routes operations by path prefix; listings and search aggregate and keep original prefixes; the longest prefix wins. The docs recommend StateBackend as the default so internal artifacts (offloaded results, conversation history) stay ephemeral.

// src/v4.ts — thread scratch + durable, per-user incident memory on Postgres

export const backend = new CompositeBackend(new StateBackend(), {

  // /runbooks/ = org-wide, written by app code only (made read-only in Ch10)
  "/runbooks/": new StoreBackend({ namespace: (rt) => [rt.context.orgId, "runbooks"] }),
});

export const agent = createDeepAgent({

});

4.4 FilesystemBackend (local disk)

import { createDeepAgent, CompositeBackend, FilesystemBackend, StateBackend } from "deepagents";

// Recommended wrapping: project files on disk, internal agent data in ephemeral state
const agent = createDeepAgent({
  backend: new CompositeBackend(new StateBackend(), {
    "/workspace/": new FilesystemBackend({ rootDir: "/srv/incident-reports", virtualMode: true }),
  }),
});

When: local dev CLIs, CI pipelines, mounted persistent volumes. When not: web servers or HTTP APIs, and the production page says not to use it in deployed agents. Security: agents can read any accessible file including .env; combined with network tools that enables exfiltration; writes are irreversible. Always set virtualMode: true with rootDir (blocks .., ~, and absolute paths outside root) — without it rootDir provides no security. rootDir must be absolute.

4.5 LocalShellBackend (local shell)

import { createDeepAgent, LocalShellBackend } from "deepagents";
const agent = createDeepAgent({ backend: new LocalShellBackend({ workingDirectory: "." }) });

Extends FilesystemBackend with execute running directly on the host (default timeout 120s, output capped at 100,000 bytes, configurable env). When: trusted local coding tools. When not: production, multi-tenant, or untrusted input — commands run with your user's permissions and virtualMode provides no protection once a shell exists. Pair with HITL if you use it at all.

4.6 ContextHubBackend

Stores the agent's filesystem in a LangSmith Context Hub repo (needs LANGSMITH_API_KEY). The agent repo mounts at /; linked skill repos appear under /skills/. Reads come from a lazily pulled in-memory cache; writes become Hub commits with optimistic parent-commit checks — a concurrent writer can make your write fail, so re-pull and retry. uploadFiles() accepts UTF-8 text only. The JS page shows this backend only in its quick-reference table (ContextHubBackend("my-agent")); check the deepagents API reference for the exact JS constructor.

Chapter 5 — Sandboxes: letting the agent run code safely

The problem

IncidentScout suspects a connection-pool leak and wants to run a quick Python script over a 2 GB log export to count timeouts per minute. LocalShellBackend would do it — on your production host, with your credentials in reach. Not acceptable.

The concept

In Deep Agents, sandboxes are backends. A sandbox backend gives the agent all the normal file tools plus execute, and everything happens inside an isolated environment. The only method a provider must implement is execute(); the BaseSandbox base class builds read/write/edit/ls/glob/grep on top of it by running scripts inside the sandbox. On every model call the harness checks whether the backend implements SandboxBackendProtocol; if not, execute is filtered out and the model never sees it.

graph LR
    subgraph Your service
      APP[App code] -- uploadFiles / downloadFiles<br/>provider API --> SBX
      AG[Agent loop] -- read_file, write_file, execute<br/>via execute() --> SBX
    end
    subgraph SBX[Sandbox]
      FS[(Filesystem)]
      SH[Shell + deps]
    end

Two planes of file access. The agent's tools go through execute() inside the sandbox. Your application code uses uploadFiles() / downloadFiles() (provider-native transfer APIs) to seed inputs before a run and retrieve artifacts after. Large execute output is automatically saved to a file and the agent is told to page through it with read_file.

Integration patterns. Agent in sandbox (image with your agent inside; API keys must live in the sandbox; rebuild to update) vs sandbox as tool (agent runs on your server and calls the sandbox API; keys stay outside; sandbox failures don't lose agent state; pay per execution; adds network latency). All doc examples, and this guide, use sandbox-as-tool.

Lifecycle. Pick thread-scoped (fresh sandbox per conversation, reused across its turns, removed by TTL — the common case) or assistant-scoped (one shared sandbox; repo clones and installed packages persist, so you must add TTLs, snapshots, or cleanup). Sandboxes cost money until shut down.

5.1 LangSmith sandboxes (first-party)

// IncidentScout v5 — thread-scoped sandbox via an async graph factory (Going to production)
import { createDeepAgent, LangSmithSandbox } from "deepagents";
import { SandboxClient } from "langsmith/sandbox";
import type { LangGraphRunnableConfig } from "@langchain/langgraph";

const client = new SandboxClient();

export async function agent(config: LangGraphRunnableConfig) {
  const threadId = config.configurable?.thread_id as string;
  const name = `thread-${threadId}`;
  // Named lookup de-duplicates across runs of the same thread
  const existing = (await client.listSandboxes()).filter((sb) => sb.name === name);
  const sandbox = existing[0] ?? (await client.createSandbox({ name, idleTtlSeconds: 3600 }));
  return createDeepAgent({
    model: "bedrock:anthropic.claude-sonnet-4-6",
    backend: new LangSmithSandbox({ sandbox }),
  });
}

A graph factory is an async function the server calls per run with the run config; it doesn't get a full Runtime, so read thread_id / assistant_id from config.configurable. For one-off scripts, create the sandbox, run, and client.deleteSandbox(sandbox.name) in finally. When: you want managed sandboxes without a third-party account, plus LangSmith snapshots, service URLs, and the auth proxy that injects credentials into outbound requests so secrets never enter the sandbox.

5.6 Bedrock AgentCore — build-your-own (no official JS backend yet)

The backends page mentions "AgentCore" in passing, but the JS sandbox integrations page lists only LangSmith, Deno, Daytona, Modal, Leap0 and Kubernetes — AgentCore is not among them. There is no official deepagents JS AgentCore backend as of this writing.

What exists instead. Python has an official one: langchain-agentcore-codeinterpreter provides AgentCoreSandbox, a SandboxBackendProtocol implementation wrapping AgentCore's Code Interpreter ("a secure, isolated MicroVM environment"). (PyPI, LangChain Python integration page)

# Python reference implementation — from the PyPI package README
from bedrock_agentcore.tools.code_interpreter_client import CodeInterpreter
from deepagents import create_deep_agent
from langchain_agentcore_codeinterpreter import AgentCoreSandbox

interpreter = CodeInterpreter(region="us-west-2")
interpreter.start()
backend = AgentCoreSandbox(interpreter=interpreter)
agent = create_deep_agent(model=model, backend=backend)
try:
    agent.invoke({"messages": [...]})
finally:
    interpreter.stop()  # sessions cannot be reconnected after stop()

On the JS side, a pull request is open but incomplete for this purpose. langchainjs PR #11724 [GitHub] (opened Sep 24, 2026, still open) adds a CodeInterpreterToolkit to @langchain/aws — 11 LangChain tools (execute_code, read_files, write_files, etc.), one sandbox session per thread_id. This gives a JS agent AgentCore tools, not the deepagents execute tool or sandbox-backed filesystem tools. No deepagentsjs issue requesting a real backend turned up in search.

Building one by hand is realistic. The JS sandboxes page says a backend needs only execute() — BaseSandbox builds the rest. AWS ships a TypeScript SDK, bedrock-agentcore, whose CodeInterpreter class exposes executeCode, executeCommand, readFiles, writeFiles, listFiles, removeFiles, startSession/stopSession (AWS TypeScript SDK reference) — but these return plain strings, not {stdout, stderr, exitCode}. The lower-level @aws-sdk/client-bedrock-agentcore (AWS SDK v3) exposes InvokeCodeInterpreterCommand directly against the InvokeCodeInterpreter API, which is the better fit for a real exit code. Composition — outline only, untested, not from any source:

// Design sketch: subclass BaseSandbox, drive it with the low-level AWS SDK v3 client.
// Verify BaseSandbox's exact method/type names against reference.langchain.com/javascript/deepagents
// before relying on this — it has not been run.
import { BedrockAgentCoreClient, InvokeCodeInterpreterCommand,
         StartCodeInterpreterSessionCommand, StopCodeInterpreterSessionCommand } from "@aws-sdk/client-bedrock-agentcore";

class AgentCoreSandboxJS extends BaseSandbox {
  private client = new BedrockAgentCoreClient({ region: "us-east-1" });
  private sessionId?: string;
  async start() {
    const { sessionId } = await this.client.send(new StartCodeInterpreterSessionCommand({
      codeInterpreterIdentifier: "<your-vpc-mode-interpreter-arn>", sessionTimeoutSeconds: 1800 }));
    this.sessionId = sessionId;
  }
  async execute(command: string) {
    const res = await this.client.send(new InvokeCodeInterpreterCommand({
      codeInterpreterIdentifier: "<same-arn>", sessionId: this.sessionId,
      name: "executeCommand", arguments: { command } }));
    // drain res.stream, map stdout/stderr/exit code into the BaseSandbox result shape
  }
  async stop() { await this.client.send(new StopCodeInterpreterSessionCommand({ sessionId: this.sessionId! })); }
}

Resource setup [AWS docs]. A code interpreter is a named resource, created with networkMode: "PUBLIC"|"SANDBOX"|"VPC"; VPC mode takes vpcConfig.securityGroups / vpcConfig.subnets and is the only mode that can reach a private Aurora instance. (create-code-interpreter CLI reference) Sessions default to a 900-second timeout, max 28,800 (8 hours) (resource management), and cannot be reconnected once stopped — stop it in a finally and start a fresh one for the next thread. Required IAM action: bedrock-agentcore:InvokeCodeInterpreter.

Pricing [AWS docs]. Billed per second, by vCPU-hour and GB-hour, with a 1-second minimum and a 128MB memory floor; AWS's own worked example puts 30,000 two-minute executions a month at about $109/month. (AgentCore pricing)

Security — read before choosing a network mode. Independent security research (Unit 42, BeyondTrust, Sonrai Security, Nov 2025–Apr 2026) found that Sandbox mode allowed DNS-based data exfiltration, and that the microVM's instance-metadata service (MMDS) lacked session-token enforcement, letting sandboxed code extract the execution role's credentials — a risk that persists in VPC mode too, unless Route 53 Resolver DNS Firewall is attached. A retest in Apr 2026 found VPC mode without that firewall "still vulnerable." [community], dated and disputed on exact timeline between sources: Unit 42, BeyondTrust, haitmg.pl retest. Treat any AgentCore sandbox as able to leak whatever it can reach on the network, credentials included, until you've attached DNS Firewall and reviewed IAM scope on the execution role.

5.7 Community providers

The JS sandbox integrations page also links Leap0 and a community Kubernetes sandbox hosted outside docs.langchain.com. Not covered in the docs beyond the links.

Security considerations (all providers)

  • Sandboxes protect your host; they do not protect against context injection. Anyone who controls part of the input can make the agent run arbitrary commands inside the sandbox.
  • Never put secrets in a sandbox (env vars, mounted files, the secrets option). Keep authenticated calls in tools that run outside the sandbox, or use a credential-injecting proxy (LangSmith auth proxy).
  • Block network when not needed (Modal blockNetwork: true); Deno has full network by default.
  • Filesystem permissions do not apply to sandboxes; with a sandbox as the Composite default, every permission path must sit under a named route.
  • Treat everything produced in the sandbox as untrusted; review outputs; use middleware to redact sensitive patterns.
  • If you must inject secrets anyway: HITL on all tool calls, restrict network, narrowest scope, shortest lifetime, monitor egress — and the docs still call it unsafe.

5.8 Sandboxes and Postgres: what's actually documented

No source — official or community — describes Postgres itself as a sandbox backend. Widening the search to GitHub and blogs doesn't change that; what exists instead are two different, narrower patterns depending on whether the code needs Postgres running inside the sandbox or just reachable from it.

Postgres inside the sandbox (Daytona, documented). Daytona sandboxes "can run Docker containers inside them (Docker-in-Docker)… Run databases (PostgreSQL, Redis, MySQL) and other services," recommending at least 2 vCPU / 4GiB memory for this. A Snapshot can bake in "the filesystem, installed packages, dependencies, and settings" — so a Postgres image plus seed data becomes a reusable template. (Daytona snapshots, Daytona sandboxes)

Postgres reachable from the sandbox (AgentCore, Modal). AgentCore's VPC network mode is AWS's own documented way for sandboxed code to reach "private resources within your AWS environment such as databases" — i.e., your Aurora cluster (Ch5.6). Modal sandboxes default to open outbound, but outbound_cidr_allowlist can restrict them to specific CIDR ranges; its domain allowlist only covers TLS/443, so it doesn't help with raw Postgres traffic on 5432. (Modal networking docs)

Community repos exist, but solve a different problem. DiTo97/deepagents-backends [GitHub] and giurlanda/deep-db-agents [GitHub] both use Postgres with Deep Agents — but as a PostgresBackend storing the agent's virtual files, or as a database the agent queries through tools, not as sandbox infrastructure. Neither shows sandboxed code opening a live connection to a database.

Why this matters for security — [community], several independent sources agree. LangChain's own sandbox docs already warn that secrets "injected into a sandbox… can be read and exfiltrated by a context-injected agent, even short-lived or scoped credentials." A May 2026 arXiv paper on agentic attack surfaces found that "Docker sandboxing does not help… the database must remain accessible for the tool to function," but that a read-only Postgres role "eliminates UPDATE, DELETE, and INSERT," lowering risk from High to Moderate, and recommends wrapping writes in BEGIN/ROLLBACK with human confirmation. (MATRA, arXiv 2605.10763) A practitioner dev.to post makes the same point more bluntly: "A database connection string is a bearer credential… the only honest remediation is to rotate the database password" once it has passed through a model's context; the fix is a read replica or a least-privilege role, not a promise the model won't misuse it. (dev.to/wolfhound1995) A read-only role alone doesn't stop resource exhaustion either — pair it with statement timeouts. (Adaptive.live)

What IncidentScout does (recommendation, not from a single source): run Aurora SQL as a host-side LangChain tool inside the ECS task — credentials never enter the sandbox — against a read-only role or read replica, with statement timeouts. Give the sandbox only exported CSV/Parquet via uploadFiles() for its analysis scripts. If sandboxed code genuinely must run SQL, prefer a disposable Postgres inside a Daytona sandbox seeded from an export over reaching the real Aurora cluster at all; if it must reach Aurora, do it only through an AgentCore custom interpreter in VPC mode, pointed at a read-only replica, with Route 53 Resolver DNS Firewall attached (Ch5.6's security note explains why that firewall is not optional).

Deploying sandboxes on AWS

Not covered in the docs. LangSmith, Daytona, Deno, and Modal are provider-hosted; the LangChain docs only show your agent calling their APIs, and no page describes running them inside your AWS account. What you deploy on AWS is the agent (Ch11): it needs outbound network access to the provider API and the provider credential. [AWS docs] Put that credential in Secrets Manager and inject it via the ECS task definition's secrets; rotation requires a new task. Node VFS runs inside the agent process, so it "deploys" with the agent — but the docs rule it out for production. AgentCore is the exception worth a special note: it is the one sandbox provider that runs inside your own AWS account rather than a third party's, and Ch5.6 covers building a custom backend for it.

Chapter 6 — Tools and MCP

The problem

Hand-writing a LangChain tool for every observability API doesn't scale, and the platform team already runs MCP servers for metrics, traces, and deploy history. Also, the sandbox chapter left a rule: authenticated calls belong in tools outside the sandbox.

The concept

Everything you pass in tools sits beside the built-in harness tools (ls, read_file, write_file, edit_file, glob, grep, execute with sandboxes, task). Three sources:

  1. Custom LangChain tools — tool(fn, { name, description, schema }) with a Zod schema.
  2. Prebuilt LangChain integrations — for example TavilySearch wrapped in a tool, as the docs do.
  3. MCP tools — @langchain/mcp-adapters' MultiServerMCPClient connects to one or more servers and returns LangChain tools you pass straight in.

Tool metadata is prompt. The docs ask for a clear name, a description that says when to use the tool, and a description for every argument.

Gotchas

  • Permissions (Ch10) don't cover custom or MCP tools that touch files — only the built-in file tools. Guard those tools yourself or with backend policy hooks.

  • Tool errors: when a tool throws, the run halts by default; ToolErrorMiddleware is not yet available in JS (Ch10).
  • Not covered in the Deep Agents pages: MCP stdio servers, OAuth, tool filtering, stateful sessions — the Deep Agents pages defer these to LangChain's separate MCP guide.

Chapter 7 — Multimodal inputs

The problem

Incidents come with screenshots of dashboards, PDFs from vendors, and occasionally a screen recording. Text-only handling misses the signal.

The concept

Deep Agents supports multimodal workflows when the chosen model supports them. Three entry points:

  1. User messages carry LangChain standard content blocks (text + image/file/audio/video).
  2. read_file returns multimodal content blocks for supported file types in the agent's filesystem (images .png .jpg .jpeg .gif .webp .heic .heif; video .mp4 .mpeg .mov .avi .flv .mpg .webm .wmv .3gpp; audio .wav .mp3 .aiff .aac .ogg .flac; files .pdf .ppt .pptx). V2 backends return binary content as Uint8Array with a mimeType (deepagents>=1.9.0).
  3. Custom tools can return an array of content blocks instead of a string.
// User input with an image (Multimodal page)
await agent.invoke({
  messages: [{
    role: "user",
    content: [
      { type: "text", text: "This is the checkout latency panel. When did it start?" },
      { type: "image", url: "https://grafana.example.com/render/checkout-p99.png" },
    ],
  }],
}, { ...config, context: ctx });

// A tool that returns text + image blocks
const captureDashboard = tool(
  async ({ panel }) => [
    { type: "text", text: `Snapshot of ${panel}:` },
    { type: "image", url: `https://grafana.example.com/render/${panel}.png` },
  ],
  { name: "capture_dashboard", description: "Snapshot a Grafana panel.",
    schema: z.object({ panel: z.string() }) },
);

// Reading a binary file directly from a backend in app code
const res = await backend.read("/workspace/screenshot.png");
if (!res.error && res.content instanceof Uint8Array) console.log(res.mimeType); // "image/png"

How compression treats media (important)

  • Offloading counts text tokens only. Non-text blocks are preserved, and an image-only message is never offloaded because of its size.
  • Summarization is text-only. When older turns are summarized, their image/audio/video/file blocks are dropped; the model only sees what the summarizer wrote about them. The text rendering of the conversation still goes to the filesystem.
  • Built-in compression never resizes images or lowers resolution.

Gotchas and recommended patterns

  • Save large media to a backend (or object store) and pass paths or URLs, not base64 blocks, in long conversations.
  • Have a tool that produces images return a short description plus a path.
  • Push image-heavy inspection into a subagent so the main agent gets a compact text result (Ch9).
  • If your provider charges many tokens per image, tune summarization thresholds or provide a custom token counter.
  • Check your provider's supported MIME types; the harness passes blocks through but the model must accept them.

Chapter 8 — Context engineering: what the model sees, and for how long

The problem

Long investigations push the context window. At the same time we want more in the prompt: team conventions ("always include customer impact first"), and deep procedures ("how to read a Postgres lock graph") that are only relevant sometimes. Stuffing everything into systemPrompt is wasteful; leaving it out makes the agent dumb.

The concept: five kinds of context

Type You control Scope
Input context System prompt, memory, skills, tool prompts Applied every run
Runtime context context passed at invoke time Per run; propagates to subagents
Context compression Offloading + summarization (built in) Automatic near limits
Context isolation Subagents (Ch9) Per delegation
Long-term memory Store-backed paths such as /memories/ (Ch4) Across conversations

Input context: prompt, memory, skills

  • systemPrompt is static and prepended to the built-in prompt. If it must vary per request ("you have read-only access"), use dynamicSystemPromptMiddleware, which can read request.runtime.context and request.runtime.store.
  • Memory = AGENTS.md files passed via memory. Always loaded, no progressive disclosure — keep them short. Content is stored in your backend, so the agent can update memory from feedback.
  • Skills = directories with a SKILL.md (Agent Skills standard) plus scripts, templates, references. Progressive disclosure: only the frontmatter is read at startup; the full skill loads when the agent decides it's relevant. Keep each skill to one workflow; move detail into referenced files.
  • Tool prompts: built-in middleware appends usage guidance for file tools, task, and HITL; your tools contribute their descriptions.
  • Prompt caching is automatic for Anthropic and Bedrock (Claude/Nova) models, covering the static prompt sections (base instructions, memory, skills). No configuration needed. On Bedrock, cached content must exceed 1,024 tokens for a checkpoint to take effect.

Compression: offloading, then summarization

  1. Offloading (Ch3): tool results over 20,000 tokens are replaced by a path + 10-line preview; redundant large tool inputs are truncated once context crosses 85% of the window.
  2. Summarization (deepagents>=1.6.0): when context crosses ~85% of the model's max_input_tokens and nothing more can be offloaded, an LLM writes a structured summary (session intent, artifacts created, next steps) that replaces old history, keeping ~10% of tokens as recent context. The original messages are also written to the filesystem as a canonical record the agent can search. Without a model profile it falls back to a 170,000-token trigger and keeps 6 messages. If any model call raises ContextOverflowError, the agent immediately summarizes and retries.

Analogy: offloading is moving papers from your desk into a labelled drawer; summarization is writing a one-page brief of the meeting and filing the transcript.

Scoping long-term memory

Scope Namespace Example
User (recommended default) user id "I prefer concise responses"
Assistant assistant id "Cap posts at 280 characters"
Global/org org id "Never disclose internal pricing" (read-only for the agent)

Two ways memory gets written. By default the agent writes memory during the conversation itself ("hot path") — immediate, but it adds latency and the agent has to multitask. The documented alternative is background consolidation ("sleep time compute"): a separate consolidation deep agent, deployed alongside the main one, periodically reads recent conversation history and merges facts into the memory store, triggered by a LangSmith cron job. Match the cron cadence to how often users actually talk to the agent, and keep it in sync with the lookback window the consolidation agent's own search tool uses — mismatched windows either reprocess the same conversations or silently drop ones outside the window.

Episodic memory (what happened and in what order, not just what was learned) rides on the checkpointer: every conversation is already a checkpointed thread. To make past threads searchable, wrap the LangGraph SDK's thread search in a tool that filters by userId or orgId pulled from runtime context, so IncidentScout can look back at how a similar incident was resolved rather than re-deriving the fix from scratch.

Gotchas

  • Shared memory is a prompt-injection vector. If one user can write memory another user's run reads, they can inject instructions. Make org-wide paths read-only for the agent (permissions, Ch10) and write them from app code.
  • Streamed tokens include summarization output. Filter them by metadata:
for await (const [namespace, chunk] of await agent.stream(input, { streamMode: "messages" })) {
  const [message, metadata] = chunk;
  if (metadata?.lcSource === "summarization") continue; // skip summary tokens in the UI
  render(message);
}
  • Memory is always injected; long memory files cost tokens every turn. Put detail in skills.
  • Custom subagents don't inherit skills (Ch9); the general-purpose one does.

Chapter 9 — Subagents: delegation and context isolation

The problem

A checkout outage touches checkout-api, payments, inventory, the DB, and the CDN. One agent checking all five drags every raw trace into one context and does it serially.

The concept

The main agent gets a built-in task tool. Each call spins up an ephemeral subagent with a fresh context, which runs autonomously to completion and returns one final report as the tool result. Subagents are stateless and cannot send multiple messages back. The parent can issue several task calls in one turn to run them in parallel. This is "context quarantine": the dozens of tool calls behind a finding never enter the parent's window.

graph TB
    M[IncidentScout coordinator] -->|task| L[log-analyst]
    M -->|task| T[trace-analyst]
    M -->|task| D[db-analyst]
    L -->|isolated work| R1[summary]
    T -->|isolated work| R2[summary]
    D -->|isolated work| R3[structured JSON]
    R1 --> M
    R2 --> M
    R3 --> M

Use subagents for multi-step work that would clutter context, specialized domains, tasks needing a different model, and keeping the coordinator high-level. Don't for simple single-step tasks, or when the parent needs the intermediate context.

Defining subagents

SubAgent field Notes Inherits from parent?
name (req.) Used by task; becomes lc_agent_name metadata —
description (req.) How the parent decides to delegate — be specific —
systemPrompt (req.) Include tool guidance and output format No
tools Keep minimal; overrides entirely when set Yes, by default
model provider:model string or model instance Yes, by default
middleware Appended to the subagent stack No
interruptOn Per-subagent HITL; needs a checkpointer Yes; overrides
skills Own skill sources; isolated skill state No (only general-purpose inherits)
responseFormat Structured output, returned to parent as JSON (>=1.8.4) —
permissions Replaces parent rules; [] = unrestricted Yes, by default

For complex workflows, pass a CompiledSubAgent { name, description, runnable } where runnable is a compiled graph (for example from createAgent); a custom LangGraph graph must have a messages state key.

Every deep agent also has a general-purpose subagent (same tools, same model unless overridden, inherits skills). Replace it by defining a subagent named general-purpose; disable it via the harness profile's general-purpose subagent enabled flag, and with no other synchronous subagents the task tool disappears.

Chapter 10 — Steering and guardrails: planning, human-in-the-loop, permissions, fault tolerance

The problem

IncidentScout now acts: it pages people and can post updates. On-call leads want to see its plan, approve anything that notifies humans, stop it from rewriting org runbooks, and not have it die when Bedrock throttles.

10.1 Planning with write_todos (opt-in)

Since v0.7 planning is opt-in. Add todoListMiddleware() to get a write_todos tool; tasks have pending / in_progress / completed status and live in agent state, which UIs can stream as a live checklist. The docs suggest it for long multi-step tasks, less capable models, and progress UIs.

const agent = createDeepAgent({ /* ... */ middleware: [todoListMiddleware()] });

10.2 Human-in-the-loop

interruptOn maps tool names to true (approve/edit/reject/respond), false, or { allowedDecisions: [...] }. It adds HumanInTheLoopMiddleware and requires a checkpointer. Decisions:

Decision Effect Use for
approve Run with original args Send as drafted
edit Run with modified args (editedAction: { name, args }) Fix a recipient
reject Skip; feedback message goes to the agent Deny a side effect
respond Your text becomes the tool result Answering an ask_user-style tool — not for denying side effects 
// IncidentScout v10 — HITL wiring (Human-in-the-loop page)
import { Command } from "@langchain/langgraph";

const agent = createDeepAgent({
  // ...v9...
  interruptOn: {
    page_oncall: { allowedDecisions: ["approve", "edit", "reject"] },
    post_incident_update: { allowedDecisions: ["approve", "reject"] },
  },
  checkpointer, // required
});

let result = await agent.invoke({ messages }, { ...config, context: ctx });
if (result.__interrupt__) {
  const { actionRequests, reviewConfigs } = result.__interrupt__[0].value;
  // Show actionRequests[i].name / .args to the human; collect ONE decision per request, in order
  const decisions = [
    { type: "reject", message: "Impact not confirmed yet. Do not page. Gather error-rate data first." },
  ];
  result = await agent.invoke(new Command({ resume: { decisions } }), { ...config, context: ctx }); // same thread_id!
}

Notes: several gated calls in one step arrive as one batched interrupt; subagents can override interruptOn; tools can call interrupt({...}) themselves and resume with new Command({ resume: {...} }). Make edits conservative — big argument changes can make the model re-plan or repeat calls. Always give reject a clear message about whether to abandon, ask, or try something safer. Because state is checkpointed, an interrupt can wait minutes or days.

10.3 Filesystem permissions (deepagents>=1.9.1)

Declarative rules for the built-in file tools: { operations: ["read" | "write"], paths: [globs], mode: "allow" | "deny" }. First match wins; no match = allowed. Paths must be absolute, without .. or ~. read covers ls, read_file, glob, grep; write covers write_file, edit_file.

permissions: [
  { operations: ["write"], paths: ["/runbooks/**", "/skills/**"], mode: "deny" }, // org content is app-managed
  { operations: ["read", "write"], paths: ["/notes/**", "/memories/**"], mode: "allow" },
],

Specific rules must come before broad ones. Subagents inherit rules unless they set their own (which replace, not merge). Permissions don't apply to custom/MCP tools or to sandbox execute; with a sandbox as the composite default, every rule path must fall under a route or construction throws. For audit logging, rate limits, or content inspection, use backend policy hooks (Ch4).

Reference AWS deployment — [AWS docs] + Composition

The AWS parts below come from AWS documentation; the LangChain parts are the APIs from earlier chapters. The HTTP wrapper around agent.invoke/streamEvents is ordinary Node code and is not described in the LangChain docs.

  1. Network [AWS docs]. A VPC with private subnets for the database and the service. The Aurora tutorial creates a private cluster; resources in the same VPC can reach it, outside ones can't.
  2. Database [AWS docs]. Aurora PostgreSQL cluster (Standard create for availability, backups, maintenance settings). One cluster, two schemas: checkpoints and store. Run checkpointer.setup() and store.setup() once at deploy time. Add pgvector only if you configure PostgresStore's index.
  3. Secrets [AWS docs]. Database credentials, sandbox API key, LangSmith key, MCP tokens in Secrets Manager; referenced from the ECS task definition's secrets. The execution role needs Secrets Manager permissions. Fargate platform 1.4.0+ for JSON-key or version selection. Rotation needs a new task (Force new deployment). Anything in environment variables is visible to the app and its logs — which is exactly why none of it may be forwarded into a sandbox (Ch5).
  4. Compute [AWS docs]. An ECS service on Fargate running your Node container. Give the task role permission to call Bedrock (see AWS's Bedrock getting-started, which the LangChain Bedrock tab links to).
  5. Optional shared disk [AWS docs]. EFS volume on Fargate (platform 1.4.0+, access points) — only if you deliberately run FilesystemBackend in a trusted internal worker; the LangChain docs say not to use host-disk backends in deployed agents.
  6. Egress. The task needs outbound access to the sandbox provider and LangSmith (both external services).
  7. Multi-tenancy (LangChain). Build namespaces from authenticated identity (context.userId, context.orgId); never trust a user id from the request body without your auth layer. Make org-wide paths read-only via permissions.
  8. Sandboxes (LangChain). Thread-scoped with idle TTL; delete in finally for one-off runs; no secrets inside.
  9. Resilience (LangChain). Retries, fallback, call limits; durable checkpoints mean a crashed task's thread can resume from its last step.

Gotchas

  • Don't combine platform-provisioned persistence with your own when on LangSmith Deployment — omit store (and the docs say the checkpointer is configured automatically).
  • rt.serverInfo exists only on LangGraph Server. Self-hosting on ECS, derive namespaces from context.
  • Graph factories are a server feature. On LangSmith Deployment an exported async function is called per run; on your own ECS service, do the equivalent in your request handler.
  • Async everywhere: sandbox creation and MCP connection are network calls.
  • Checkpoint growth: prune old checkpoints.

export async function buildAgent(threadId: string) {

  // Ch3/4/5/8: sandbox is the default (scratch + execute); durable paths route to Postgres
  const backend = new CompositeBackend(new LangSmithSandbox({ sandbox }), {
    "/memories/": new StoreBackend({ namespace: (rt) => [rt.context.orgId, "memories"] }),
    "/runbooks/": new StoreBackend({ namespace: (rt) => [rt.context.orgId, "runbooks"] }),
    "/skills/":   new StoreBackend({ namespace: () => ["skills"] }),
  });

  return createDeepAgent({
    model: "bedrock:anthropic.claude-sonnet-4-6",           // Ch1 (+ automatic Bedrock prompt caching)
    systemPrompt: `You are the IncidentScout coordinator.
Customer impact first, then timeline, then cause. Read /memories/AGENTS.md conventions and /runbooks/.
Delegate per-service log work to log-analyst (in parallel) and heavy analysis to data-cruncher.

    tools: [fetchLogs, pageOncall, postIncidentUpdate, ...mcpTools], // Ch6
    contextSchema,                                          // Ch2
    backend, store, checkpointer,                           // Ch4/5
    memory: ["/memories/AGENTS.md"],                        // Ch8
    skills: ["/skills/"],                                   // Ch8
    subagents,                                              // Ch9
    permissions: [                                          // Ch10 (paths under routes: required with a sandbox default)
      { operations: ["write"], paths: ["/runbooks/**", "/skills/**"], mode: "deny" },
    ],
    interruptOn: {                                          // Ch10
      page_oncall: { allowedDecisions: ["approve", "edit", "reject"] },
      post_incident_update: { allowedDecisions: ["approve", "reject"] },
    },
    middleware: [                                           // Ch10
      todoListMiddleware(),
      modelRetryMiddleware({ maxRetries: 3, backoffFactor: 2.0, initialDelayMs: 1000 }),

      modelCallLimitMiddleware({ runLimit: 50 }),
      toolCallLimitMiddleware({ runLimit: 200 }),
    ],
  });
}

// ---------- Request handler (your HTTP framework calls this) ----------
export async function handleTurn(threadId: string, ctx: Ctx, text: string) {
  const agent = await buildAgent(threadId);
  const config = { configurable: { thread_id: threadId }, context: ctx };
  const result = await agent.invoke({ messages: [{ role: "user", content: text }] }, config);
  if (result.__interrupt__) {
    // Return pending actions to the UI; the human's decisions come back via resumeTurn
    return { pending: result.__interrupt__[0].value.actionRequests };
  }
  return { reply: result.messages.at(-1)?.content };
}

export async function resumeTurn(threadId: string, ctx: Ctx, decisions: unknown[]) {
  const agent = await buildAgent(threadId);
  return agent.invoke(new Command({ resume: { decisions } }),
    { configurable: { thread_id: threadId }, context: ctx });
}

The agent — src/incidentscout.ts

// src/incidentscout.ts — middleware + skills + multimodal files, wired into one Deep Agent.
// Verified against deepagents@1.14.1 / langchain@1.5.12 by test/wiring.test.ts.
import * as z from "zod";
import { createDeepAgent, CompositeBackend, StateBackend, StoreBackend } from "deepagents";
import { createMiddleware, toolErrorMiddleware, modelCallLimitMiddleware, tool } from "langchain";
import type { BaseStore, BaseCheckpointSaver } from "@langchain/langgraph";
import type { BaseChatModel } from "@langchain/core/language_models/chat_models";

// ---------- runtime context: set by YOUR auth layer, never from the request body ----------
export const contextSchema = z.object({ userId: z.string(), orgId: z.string() });

// ---------- skills: seeded by app code into the shared "skills" namespace ----------
const POSTMORTEM_SKILL = `---
name: postmortem
description: Blameless incident postmortem. Use when asked to write up or summarize a resolved incident.
---
# Postmortem
1. Impact first: who was affected, how long, how badly.
2. Timeline in UTC from first signal to resolution.
3. Root cause and contributing factors. No blame on individuals.
4. Action items with owners.
`;

export async function seedSkills(store: BaseStore) {
  // The CompositeBackend strips the "/skills/" route prefix before hitting the store,
  // so the store key is "/postmortem/SKILL.md", visible to the agent at "/skills/postmortem/SKILL.md".
  await new StoreBackend({ namespace: ["skills"], store }).uploadFiles([
    ["/postmortem/SKILL.md", new TextEncoder().encode(POSTMORTEM_SKILL)],
  ]);
}

// ---------- multimodal uploads: org-scoped binary files the agent opens with read_file ----------
export async function uploadIncidentFile(store: BaseStore, orgId: string, path: string, bytes: Uint8Array) {
  const [res] = await new StoreBackend({ namespace: [orgId, "uploads"], store }).uploadFiles([[path, bytes]]);
  if (res.error) throw new Error(`upload failed: ${res.error}`);
}

// In deepagents@1.14.1 the namespace factory receives { state, config, assistantId } — NOT a Runtime,
// so per-run `context` is not visible here. Pass the org id through config.configurable as well.
const orgScoped = (suffix: string) =>
  new StoreBackend({
    namespace: ({ config }) => {
      const org = config?.configurable?.orgId;
      if (typeof org !== "string" || !org) throw new Error("configurable.orgId is required");
      return [org, suffix];
    },
  });

// ---------- custom middleware ----------
export type AuditEvent = { tool: string; ms: number; ok: boolean };

// wrapToolCall: time and record every tool call (built-in file tools included).
const auditTools = (sink: AuditEvent[]) =>
  createMiddleware({
    name: "AuditTools",
    wrapToolCall: async (request, handler) => {
      const t0 = Date.now();
      const res: any = await handler(request);
      const ok = res?.status !== "error";
      sink.push({ tool: request.toolCall.name, ms: Date.now() - t0, ok });
      return res;
    },
  });

// wrapModelCall: add per-org policy from runtime context to the system prompt on every model call.
const orgPolicy = createMiddleware({
  name: "OrgPolicy",
  contextSchema,
  wrapModelCall: (request, handler) =>
    handler({
      ...request,
      systemMessage: request.systemMessage.concat(
        `\nOrg: ${request.runtime.context.orgId}. Never page on-call before customer impact is confirmed.`,
      ),
    }),
});

// ---------- the agent ----------
export function buildAgent(opts: {
  model: BaseChatModel | string;
  store: BaseStore;
  checkpointer: BaseCheckpointSaver;
  audit?: AuditEvent[];
  fetchLogsImpl?: (service: string, minutes: number) => Promise<string>;
}) {
  const fetchLogs = tool(
    async ({ service, minutes }) =>
      (opts.fetchLogsImpl ?? (async (s, m) => `[stub] last ${m}m of ${s}: ERROR timeout payments-db`))(service, minutes),
    {
      name: "fetch_logs",
      description: "Fetch recent error logs for one service. Use when investigating an incident.",
      schema: z.object({ service: z.string(), minutes: z.number().default(15) }),
    },
  );

  const backend = new CompositeBackend(new StateBackend(), {
    "/skills/": new StoreBackend({ namespace: ["skills"] }), // shared, curated by your team
    "/uploads/": orgScoped("uploads"),                         // PDFs, screenshots, exports
    "/memories/": orgScoped("memories"),
  });

  return createDeepAgent({
    model: opts.model,
    systemPrompt: `You are IncidentScout. Customer impact first, then timeline, then cause.
User-provided files live under /uploads/<incident>/ — open them with read_file.`,
    tools: [fetchLogs],
    contextSchema,
    backend,
    store: opts.store,
    checkpointer: opts.checkpointer,
    skills: ["/skills/"],
    permissions: [{ operations: ["write"], paths: ["/skills/**", "/uploads/**"], mode: "deny" }],
    middleware: [
      orgPolicy,
      auditTools(opts.audit ?? []),
      // Earlier in the list = outer wrapper. AuditTools wraps toolErrorMiddleware,
      // so a thrown tool error reaches audit as an error ToolMessage (ok: false), not an exception.
      toolErrorMiddleware({
        onError: (_err, req) => `${req.toolCall.name} failed (upstream error). Try another data source.`,
      }),
      modelCallLimitMiddleware({ runLimit: 30 }),
    ],
  });
}

What each piece does:

  1. seedSkills writes SKILL.md under the store key /postmortem/SKILL.md. The /skills/ route prefix is stripped before the store is hit, so the agent sees /skills/postmortem/SKILL.md. Writing the key with /skills/ makes the skill invisible — the most common mistake.
  2. uploadIncidentFile writes raw bytes (Uint8Array) into [orgId, "uploads"]. Nothing is base64-encoded into the conversation until the agent actually reads the file.
  3. orgScoped builds the namespace from config.configurable.orgId and fails closed if it is missing, so a request without an org can never fall back to a shared namespace.
  4. orgPolicy (wrapModelCall) appends per-org policy to the system message on every model call, reading request.runtime.context — this is where runtime context is available.
  5. auditTools (wrapToolCall) times every tool call, including the built-in file tools, into a sink you control (swap for a logger or metrics client).
  6. toolErrorMiddleware turns exceptions from fetch_logs into a model-readable error message without leaking the raw error text (hostnames, stack traces).
  7. permissions make /skills/ and /uploads/ read-only to the agent: content there is written by app code only, which closes the shared-content prompt-injection path from Ch8.

Gotchas

  • Namespace factory ≠ runtime context (see corrections above). If isolation silently looks wrong, log what your factory receives.
  • Store keys omit the route prefix for skills, uploads and memories alike.
  • Skills need frontmatter with name and description; the description is what the model uses to decide to load the skill, so write it as "Use when…".
  • Custom subagents don't inherit skills — pass them explicitly (Ch9).
  • Media and summarization: old image/PDF blocks disappear when history is summarized; files under /uploads/ can be re-read, inline blocks cannot.
  • fakeModel() is for wiring tests, not quality. It proves the harness plumbing; evaluate prompt and model behaviour separately with a real model.

Next problem

The wiring is verified in isolation. Evaluating whether the model uses these pieces well — picks the right skill, opens the PDF before answering — is an evaluation problem, not a unit-test one.

Glossary

Term Meaning
Agent harness An opinionated, batteries-included layer over an agent loop with built-in tools, prompts, and subagents. Deep Agents is one.
Agent loop Model call → tool execution, repeated until the model stops calling tools.
Assistant A configured agent instance; memory and sandboxes can be scoped to it.
Backend The storage behind the virtual filesystem tools (StateBackend, StoreBackend, CompositeBackend, etc.).
BackendProtocolV2 The interface a backend implements: ls, read, readRaw, write, edit, glob, grep (+ optional file transfer).
BaseSandbox Base class that builds file operations on top of a provider's execute().
Checkpointer LangGraph component that saves a thread's graph state at each step (e.g. MemorySaver, PostgresSaver).
CompiledSubAgent A subagent defined by a prebuilt, compiled graph (runnable).
Context (runtime) Per-run data passed as context and typed by contextSchema; visible to tools/middleware, not automatically to the model; propagates to subagents.
Context isolation / quarantine Doing heavy work in a subagent so only its final result enters the parent's context.
Graph factory An exported async function the LangGraph server calls per run to build the agent (used for per-thread sandboxes).
General-purpose subagent The auto-added subagent with the parent's tools and model; inherits skills.
Harness profile Per-provider/model defaults (e.g. excluded_tools, prompt overrides, general-purpose subagent settings).
HITL (human-in-the-loop) Pausing before configured tool calls for approve / edit / reject / respond decisions, via interruptOn.
Interrupt A LangGraph pause that returns control with __interrupt__; resumed with new Command({ resume }) on the same thread.
Interpreter createCodeInterpreterMiddleware() from @langchain/quickjs: an eval tool running JS in QuickJS, no shell/network.
LangGraph The runtime underneath: durable execution, streaming, interrupts, persistence.
lc_agent_name Metadata key naming which agent/subagent produced a run; used in tracing and tool branching.
MCP Model Context Protocol; MultiServerMCPClient loads MCP server tools as LangChain tools.
Memory (AGENTS.md) Files passed via memory, always injected into the prompt; the agent can update them.
Middleware Hooks (beforeAgent, beforeModel, wrapModelCall, afterModel, wrapToolCall, afterAgent) that run inside the agent graph.
Namespace factory Function (rt) => string[] that scopes StoreBackend data per user, org, assistant, or thread.
Offloading Replacing large tool inputs/results in the conversation with a file reference (+ preview).
Permissions First-match-wins allow/deny rules on built-in file tools, by operation and path glob.
Progressive disclosure Skills load only frontmatter at startup and full content when relevant.
Prompt caching Automatic caching of static prompt sections for Anthropic and Bedrock models.
Sandbox A backend with an isolated environment and an execute tool.
Skill A directory with SKILL.md (Agent Skills standard) plus resources, loaded on demand.
Store LangGraph BaseStore for cross-thread key/value data (e.g. InMemoryStore, PostgresStore).
Subagent An ephemeral child agent launched by the task tool with fresh context, returning one report.
Summarization Replacing older history with an LLM-written summary near the context limit, while writing the full history to the filesystem.
Thread One conversation, identified by thread_id; scope of checkpoints and default files.
Virtual filesystem The file tools (ls, read_file, write_file, edit_file, glob, grep, execute) and the backend behind them.
write_todos Planning tool added by todoListMiddleware() (opt-in since v0.7).
