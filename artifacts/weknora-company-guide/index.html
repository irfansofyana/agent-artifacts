Enterprise setup guide · researched October 16, 2026

Start with one General workspace for common knowledge. Add separate workspaces wherever the readers must differ. Use Google or JumpCloud for login, then manage workspace membership explicitly.

The permission rule to remember: a normal KB is readable by members of its workspace. Creating a KB does not make you its only reader. An organization, also called a shared space, connects workspaces through explicit resource shares.[6][4]

Native generic OIDC supports the integration pattern for Google and JumpCloud. It does not provide automatic directory-group-to-workspace mapping. Configure one upstream OIDC provider; if both identities must coexist, a broker is a separate architecture decision.[12]

Version and evidence

The latest release checked was v0.8.3, published October 14, 2026. This guide audits upstream 973d9d051f2d2a1704bf3a92dd6b1c0b3d1988d4, twenty commits after that release. OIDC configuration, JIT provisioning, invitations and the basic workspace/share model are already in v0.8.3. A post-release creator-role-floor change is called out below. This is a static source review, not a completed deployment or penetration test.[3][20]

Observed implementation is cited inline. Layouts, deployment settings and rollout steps marked recommended are engineering recommendations. No live Google or JumpCloud login was performed.

1. What belongs to what?

  • User: one login identity. The same person can belong to several workspaces and hold a different role in each.[5]
  • Workspace: called Tenant in the backend. Treat it as the normal resource and audience boundary. Users operate in an active workspace; switching context does not grant membership.[5][6]
  • Knowledge base: the source workspace owns it. Documents, FAQ entries and chunks belong beneath it. A share points to that source resource; it does not move or copy ownership into a shared space.[4]
  • Agent: a workspace resource with configured knowledge/tool scope. Sharing an agent can grant readers access to the source-workspace KBs included in that scope.[8]
  • Organization / shared space: a collaboration overlay. Its members are workspaces, not individual employees. It is not a company root containing departmental tenants.[4]

To share a KB across workspaces, first enroll both source and receiving workspaces in the same organization. The source workspace needs editor-or-admin organization membership, and the person sharing must satisfy the source resource's authoring guard. Then create the explicit KB share. Joining the organization alone does not publish every source KB.[7][10]

A single company workspace is enough when everyone may read all its ordinary KBs. Department names and “mine” filters help organize content; they are not reader ACLs. For confidential People or Finance content, change the workspace audience.[6]

2. RBAC has two role ladders

A person's workspace role and a workspace's organization role answer different questions. Workspace roles control what the person can do locally; organization roles constrain what that workspace can do through shared resources.[5][4]

Human user actionViewerContributorAdminOwner
Read/search ordinary workspace KBs; ask questionsYesYesYesYes
Create KBs / agentsNoYesYesYes
Change own resourcesNo*YesYesYes
Change another creator's resourcesNoNoYesYes
Workspace infrastructure/settingsNoNoYesYes
Membership/role changes and invitationsNoNoNoYes
Manage API keys / delete workspaceNoNoNoYes

Swipe the matrix on small screens. Human JWT permissions with RBAC enabled; machine API keys and platform administration are separate. The actual member/invitation mutation routes require Owner, despite broader descriptions of Admin in some comments.[9][10][11]

*Release caveat: the audited main branch requires a resource creator to remain Contributor or above to use the ownership bypass. That floor was added after v0.8.3. Do not assume the same demotion behavior in v0.8.3; test it on the exact image you deploy or choose a release containing the fix.[20][3]

The organization ladder is admin > editor > viewer. For each shared-KB path, effective permission is the lower of the share's grant and the receiving workspace's organization role; a human workspace Viewer is then capped at read-only. If several valid sharing paths exist, the highest effective result wins.[7]

Share permission: editor
Receiving workspace's organization role: viewer
Employee's workspace role: Contributor
Result: read-only

Share permission: editor
Receiving workspace's organization role: editor
Employee's workspace role: Viewer
Result: read-only

A second organization granting editor access can broaden access even if the first grants only viewer. Review all sharing paths rather than treating one restrictive grant as a global deny.[7]

3. Recommended company layout

  1. Create General for approved company-wide content. Most employees should be Viewers; designated content maintainers should be Contributors.
  2. Create restricted workspaces only when audience or administration differs. Give People and Finance their own memberships; keep confidential KBs out of General.
  3. Add a company shared space only when cross-workspace reuse is needed. Publish approved common KBs there at viewer permission. Department users can also join General for everyday questions.
  4. Use a small number of Owners for membership and credential administration. Assign Admin where infrastructure and broad content maintenance are needed, not merely because someone writes documents.
  5. Curate an employee-facing assistant with an explicit approved KB list. Do not make employees configure models, storage or retrieval settings.

These recommendations follow from workspace-wide reading and explicit cross-workspace grants. A shared space adds collaboration, not infrastructure isolation. If platform operators must be isolated from particular material, separate deployments and backends need their own security design.[6][7]

Agent sharing needs content review. A reachable shared agent can grant direct read access to its KB scope, even without an explicit agent ID on a KB read. Selecting all can expose future source-workspace KBs; only Admin+ may share that scope. A prompt telling an agent not to reveal secrets is not a substitute for limiting its KBs.[6][8]

4. Google and JumpCloud SSO

Google: use a Google OAuth web client with OIDC, exact callback registration and openid profile email. Use an organization-restricted app configuration where available and verify that an outsider is rejected. Google documents stable sub identifiers and the hd claim for Workspace membership; WeKnora's current email-based account linking does not enforce those policies for you.[2][14]

JumpCloud: configure a Custom OIDC app with Authorization Code and client authentication client_secret_post. Grant the app only to intended users/groups. Use the discovery endpoint for your JumpCloud region. Incoming group claims do not become WeKnora memberships automatically.[1][14][12]

Recommendation: if Google Workspace is already the company's identity authority, start there. If JumpCloud already controls application access and lifecycle, choose JumpCloud as the single WeKnora provider. Avoid adding a broker solely for a pilot.

For a portal tile, use the same-origin /api/v1/auth/oidc/start endpoint. It redirects into an ordinary authorization-code flow and constructs its callback from the request host and forwarded HTTPS scheme. An existing IdP session may reduce prompts; this does not promise silent authentication. Configure the reverse proxy to preserve the public host and overwrite trusted forwarding headers.[13]

Register exactly https://knowledge.example.com/api/v1/auth/oidc/callback at the IdP. The hostname here is illustrative. Use the real canonical HTTPS hostname consistently.[13][2]

Illustrative environment configuration

These are verified backend variable names, not a tested deployment file. Ensure your actual Compose/Kubernetes configuration passes every variable into the application; an unreferenced host .env entry has no effect. Runtime database settings may override deployment defaults.[12]

# Shared backend policy
JWT_SECRET=<high-entropy-secret-shared-across-app-replicas>
DISABLE_REGISTRATION=true
WEKNORA_AUTH_DEFAULT_TENANT_MODE=tenantless
WEKNORA_TENANT_SELF_SERVICE_CREATION_ENABLED=false
WEKNORA_TENANT_ENABLE_RBAC=true

# Google OIDC provider
OIDC_AUTH_ENABLE=true
OIDC_AUTH_PROVIDER_DISPLAY_NAME=Google Workspace
OIDC_AUTH_ISSUER_URL=https://accounts.google.com
OIDC_AUTH_DISCOVERY_URL=https://accounts.google.com/.well-known/openid-configuration
OIDC_AUTH_CLIENT_ID=<google-web-client-id>
OIDC_AUTH_CLIENT_SECRET=<secret-from-secret-manager>
OIDC_AUTH_SCOPES="openid profile email"
OIDC_USER_INFO_MAPPING_USER_NAME=name
OIDC_USER_INFO_MAPPING_EMAIL=email

For JumpCloud, replace the provider block, clear inherited Google issuer/endpoint overrides, and let discovery supply the exact issuer. The following discovery URL is the US example; EU and IN hosts differ.[1][12]

OIDC_AUTH_ENABLE=true
OIDC_AUTH_PROVIDER_DISPLAY_NAME=JumpCloud
OIDC_AUTH_DISCOVERY_URL=https://oauth.id.jumpcloud.com/.well-known/openid-configuration
OIDC_AUTH_CLIENT_ID=<jumpcloud-client-id>
OIDC_AUTH_CLIENT_SECRET=<secret-from-secret-manager>
OIDC_AUTH_SCOPES="openid profile email"
OIDC_USER_INFO_MAPPING_USER_NAME=name
OIDC_USER_INFO_MAPPING_EMAIL=email

5. Make first use predictable

By default, provisioning creates a personal workspace and Owner membership. tenantless creates an identity without a workspace. It does not itself prevent self-service workspace creation, so disable that separately if the rollout should be centrally managed.[14][12]

DISABLE_REGISTRATION=true disables password signup, including invitation-based password signup under invite_only. It does not stop first-login OIDC account creation. Use IdP application access controls to determine who may create an SSO identity.[15][14][12]

Recommended pilot flow:

  1. Bootstrap the deployment administrator and create General. Configure providers, storage and a small approved KB set as administrators.
  2. Pre-create employee identities and add them to General as Viewer, or use a workspace invite link for the initial SSO join. Match identity emails carefully.
  3. Give users one company launch link, one clear login button and a named default assistant. They should arrive with membership already assigned; test active-workspace restoration for returning users.
  4. Use explicit KB selection in the assistant. Check answers and citations with real representative documents before widening access.
  5. Once the pilot works, automate provisioning if manual onboarding is too costly. Treat directory-to-membership synchronization as a custom integration with an auditable policy.

Direct email invitations require an existing local account. Shared invite links can enroll new identities, and the frontend preserves a pending link token across OIDC login. They are multi-use bearer links until expiry/revocation, so distribute them narrowly and revoke them after a cohort joins. No native SCIM or OIDC group mapper was found in the inspected implementation.[16][17][18][12]

6. Security and offboarding checks

  • Keep RBAC enforced. Disabling it makes human role guards log and pass; do not rely on role labels alone.[22]
  • Account matching is by email, not a persisted issuer/subject identity. The inspected claims mapping does not enforce email_verified or Google hd. Review identity trust and email reassignment with security before a broad rollout.[14][2]
  • State is signed and browser-cookie-bound. Local login credentials return to the frontend in a base64url URL fragment, so this is not an HttpOnly-cookie-only session architecture.[13]
  • Disabling the IdP application alone does not immediately revoke existing local sessions. Local refresh uses WeKnora's token records without contacting the IdP.[14]
  • Disable the WeKnora account and revoke local sessions during offboarding. The repository implementation performs account status change and session revocation transactionally; access validation checks account activity and token revocation.[19][14]
  • Also remove unwanted workspace memberships, retire invite links and review machine API keys. Revoking a link does not undo memberships already accepted.[9][17]
  • Viewer means readable, not copy-proof. Preview returns original file bytes; hiding an explicit download action does not provide data-loss prevention.[11]

Backend retrieval checks the original caller against each loaded KB before embedding/store resolution. That is useful logical isolation, but it is still application enforcement on shared infrastructure. The review did not exercise those checks against a running server.[21]

7. Pilot acceptance checklist

Run these against the exact deployment image, with separate test accounts and non-sensitive fixtures. A source review is not a substitute for the results.

  • An allowed employee completes Google/JumpCloud login; an unassigned outsider cannot.
  • A new employee lands in General as Viewer without an accidental personal Owner workspace.
  • A Viewer can ask and read citations but cannot upload, edit, invite or create a key.
  • A Contributor can maintain their content but cannot change another creator's content.
  • An Admin cannot mutate membership; an Owner can.
  • A creator demoted to Viewer loses mutation access, including old resources. Pay special attention to v0.8.3's post-release fix.
  • A General-only user cannot list, search, preview or fetch a restricted People KB by guessed IDs.
  • A viewer share remains read-only, and no other organization path broadens it unexpectedly.
  • A shared assistant exposes only approved KBs, including after a new restricted KB is created.
  • Local account disable blocks an already-open browser and refresh; removing IdP access alone is tested separately.
  • Mobile/desktop login, citations, supported language, backups and restore meet the actual employee workflow.
