1. Executive Summary

Amp is a frontier autonomous coding agent built by Sourcegraph. It represents a paradigm shift from AI code assistants to genuinely autonomous agents that plan, execute, and iterate on multi-step development tasks across entire codebases. As of early 2026, over 40,000 development teams have adopted Amp as their primary agentic coding workflow.

Bottom line: Amp is not an autocomplete tool or IDE plugin — it's a semi-autonomous developer that reasons about your codebase, spawns parallel subagents, runs tests, interprets output, and iterates until the job is done.

2. Design Philosophy

2.1 Core Principles

Amp's design philosophy rests on six foundational beliefs:

  1. Code First, Chat Second. Amp reverses the typical AI priority. Chat interfaces are for brainstorming; Amp is for when you need to refactor authentication across 87 microservices. The agent is designed to write, execute, and iterate on code autonomously, with conversation as a supporting mechanism rather than the primary interface.
  2. Human Intelligence Guides AI Capability, Doesn't Gate It. Amp is built on the premise that humans should steer strategy while the agent handles execution. Rather than requiring human approval at every step, Amp operates with explicit permissions and only pauses when it genuinely needs direction. Every tool call outside of Amp requires your approval.
  3. Speed and Iteration Over Traditional Stability. The core Amp team (approximately 8 people) adopted a "push to main, ship 15 times a day" mentality. No formal code reviews, no extensive planning cycles. In an environment where new models and techniques emerge weekly, the ability to iterate quickly is more valuable than the ability to scale reliably.
  4. Opinionated About Model Use and Workflow Shape. Amp abstracts model selection — it picks the right model for each task rather than making the user manage providers. Their philosophy: "We tune the prompts and the tools to get the best performance for each model." If the team doesn't use and love a feature, they kill it.
  5. On the Frontier, Always. Amp goes where the models take it. No backcompat, no legacy features. This means they can incorporate new model capabilities within hours of release rather than months later.
  6. Threads as Version Control for Thought. Every interaction is a persistent, shareable thread. "You wouldn't code without version control — would you?" Amp applies the same philosophy to AI reasoning.
"A product that ships 15 times a day can incorporate new model capabilities within hours of their release. A product that follows traditional release cycles will be months behind."

2.2 Why Sourcegraph Started Fresh (Not Cody 2.0)

Sourcegraph made the bold decision to launch Amp as a completely new product rather than incrementally improving Cody. The reasoning reveals a crucial insight about AI-era product development:

  • A chat-based assistant like Cody operates on fundamentally different computational economics than a tool-calling agent. You cannot make a $20 subscription model work for autonomous agents that reason, execute tools, and iterate autonomously.
  • Tight integration with the Sourcegraph platform meant Cody was bound by platform release cycles. Amp needed to ship 15 times a day, not follow enterprise release schedules.
  • By creating a separate brand, Sourcegraph could reset customer expectations: "This is not Cody 2.0. This is a completely different thing."

3. Technical Architecture

3.1 Multi-Model Routing Layer

Amp's most distinctive technical feature is its multi-model orchestration. The routing engine determines which model handles each part of a task automatically:

ModelPrimary RoleStrengths
Claude Opus 4.5UI, frontend, polished outputInstruction following, clean code, documentation
Gemini 3Core code generationSpeed, large-scale generation, throughput
GPT-5 / o3 (Oracle)Deep reasoning, architecture, reviewComplex analysis, debugging, architectural decisions

For a request like "refactor the authentication module and update the API documentation," the routing engine may simultaneously run the refactor through Gemini 3 while channeling the documentation rewrite through Claude Opus 4.5. This architecture is a direct response to the reality that no single model dominates every dimension of software development.

Amp operates with a 200K token context window across all three model backends, meaning it can hold an entire service's worth of code in working memory simultaneously. Context coherence is preserved even as different models handle different slices of the work.

4. Built-in Agents & Specialized Tools

4.1 🧠 Oracle — The Reasoning Powerhouse

What it is: A read-only subagent powered by OpenAI's o3 — one of the most capable reasoning models available. It's available as a tool that the main agent can consult for complex reasoning tasks.

Design decision: The Amp team deliberately did not push the Oracle too hard in the system prompt, to avoid unnecessarily increasing costs. Instead, developers explicitly instruct the agent to "use the oracle" when needed. This is a conscious cost-conscious design choice.

When to use the Oracle:

  • Reviewing commits for subtle logic changes
  • Analyzing complex function relationships and suggesting refactors
  • Debugging hard-to-find bugs with deep reasoning
  • Architectural analysis and design review
  • Code review at the architectural level

Example prompts from the Amp team:

  • "Use the oracle to review the last commit's changes. I want to make sure the actual logic for when an idle or requires-user-input notification sound plays has not changed."
  • "Analyze how the functions foobar and barfoo are used. Then I want you to work a lot with the oracle to figure out how we can refactor the duplication between them while keeping changes backwards compatible."
  • "I have a bug in these files. Help me fix this bug. Use the oracle as much as possible, since it's smart."

Oracle Mode vs Amp Tab: Together they cover both the micro (cursor-level completions) and macro (architectural reasoning) of software development in a single tool — a pairing more notable than either feature in isolation.

4.2 📚 Librarian — The Code Searcher

What it is: A specialized subagent built for searching remote codebases — all public GitHub code plus your private repositories.

Purpose: The Librarian aggressively searches through repositories and documentation sites to gather context. It primes the main agent with the information it needs before coding begins — especially valuable for newer libraries or private codebases where context isn't in training data.

When to use the Librarian:

  • Reading framework/library source code to understand implementation details
  • Finding examples of patterns in open-source code
  • Connecting the dots between your code and its dependencies
  • Searching documentation across multiple repositories

Example prompts:

  • "Use the Librarian to lookup how React's useEffect cleanup function is implemented."
  • "Explain how new versions of our documentation are deployed when we release. Search our docs and infra repositories."
  • "Ask the Librarian to explain why we're getting this error from Zod and show me the validation logic causing it."

Requires a GitHub connection configured in Amp settings.

4.3 🔀 Parallel Subagents — The Execution Engine

What it is: Amp can spawn multiple independent subagents, each with its own isolated context window, shell access, and file editing tools. The orchestration layer handles dependency resolution and scheduling.

Real-world benchmark: In a refactor of a 180,000-line Go codebase, Amp spawned 7 parallel subagents that simultaneously updated interface definitions, adjusted call sites, rewrote unit tests, and regenerated mocks — completing in 11 minutes what a single-threaded agent would have needed over an hour to process sequentially.

Dependency tracking: If subagent 3 needs the output of subagent 1 before it can proceed, the scheduler waits for the prerequisite before dispatching the dependent task. Best results come when tasks are genuinely independent.

This is the feature that most convincingly separates Amp from tools that describe themselves as "agentic" without running genuinely concurrent work.

4.4 ⌨️ Amp Tab — Free Autocomplete Engine

A free, compiler-error-aware autocomplete that reads the compiler/linter's current error state, factors in imports and surrounding type context, and generates completions that are already syntactically and semantically valid. In 2026 benchmarks, it ranked as the most accurate compiler-error-aware autocomplete engine among free-tier offerings, beating GitHub Copilot Free and Cody Lite.

4.5 🧰 Toolboxes — Simple Extensibility

Like Claude Code skills but with less abstraction. Write simple executables in any language that describe themselves and handle inputs. When Amp starts, it runs each executable with TOOLBOX_ACTION=describe and the tool writes its description to stdout. When the agent decides to use the tool, it runs it again with TOOLBOX_ACTION=execute. No complex SDKs required.

5. Distinctive Features

5.1 Persistent Threads & Thread Sharing

All interactions are stored as persistent threads on Amp's servers. Threads have visibility levels (public, unlisted, workspace-shared, private) and can be shared with teammates. This enables:

  • Resuming work across devices (laptop → server → phone)
  • Reading teammates' threads to understand their approaches
  • Referencing past threads with @-mentions or URLs
  • Code review with full reasoning traces (not just diffs)
  • Search across threads by keyword, file path, repository, author, or date

5.2 Handoff — Smart Context Transitions

A superior alternative to Claude Code's /compact. Handoff generates a new thread prompt with summarized context that you can edit before starting fresh. This strikes a balance between automation and control — you guide the transition rather than letting the agent guess what matters.

5.3 Message Queueing

Send messages that queue for execution after the agent finishes its current turn — without interrupting ongoing work. Use Cmd-Shift-Enter (macOS) or Ctrl-Shift-Enter (Windows/Linux).

5.4 Scoped Instructions (Glob-based Guidance)

Create instruction files with YAML front matter that only apply to specific file patterns. For example, TypeScript conventions only apply when working with .ts/.tsx files, frontend guidance only in src/components/, backend only in server/ and api/. This enables subagent specialization — different guidance automatically applies based on the files being worked on.

5.5 Editing, Reverting & Forking Messages

Press up arrow in the CLI to edit prior messages, delete and restore (reverts changes), or fork (creates a new thread from that point).

5.6 AGENTS.md Compatibility

Amp falls back to CLAUDE.md when no AGENTS.md exists, enabling the same rules files across both Amp and Claude Code. Also supports Cursor's .cursorrules via symbolic links. Pragmatic interoperability with the ecosystem.

5.7 Orbs — Remote Execution

Remote machines that run Amp threads so your laptop can be freed up. Think of them as dedicated compute for your agent workflows.

8. Limitations & Considerations

  • Cost can accumulate: Pay-per-token with premium models means complex multi-step tasks can be expensive. Not cheap compared to fixed-price subscriptions.
  • CLI performance: Lag occurs with long threads or large repos.
  • Resource usage: CPU and RAM spikes during multi-agent workflows.
  • Free mode constraints: Limited context; best for small projects or experimentation.
  • No BYOK: No support for bring-your-own-key with enterprise-hosted models.
  • Subagent dependency tracking: Solid but not infallible — review execution plans on tightly coupled codebases.
  • Young product: Rapid iteration means features change quickly and documentation may lag.

9. Key Takeaways

What Makes Amp Great

  1. Parallel subagent execution — The single feature that most convincingly separates it from "agentic" tools. 7 subagents doing in 11 minutes what takes 1+ hour sequentially.
  2. Multi-model routing — No single model is best at everything. Amp picks the right model per subtask automatically.
  3. Unconstrained tokens — No artificial limits. The agent uses what it needs for quality results.
  4. Persistent thread memory — Threads as version control for AI reasoning. Resumable, shareable, searchable.
  5. Oracle + Librarian — Specialized built-in agents for deep reasoning and codebase search that the main agent can delegate to.
  6. Team-first design — Thread sharing, leaderboards, AGENTS.md, and workspace features built for engineering organizations.
  7. Frontier speed — Small team (~8 people), 15 ships/day, no legacy drag. Incorporates new model capabilities within hours.
  8. CLAUDE.md compatibility — Pragmatic interoperability with the second-most-popular agent. Same rules files work across both.
Amp's Design Philosophy in One Sentence:
"Build for the frontier, not for stability. Ship fast, iterate constantly, let the models lead, and give developers the tools to orchestrate autonomous work rather than manually supervise every step."
