Goal & Loop Engineering

The model is no longer the whole product. The emerging engineering problem is to define a verifiable finish line, repeatedly place an agent in a useful state, measure what happened, and decide whether to continue, escalate, or stop.

The short version

“Loop engineering” is real. “Goal engineering” is mostly a component, not yet a field.

My definition: Loop engineering is the design of triggers, state, context, actions, verification, budgets, recovery, and stop conditions that let one or more agents make bounded, measurable progress over repeated turns.

What changed

Prompt engineering optimizes one model invocation. Context engineering controls what enters its attention. Harness engineering builds the runtime around an agent. Loop engineering coordinates repeated agent runs over time and closes the feedback path from output back to the next input.

What did not change

A loop does not rescue a vague objective, weak tools, missing permissions, or an unverifiable task. It amplifies the quality of its goal and verifier—including their mistakes.

Why “goal engineering” matters

Anthropic's /goal primitive makes the distinction concrete: the agent keeps working across turns while a separate evaluator checks a completion condition. The hard engineering is writing a condition that is observable, sufficiently complete, hard to game, and safe to pursue.

The real bottleneck

Not generating more attempts. It is building trusted evidence that an attempt is good. In mature systems the verifier, telemetry, and escalation policy matter more than clever prompt prose.

Terminology warning: The behavior is older than the label. ReAct, evaluator–optimizer workflows, test-driven repair, control theory, MAPE-K autonomic loops, and reinforcement-learning feedback all predate the June 2026 “loop engineering” wave. The new part is productized agent primitives and a shared practitioner vocabulary—not the invention of iteration.
Historical lineage

The label is new. The engineering problem is not.

Exact-phrase research found almost no authoritative use of goal engineering as a settled discipline. It is better treated as an umbrella over requirements, objective design, alignment, constraints, evaluation, and monitoring. Likewise, loop engineering coalesced as practitioner language in June 2026, but its mechanics descend from older work.

1975–1976 · Proxy failure

Goodhart and Campbell explain why measurements become corrupted when optimized as targets. This is the root warning behind benchmark gaming and grader exploitation.

2016–2020 · Objective failure

Concrete Problems in AI Safety, OpenAI's CoastRunners example, AI Safety Gridworlds, and DeepMind's specification-gaming catalog made proxy exploitation operational.

2021–2022 · Learned goals

Goal misgeneralization showed that even correct training rewards do not guarantee the learned policy pursues the intended goal out of distribution.

2022–2024 · Agent loops

ReAct formalized thought–action–observation; Reflexion and Self-Refine added feedback and revision; SWE-agent showed that the agent–computer interface materially affects behavior.

2024–2026 · Harness + evals

Anthropic, OpenAI, Fowler/Thoughtworks, Hamel Husain, and production builders shifted focus toward tools, tests, traces, permissions, durable state, and eval-driven improvement.

June 2026 · “Loop engineering”

Peter Steinberger's viral formulation, Addy Osmani's synthesis, Boris Cherny's talks, and product primitives such as /goal and /loop gave the existing system pattern a shared name.

Important distinction: Specification gaming means satisfying a flawed literal specification without the intended outcome. Goal misgeneralization means pursuing the wrong learned goal out of distribution even when the training reward was correct. Better prompting alone does not solve either problem.

The minimum viable loop

Think in nested loops, not one magic loop

6 · External feedback loop — days to weeks
Real users, production telemetry, A/B tests, incidents, market response reshape product vision.
5 · Developer / product loop — hours to days
A human contributes context, taste, priorities, and risk judgment the agent does not possess.
4 · Improvement loop — runs to weeks
Traces and failures become datasets and evals; prompts, tools, memory, or harnesses are changed and re-evaluated.
3 · Goal loop — minutes to hours
The agent works across turns until a separate completion condition is satisfied or a guardrail ends the run.
2 · Evaluator–optimizer loop — seconds to minutes
Generate, evaluate against criteria, feed back, revise. Useful only when evaluation is meaningful.
1 · Tool-use agent loop — seconds
Model reads context, calls a tool, observes the result, and chooses the next action until it returns control.
Andrew Ng's useful contribution: separate the fast agentic coding loop, the slower developer-feedback loop, and the slow external-feedback loop. Faster code generation does not eliminate product judgment; it moves the human to the loops where their context advantage matters most.

Patterns that actually earn the loop

Test–repair

Implement → run tests → diagnose → patch → rerun. Best when tests approximate the true specification.

Evaluator–optimizer

Draft → score against rubric → critique → revise. Best when criteria are explicit and iteration improves measurable quality.

Monitor–respond

Poll or receive event → inspect state → act if needed → checkpoint. Best for queues, CI, alerts, feedback, or issue triage.

Research fan-out

Plan → delegate independent searches → synthesize → identify gaps → targeted follow-up. Needs source provenance and stopping thresholds.

Long-horizon shifts

Initializer creates plan/state → each fresh context makes one increment → leaves artifacts for the next. Anthropic's long-running harness pattern.

Improvement flywheel

Collect traces → label failures → formalize evals → propose harness change → test against held-out cases → deploy cautiously.

When not to loop

Use a deterministic workflow or a single call when the path is known, the task is cheap and one-shot, the verifier is weaker than the generator, actions are irreversible, or a human decision is the actual bottleneck. Autonomy is not automatically leverage.

A practical design recipe

  1. Write the goal contract. Outcome, scope, non-goals, constraints, acceptance evidence, and who may waive a condition.
  2. Choose the slowest loop first. Define the real user/product feedback path before optimizing fast agent motion.
  3. Build the verifier before autonomy. Prefer executable checks: tests, schemas, policy checks, simulations, reconciliations, browser inspection.
  4. Make state explicit. Separate immutable intent, current plan, observed facts, artifacts, and attempt history.
  5. Bound the action space. Least privilege, sandboxing, scoped credentials, worktrees, reversible operations, approval for consequence.
  6. Add one loop. Trigger → one bounded unit of work → verify → checkpoint → decision. Do not start with a swarm.
  7. Instrument traces. Goal version, context sources, tool calls, state diffs, verifier output, latency, spend, retries, termination reason.
  8. Test adversarially. Ambiguous goals, flaky tools, stale state, verifier exploits, duplicate events, partial writes, timeouts.
  9. Add recovery and escalation. Retry only transient failures; require a different strategy after semantic failure; escalate uncertainty.
  10. Improve from evidence. Turn real failures into regression evals before changing prompts or adding more agents.

Goal contract template

OUTCOME: What must be true in the world? SCOPE: What may change? What must not? EVIDENCE: Which checks prove completion? CONSTRAINTS: Safety, cost, time, quality, policy. PRIORITY: What trades off against what? ESCALATE WHEN: Which uncertainty needs a human? STOP WHEN: Success OR budget OR timeout OR no progress.

Control-loop pseudocode

while budget.remaining() and not deadline.expired(): state = load_validated_state() work = select_next_bounded_action(goal, state) result = agent.run(context_for(work, state)) evidence = independent_verify(result, goal) checkpoint(result, evidence) if evidence.satisfies(goal): return SUCCESS if unsafe(evidence): return ESCALATE if no_progress(history): return ESCALATE return BUDGET_STOP
Production rule: Never let an LLM's declaration of completion be the only stop signal for consequential work. “Done” is a claim. The loop needs evidence.
Practical field guide

How to use goals and loops with coding agents

The rule: use a goal when you can describe the finish line better than the path. Use a loop when useful new evidence appears after each attempt. If neither is true, use one normal agent turn.

Decision matrix

SituationUseWhyExample
Small, obvious editNormal promptA loop adds cost without reducing uncertainty.Rename a function and update three references.
Path unclear, finish line objectiveGoalAgent can choose steps while tests define done.Make all contract tests pass without changing the public API.
New evidence arrives repeatedlyLoopEach check changes the next useful action.Poll CI, diagnose failure, patch, push, re-check.
Broad migration with many independent unitsGoal + worktree + checkpointsPersistent objective; bounded progress and rollback.Migrate 80 endpoints to a new auth middleware.
Visual/product taste is the verifierHuman-guided iterationsThe agent cannot infer your taste from a binary check.“Make the dashboard feel premium.”
Irreversible or high-impact actionNo autonomous loopHuman approval is part of correctness.Production schema deletion, payments, mass messaging.
Flaky or gameable validationFix verifier firstThe loop will optimize noise or exploit the check.“Stop when the LLM judge says it looks good.”

Four hands-on examples

1 · Bug repair

Weak: “Fix the checkout bug.”

GOAL: Reproduce and fix checkout issue #418. DONE WHEN: - A regression test fails before the fix and passes after it. - Existing checkout tests pass. - No public API or database schema changes. - Final response includes root cause, changed files, and test output. STOP/ASK: if reproduction needs production data or payment credentials.

Why the loop helps: reproduce → inspect evidence → patch → test → diagnose. Every iteration produces objective information.

2 · Mechanical migration

Best shape: plan once, then process one bounded batch per turn.

GOAL: Migrate all Express handlers under src/api/ to typed errors. INVARIANTS: response status/body remain backward compatible. BATCH: at most 5 handlers per iteration; commit after each green batch. VERIFY: npm test -- api && npm run typecheck && npm run lint. DONE: search finds no legacy throwError() calls and all checks pass. ESCALATE: ambiguous response behavior or test fixture disagreement.

Use a worktree. The checkpoint is the unit of recovery—not one giant final diff.

3 · Browser/UI loop

GOAL: Implement the supplied settings-page design at desktop and mobile. EVIDENCE EACH TURN: 1. start app; 2. capture 1440×900 and 390×844 screenshots; 3. compare layout, overflow, focus order, and console errors; 4. fix the largest objective mismatch. DONE: visual checks pass, zero console errors, keyboard flow works, and Playwright tests pass. ASK: for subjective color/type choices not specified in the design.

Browser screenshots are sensors. “Looks good to me” is not.

4 · CI babysitting

Every 10 minutes: - inspect the latest run for this branch; - if running, wait; - if failed, read only failing logs, classify transient vs code failure; - retry transient failure once; patch code failures and run the focused test; - stop when CI is green or after 3 materially different failed strategies; - never merge or deploy; ask before changing workflow permissions.

This is a real scheduled loop because external state changes over time. A goal alone is not enough.

Design your loop in seven fields

1. OBJECTIVE — observable state in the codebase or environment 2. INVARIANTS — behavior that must not regress 3. SENSOR — tests, compiler, browser, CI, logs, benchmark 4. ACTION SPACE — files/tools/commands the agent may use 5. MEMORY — plan, progress file, commits, evidence log 6. CONTROL — retry, replan, rollback, escalate 7. TERMINATION — success, blocked, needs-user, budget, no-progress
Prompt pattern: give the agent the objective and constraints, not a brittle 30-step recipe. Give the controller the mechanical loop: what evidence to collect, how to react, and when to stop.

Claude Code

Claude Code v2.1.139+ has native /goal. A small evaluator checks the condition after each turn. Use /loop for interval-based repetition, not goal completion.

Interactive

/plan Investigate the failing checkout flow and propose the smallest fix. /goal Fix checkout issue #418. Done when a regression test proves the bug, the fix passes focused and existing checkout tests, and no public API changes. Ask before using production data or credentials.

Check status with /goal; clear with /goal clear. Use /loop 10m check CI... when time or external events drive repetition.

Automation-safe print mode

claude -p 'Fix issue #418 under the goal contract in GOAL.md. Run focused tests, record evidence, and stop if production access is required.' \ --allowedTools 'Read,Edit,Write,Bash(npm test *),Bash(git diff *)' \ --max-turns 10 --max-budget-usd 5 --output-format json

Use a worktree for broad edits. Never pair an open-ended goal with --dangerously-skip-permissions.

OpenAI Codex

Codex supports /goal <objective> in its app, IDE, and CLI. OpenAI recommends it for durable work with a clear validation loop; use /plan first when the approach needs investigation.

Interactive goal

/plan Map the legacy auth middleware, consumers, tests, and compatibility risks. /goal Migrate all endpoints to AuthContext. Preserve response behavior, process at most five endpoints per checkpoint, and continue until typecheck, auth tests, and the legacy-usage search are clean. Ask on ambiguous behavior.

CLI fallback / custom loop

codex exec --full-auto ' Work on the next incomplete item in GOAL.md. Run the listed verification commands. Update PROGRESS.md with evidence. Stop after one green checkpoint, or report BLOCKED with the exact evidence.' # External controller repeats only while PROGRESS.md reports CONTINUE.

Prefer Codex-managed worktrees or git worktree for scheduled and parallel work. Avoid --yolo; a loop multiplies permissions as well as productivity.

Pi coding agent

Stock Pi is extensible rather than opinionated. Irfan's pi-setup already contains a local goal-loop extension with project-scoped state, evidence, turn budgets, verification commands, and an optional read-only evaluator subagent.

Use the local extension

/goal Migrate the config loader to Zod without changing exported types. /goal verify npm test -- config /goal verify npm run typecheck /goal status /goal pause /goal resume /goal clear

Defaults: 10 continuation turns, 3 failed verification attempts, last 10 evidence entries. It stops on complete, blocked, needs-user, or budget.

Pi-specific safety

  • Keep model-created goals disabled during brainstorming.
  • Keep pi-permission-system enabled; the extension does not bypass permissions.
  • Use the evaluator subagent only for terminal or suspicious states, not every turn.
  • Persist truth in tests, commits, and progress artifacts—not only conversation history.
  • Run /reload after installing or changing the extension.

Tips that matter more than the agent brand

  1. Start with the verifier. If you cannot state how success is observed, you do not have a goal—you have a wish.
  2. Make one loop iteration small. One failing test, one batch, one screenshot comparison, one CI transition.
  3. Keep best-so-far. A later iteration can regress; compare and preserve the strongest checkpoint.
  4. Separate worker and judge. Deterministic checks first; independent model/human evaluation only where needed.
  5. Detect no progress. Hash repeated commands/errors, cap failed strategies, and escalate instead of thrashing.
  6. Fresh context for long work. Reconstruct from GOAL.md, PROGRESS.md, git, and test output instead of dragging an enormous chat forward.
  7. Restrict authority. Narrow tools, sandbox/worktree, no secrets, idempotent side effects, approval before push/merge/deploy.
  8. Turn failures into harness improvements. New regression test, rule, skill, hook, or clearer tool—not another motivational prompt.
Bad goal smell: “Improve quality until it is excellent.” Good goal: “Reduce p95 latency below 250 ms on the fixed benchmark, preserve error rate and API behavior, stop after three strategies fail, and show before/after evidence.”
