Per-user MCP access without exposing the MCP server

A practical design for a custom Slack bot that lets each user connect their own account. It explains which credentials the bot stores, how to protect them, and how the browser-based OAuth flow works over VPN.

Core answer: The token store belongs to your bot backend, not Slack or the MCP server. Keep only the credentials and metadata required to reconnect on behalf of a specific user; store the sensitive fields encrypted and never pass them to the model.

1. System architecture

One bot application handles Slack events, acts as the MCP client, and hosts a small OAuth callback route. Socket Mode is an outbound WebSocket connection to Slack; it does not require a public Slack event webhook. The backend reaches MCP and the authorization server over VPN. A browser must reach the authorization page and the callback URL through that same VPN. [1][2][3]

Bot backend

Bolt listener + MCP client + /oauth/callback. A single deployment is enough to prototype; split services only for a demonstrated scaling or security reason.

MCP & authorization

MCP validates user-bound access tokens and enforces tool permissions. The OAuth authorization server may be the same deployment or a separate service. DCR registers the bot as a client; it does not register every user. [3][5]

Token store

The backend maintains an encrypted per-user grant and a separate per-issuer client-registration record. A bot-wide Slack token is for Slack API access, never a substitute for a user's MCP token.

2. User flows

Flow A · First-time connection

A user messages the custom bot. The bot sees no grant for that Slack identity, creates a short-lived OAuth transaction, and sends a Connect link. The user's browser authorizes through VPN and returns to the bot callback. The backend verifies state and PKCE, exchanges the code, and encrypts the resulting user grant. The redirect is browser → bot, not an inbound push from Slack or the authorization server. [1][3][4]

Flow B · A subsequent tool call

The bot derives the caller from the trusted Slack event, loads only that user's grant, refreshes when needed, and sends Authorization: Bearer on MCP requests. The MCP resource server checks token audience, validity, scope, and underlying user permissions; the bot returns the authorized result. [3][4]

3. What the token store actually needs

Separate durable user grants, client registration, and temporary OAuth transactions. The fields below are a proposed application schema—not fields mandated by the MCP wire protocol. Make each identity key explicit; never infer a user's authorization from a model-supplied user_id.

User grantenterprise_id?, team_id?, slack_user_id, issuer, canonical resource, encrypted access_token, expires_at, optional encrypted refresh_token, granted_scopes, status, key_version, updated_at.Fetch exactly one user's MCP credential. Store a refresh token only if one was issued. Include the Enterprise/workspace context so IDs cannot silently collide.

Do not store: user passwords, raw OAuth authorization codes after exchange, access tokens in Slack messages or URLs, unnecessary profile/email copies, or full token values in application logs and audit events. The LLM receives tool descriptions and sanitized tool results—not bearer tokens.

Illustrative data shape (no real credentials)

grant_key = (enterprise_id?, team_id?, slack_user_id, issuer, resource)
user_grant = {
  grant_key, encrypted_access_token, access_expires_at,
  encrypted_refresh_token?, granted_scopes, status, key_version
}
client_registration = { issuer, client_id, redirect_uri, encrypted_client_secret? }
auth_transaction = { state_hash, encrypted_pkce_verifier, expected_issuer,
                     grant_key, expires_at, consumed_at? }

Storage choice: for a one-instance prototype, a persistent database such as SQLite with application-level authenticated encryption is enough. For concurrent replicas, use a transactional shared database (for example PostgreSQL) and an external key-management service. A plain JSON file with raw tokens is a teaching shortcut, not the target design. The reference sample itself labels its SQLite/JSON approaches as educational. [1][6]

4. How to store and use tokens safely

  1. Encrypt sensitive columns before database write. Use a vetted authenticated-encryption library (for example AES-256-GCM or XChaCha20-Poly1305), a fresh nonce per encryption, and authenticated context tying ciphertext to the grant key. Keep the master key outside the database and backups, ideally in a KMS or secret manager. Store a key version to allow rotation. Disk encryption alone does not protect against a leaked DB dump.
  2. Restrict access. Only the bot's service identity may decrypt grants. Limit DB permissions, use encrypted backups with a separately protected key, and never expose raw token fields to admin pages, logs, traces, analytics, or model/tool output. Least-privilege secret access and rotation matter. [4][6]
  3. Bind the correct user. Build the grant key from the Slack event identity supplied to your authenticated Socket Mode connection, not from user-controlled message text. On callback, resolve the user exclusively through a one-use server-side state record. Never let a callback query parameter choose another user's grant.
  4. Honor OAuth protections. Enforce HTTPS for authorization endpoints and callback (except loopback development), exact redirect URIs, PKCE S256, expected issuer validation, and the MCP resource parameter. The MCP server must reject a token with the wrong audience. [3][4]
  5. Refresh atomically. If a refresh token is issued, refresh shortly before expiry under a per-grant lock or compare-and-swap transaction; when a provider rotates the refresh token, persist the replacement in the same transaction before concurrent calls reuse the old one. If refresh fails or access is revoked, mark the grant disconnected and ask the user to reconnect. Do not retry indefinitely.
  6. Make disconnect real. Delete the stored user grant, clear pending OAuth transactions, and request provider revocation where supported; otherwise deletion prevents future bot use but does not itself revoke an already issued token. Audit connection/disconnection and errors without token values.

5. VPN boundary and the callback

No public MCP endpoint

Only the bot backend needs private network access to MCP. The browser does not call the MCP endpoint during normal bot use.

Browser-reachable callback

The callback can be served by the same bot process through a VPN-only HTTPS reverse proxy. Every user browser must resolve its private DNS name and trust its TLS certificate. A backend-only localhost URL will not work for remote users. [4]

Outbound Slack connection

Socket Mode carries events over a connection initiated by the bot; it removes the public Slack webhook requirement, not the separate browser callback requirement. Socket Mode apps are not currently eligible for the public Slack Marketplace. [2]

VPN prerequisite: if a user clicks Connect from a device outside VPN, Slack chat can still work while OAuth login or the callback fails. Fail clearly and tell them to reconnect to VPN—do not silently open the entire MCP server to the internet.

6. Minimum verification before rollout

  • Alice connects; her MCP request uses Alice's token. Bob is initially unconnected; Bob receives no Alice data or token.
  • Bob connects; swapping Slack message text or tool arguments cannot switch the selected grant.
  • Wrong state, expired state, replayed callback, wrong issuer, invalid PKCE, and wrong redirect URI all fail closed.
  • Wrong token audience, insufficient scope, revoked token, expired token, and no refresh token return an explicit reconnect/permission outcome.
  • Two concurrent refreshes of the same grant cannot overwrite a rotated refresh token.
  • A process restart preserves client registration and encrypted grants; a database backup without the separate key does not reveal tokens.
  • Disconnect removes the correct user's grant without affecting another user. Logs, traces, tool results, and error pages contain no bearer tokens.
  • From a real user device on VPN, open the Connect link and complete HTTPS callback. Repeat outside VPN to confirm a clear failure message.

Scope note: these are design and acceptance criteria, not claims that a bot has been implemented or that the private endpoint was tested.
