WeKnora least-privilege issue map for a single workspace

Every issue in the Tencent/WeKnora repository that matters if we want least privilege inside a single workspace: what others already reported, where each one stands, and what has no issue at all yet.

Bahasa Indonesia·English

Summary

The core problem is one thing: WeKnora has no per-resource ACL inside a single workspace. What exists is a workspace-level role and a cross-workspace share mechanism. Every issue below is a fragment of that problem, spread across 42 items: 27 still open, 10 closed, 5 resolved through a PR.

Read the map layer by layer, because each layer owns a different slice of the problem. Layers 0 and 1 get most of the discussion, but the most concrete hole today sits in #5284: anyone holding a shared team MCP token can write to knowledge bases beyond their role, and the audit trail cannot be traced back to a person.

We opened #5618 ourselves, about platform-level default MCP services for all workspaces. It exists precisely because there is no ACL inside one workspace, which pushed the design toward multi-workspace.

How this research was done

The sweep ran against the GitHub API on 17 November 2026: 34 keyword queries (English and Chinese) over issue titles and bodies in Tencent/WeKnora, 412 unique issues caught, about 30 read in full.

Layer map

Layer 0 · Identity & membership

  • #674 Open Separation of duties (system admin / auditor / operator), registration control, LDAP / AD / SSO integration.
    Opened Feb 2026, no maintainer response yet.
  • #1037 Open Admin user panel: list all users, assign roles, disable/delete accounts.
    No maintainer response. Today it needs raw SQL.
  • #4873 Open Organization member management: batch add, name-based search, SystemAdmin override.
    Labeled needs-triage. A contributor offered a PR for the name-search part.
  • #5092 Open Provisioning without SMTP: admin-created accounts, one-time login links, hard delete.
    Aimed at on-prem deployments with no mail server.
  • #5001 Open Promote the first system admin at sign-up instead of the next app restart.
    Small, but a fresh deployment can't be administered without a restart.
  • #4200 Open Exempt system admins from the self-service creation limit, plus a config entry for can_access_all_tenants.
    Bug: the code only reads can_access_all_tenants, never is_system_admin.
  • #1303 Closed Multi-tenancy with RBAC: per-user roles inside one tenant.
    Closed without implementation. #5295 is the follow-up, narrowed to per-KB ACL.
  • #2033 Merged PR Ordinary users don't get their own workspace automatically, only via invite.
    Shipped in PR #2037: WEKNORA_AUTH_DEFAULT_TENANT_MODE=tenantless plus the self-service flag.
  • #2386 Closed Suggestions to consolidate the permission system and restrict registration.
    Maintainer: registration modes, system admin, and OIDC SSO already exist.
  • #4201 Merged PR Owner can't demote themselves on the members page (ownership transfer).
    Fixed in PR #4213.

Layer 1 · Knowledge-base level ACL

  • #5295 Open Per-KB access control inside a single workspace: workspace / restricted / private visibility, per-user/role grant table, filtered listing, 404 instead of 403.
    No maintainer response yet. Design-wise this is the most complete one, and the closest to what we need.
  • #4216 Open Custom roles plus knowledge-base-granular authorization inside the workspace.
    Labeled needs-triage. Notes that roles are 4 hardcoded values, a viewer reads every KB, and tags are not an authorization boundary.
  • #3626 Open Proposes “Section”: inside one shared space, a KB can be limited to a chosen set of members.
    Labeled needs-triage. Another user backed it and asked for user-level sections (not just space-level) plus a hierarchy.
  • #4878 Open KB sharing: batch, delegated share permission, and space-side management.
    Labeled needs-triage. Today sharing only works from the owning workspace with a full-access key, so platform admins can't manage it.
  • #4338 Open A workspace editor can't edit KBs created by others, while the same role can via a shared space.
    Labeled needs-triage. Pinged the maintainer, no answer yet.
  • #4511 Closed Inconsistent scope semantics: one key can search a shared KB (200) but not list it (403).
    Closed. Still relevant if we use scoped keys.
  • #2709 Closed A user granted admin through an organization share gets no Settings button in the UI.
    Frontend only. Per the thread, the fix never landed upstream.

Layer 2 · Document & chunk

  • #2024 Open Document-level ACL plus retrieval filtering (enforced at chunk retrieval, not hidden in the UI).
    Maintainer folded #2809 into this one. Latest comment (9 Nov) argues the visible set must be pushed into the query before top-k.
  • #2090 Open KB/file metadata, a metadata_filter parameter on knowledge_search / grep_chunks, plus file-level search.
    The foundation for the ACL filtering in #2024. Also what makes the “invisible KB, still the grounding source” case expressible.
  • #2809 Closed Per-document permissions: who may edit, delete, and who may RAG that document.
    Closed as duplicate, pointed at #2024.
  • #2266 Merged PR Guests / read-only members had no restriction on document operations (download, delete, rebuild).
    Partly shipped: download needs Editor+, other operations are hidden in the UI (PR #2250).
  • #4779 Open No retriever backend stores a tenant dimension; isolation lives entirely in the application layer.
    A question, unanswered. Matters if we want fail-closed enforcement.

Layer 3 · Consumption through agents & MCP

  • #5420 Open Usage-level permissions for agents, skills, and MCP inside one tenant, plus who may attach an MCP server to an agent.
    Labeled needs-triage. Without it, a private KB bound to an agent still leaks through answers and citations.
  • #5284 Open Personal MCP endpoints that act as their owner, instead of one static team token.
    The most concrete hole: a Viewer can write to a KB through MCP, the “only the creator or an admin may change documents” rule isn't applied on MCP writes, and audit lands on a synthetic mcp-<endpoint_id> user.
  • #5157 Open Per-IM-session MCP tool whitelist (tool-level, subtractive only).
    Today tool policy is global per (tenant, service, tool), so once a tool is enabled, every entry point can call it.
  • #3598 Open MCP dynamic headers from the current user's context.
    Labeled needs-triage. The counterpart to #2951: per-user identity instead of a shared header.
  • #3479 Open Agent-native integration patterns: read-only access mode for consuming agents, audit trail, stale detection.
    No maintainer response yet.
  • #5079 Open Asks to let IM expose the agent's wiki-update capability, with admin control.
    Labeled needs-triage. It points the other way from least privilege, but it's where the wiki-write path is discussed.
  • #2951 Open An MCP service with static-header auth on a shared agent shouldn't use the sharer's header.
    If the MCP server derives authorization from that header, every user of the shared agent inherits the owner's rights.
  • #5193 Closed Read-only mode: enforcement is correct, the assistant's explanation to the user was wrong.
    Closed. Evidence that read-only enforcement does work for write operations.

Layer 4 · Machine credentials

  • #3276 Open Per-KB API key permissions: retrieve / ingest / manage_kbs, plus a permission field in list responses.
    Proposed to be enforced in RequireKBAccess, so even an Admin of the KB can't bypass the key's limit.
  • #5561 Open A KB-scoped API key gets 403 when selecting explicit documents (knowledge_ids) in agent-chat.
    Labeled needs-triage. The scoping path isn't consistent yet.
  • #3572 Open Move end-user identity config from the workspace level down to each API key.
    Labeled needs-triage. Still a discussion about boundaries.
  • #3351 Merged PR An MCP server with multiple API keys, each scoped to different KBs.
    Resolved by PR #3371: a Go built-in MCP server where each workspace creates endpoints with its own token and allowed-KB list. The Python MCP server is deprecated.
  • #2413 Merged PR Per-request API keys for multi-tenant isolation on the MCP server.
    Same resolution, via PR #3371.
  • #2603 Closed An endpoint to update the KB allow-list of an existing scoped API key.
    Closed (owner-only). We don't need a new key every time a KB is added.
  • #3402 Closed Audit couldn't tell which API key triggered an action.
    Closed.
  • #4228 Closed OAuth MCP can't serve users of an application sitting in front of WeKnora: no browser, no pre-registered clients.
    Closed, PR #4229. Only relevant if we put WeKnora behind another application.

Layer 5 · Cross-cutting

  • #3747 Open Masking at every stage (ingest, retrieval, output), document classification labels, copy/download/export restrictions, audit, lifecycle, and a rule library.
    Labeled needs-triage. Broadest and costliest. Makes sense only after the ACL layer exists.
  • #3317 Open Long-term memory has no operator surface, yet it's built for principals without an account (IM users, embed visitors, API users).
    Phase 1 merged (PR #4954); the follow-up was claimed by a contributor.
  • #4958 Open A pluggable deny-only policy extension point for KB access: it can only veto, never grant.
    Proposed with a ready patch. Doesn't close the ACL gap, but works as a safety net outside it.
  • #3426 Closed Security audit write-up: 76 findings plus 11 functional defects.
    PR #3425 was closed unmerged; the maintainer asked for the remaining findings to be split into separate issues. No evidence of that happening.

Workarounds that work today

While per-resource ACL doesn't exist, what you can use today is moving granularity to the workspace level and leaning on the scopes the platform already provides. Everything below comes from the upstream CHANGELOG and issue text, and hasn't been exercised at runtime in our deployment. Some rows reference items outside the 42 issues above; those are cited as evidence of a capability, not as part of the map.

Separating who can see which knowledge base

What works today: Split KBs across workspaces: a workspace acts like a folder, and a KB living in another workspace never shows up in your list. To grant access without moving people, share the KB into a shared space (organization) with viewer or editor permission, and hand out the Viewer role in the target workspace to those who only need to ask.

What still leaks: Granularity becomes per workspace, not per person per KB. One share covers every member of the space, and anyone who needs access has to switch workspaces. The audit trail splits per workspace too.

Related issues: #5295 #4216 #3626

Consumable through an agent, but not visible

What works today: Share the agent only, and keep the KB in the owning workspace. The recipient can only query through that agent, and the KB never appears in their workspace.

What still leaks: This is an interface boundary, not a security boundary. KB content can still be teased out through answers, citations, and file previews, and nothing yet restricts who may run that agent.

Related issues: #5420 #5284

Machine credentials with the narrowest scope

What works today: Tenant API keys are now capability-scoped and can be restricted to a specific list of KBs, with route-level guards (DenyAPIKeyPrincipal, api_key_gate). Cleaner still: use the built-in per-workspace MCP endpoints, where each endpoint has its own token, its own KB scope, its own rate limit, and write tools off by default. Tokens are rotatable.

What still leaks: Capabilities are still global per key, so “KB A read-only, KB B writable” with one key isn't expressible. On the knowledge_ids path a KB-scoped key is still rejected with 403. And an endpoint token identifies the endpoint, not a person: whoever holds it gets everything the endpoint allows.

Related issues: #3276 #5561 #5284

Limiting what an agent is allowed to write

What works today: Agents have read-only, confirm-before-change, and automatic-write access levels, plus HITL approval, suspended runs, and scoped grants (PR #4250, #4490). On MCP endpoints the write tool group is off by default, and IM already strips write tools.

What still leaks: Those levels belong to a chat session, not to an organization-wide grant, so they can't serve as standing policy. And the wiki-write path through local agent tools still doesn't check who owns the KB.

Related issues: #5420 #5079

Knowing who changed what

What works today: Wiki page revisions and chunk revisions store last_edit_source (pipeline, agent, user, or revert) and last_editor_id. There is a per-KB activity trail, a per-tenant audit log, and a platform audit log.

What still leaks: Actions an agent runs inside one workspace can't be attributed to a specific member. Through an MCP endpoint the audit records a synthetic user, so tracing stops at the endpoint.

Related issues: #5284

Controlled onboarding and registration

What works today: Registration modes are selectable (invite_only, invite_register, DISABLE_REGISTRATION), there is tenantless provisioning with a gated self-service workspace flag, OIDC SSO, admin-created accounts, and password reset with session revocation.

What still leaks: Batch invites and a user-management panel don't exist yet, so bulk provisioning stays manual or scripted against the API. The first system admin still needs an app restart.

Related issues: #1037 #4873 #5001 #5092

Enforcing your own policy (compliance, deny rules)

What works today: There is a deny-only policy extension point with a ready patch that registers into the existing authorization choke points (16 files, +506/−3). A blunter option: run RBAC in audit-only mode with tenant.enable_rbac=false during a migration.

What still leaks: Deny-only: it can veto but never grant, and it isn't upstream, so it has to live in a fork. Audit-only mode is not enforcement.

Related issues: #4958 #4216

One MCP OAuth server shared across workspaces

What works today: Insert one mcp_services row with is_builtin=true directly in the database. It shows up in every workspace, and OAuth tokens are stored per (tenant, principal, service), so every user keeps their own token in their own workspace.

What still leaks: There is no supported way to provision it (config, env, or SystemAdmin API), secret rotation needs raw SQL, the Authorize button never appears for a builtin row, and new agents attach no MCP by default.

Related issues: #5618

The multi-workspace pattern moves granularity from the resource to the workspace: admin cost rises and the audit trail fragments. That's the same objection the author of #5420 raised against splitting workspaces, so treat these workarounds as a stopgap, not a target design.

Gaps with no issue yet

  • The wiki-write path through local agents isn't ownership-checked. The agent's wiki tools don't validate KB ownership before writing. No issue tracks this, and #5079 asks for the opposite direction by opening write access in IM.
  • End-to-end enforcement of “consumable through an agent, not listable” is incomplete. The listing and 404 side exists in the #5295 proposal, but leakage through answers, citations, file previews, and a shared agent's KB scope has no dedicated issue.
  • Audit attribution for actions run by an agent. Per-API-key audit was closed in #3402 and #5284 mentions the synthetic MCP user, but nothing proposes per-member audit for agent runs inside a single workspace.
  • There is no single authorization choke point. #4958 comes closest, but it's a per-deployment veto. Every path (list, IM, MCP, agent, wiki) still decides on its own, so each new feature can open a new leak.

Recommended contribution order

  1. #5295 — the per-KB ACL foundation. The design is the most complete and closest to what we need. If maintainers stay silent, decide whether to send a patch there or maintain a fork, accepting drift risk in access, session, IM, and MCP.
  2. #3276 and #5284 — machine-access holes. Both are small and self-contained. #3276 aligns API-key scope with per-KB permissions, #5284 closes MCP writes and their audit attribution.
  3. #5420, then #2024 + #2090 — usage and document level. Order matters: KB ACL first, then agent/MCP usage permissions, then document-level filtering, which needs metadata.

Limitations

  • Issue states come straight from the GitHub API on 17 November 2026 (WIB), not from memory or a summary.
  • This is a read-only pass over the tracker and the code. Nothing was exercised at runtime, so behavioural claims (for example, that a Viewer can write through MCP) are inferred from code and issue text, not reproduced.
  • The keyword sweep is broad but not guaranteed exhaustive. Issues filed after that date are not included.
  • Effort estimates, where present, are guesses from reading code, not measurements.
  • The workaround section is assembled from the upstream CHANGELOG and issue text. Nothing was run end to end against our own WeKnora deployment, so treat those as direction rather than tested instructions.
