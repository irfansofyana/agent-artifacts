Peta issue least-privilege WeKnora di dalam satu workspace

Semua issue di repo Tencent/WeKnora yang relevan kalau kita mau menerapkan least privilege di dalam satu workspace: apa yang sudah dilaporkan orang lain, statusnya sekarang, dan bagian mana yang belum punya issue sama sekali.

Bahasa Indonesia·English

Ringkasan

Masalah intinya satu: WeKnora belum punya ACL per resource di dalam satu workspace. Yang ada cuma role level workspace dan mekanisme share antar-workspace. Semua issue di bawah ini adalah pecahan dari masalah itu, tersebar di 42 item: 27 masih open, 10 sudah ditutup, 5 selesai lewat PR.

Baca peta ini per layer, karena tiap layer punya pemilik masalahnya sendiri. Layer 0 dan 1 yang paling sering dibahas orang, tapi lubang paling konkret sekarang justru ada di #5284: siapa pun yang memegang token MCP satu tim bisa menulis ke knowledge base di luar role-nya, dan audit-nya tidak bisa dilacak ke orang.

Kita sendiri sudah membuka #5618 tentang MCP default level platform untuk semua workspace. Issue itu lahir justru karena ACL dalam satu workspace belum ada, jadi keputusannya jatuh ke multi-workspace.

Bagaimana riset ini dikerjakan

Sweep dilakukan lewat GitHub API pada 17 November 2026: 34 query kata kunci (Inggris dan Mandarin) ke title dan body issue di Tencent/WeKnora, 412 issue unik terjaring, sekitar 30 dibaca penuh.

Peta per layer

Layer 0 · Identitas & keanggotaan

  • #674 Open Pemisahan tugas (system admin / auditor / operator), kontrol registrasi, integrasi LDAP / AD / SSO.
    Dibuka Feb 2026, belum ada respons maintainer.
  • #1037 Open Panel user admin: daftar semua user, atur role, disable/delete akun.
    Belum ada respons maintainer. Sekarang harus lewat SQL.
  • #4873 Open Manajemen member organization: batch add, pencarian by nama, override SystemAdmin.
    Berlabel needs-triage. Ada kontributor yang nawarin PR untuk bagian pencarian nama.
  • #5092 Open Provisioning tanpa SMTP: akun dibuat admin, one-time login link, hard delete.
    Untuk deployment on-prem tanpa mail server.
  • #5001 Open Promosi system admin pertama saat sign-up, bukan saat app restart berikutnya.
    Kecil, tapi bikin deployment baru gak bisa dikelola tanpa restart.
  • #4200 Open System admin dikecualikan dari batas self-service creation, plus entry config can_access_all_tenants.
    Bug: kode cuma lihat can_access_all_tenants, bukan is_system_admin.
  • #1303 Closed Multi-tenancy dengan RBAC: role per user di dalam satu tenant.
    Ditutup tanpa implementasi. #5295 adalah lanjutannya, dipersempit ke ACL per KB.
  • #2033 Merged PR User biasa gak otomatis punya workspace sendiri, cuma bisa diinvite.
    Sudah jadi lewat PR #2037: WEKNORA_AUTH_DEFAULT_TENANT_MODE=tenantless plus flag self-service.
  • #2386 Closed Saran konsolidasi sistem izin + batasi registrasi.
    Maintainer: sudah ada mode registrasi, system admin, dan OIDC SSO.
  • #4201 Merged PR Owner gak bisa menurunkan dirinya sendiri di halaman member (transfer ownership).
    Sudah diperbaiki di PR #4213.

Layer 1 · ACL level knowledge base

  • #5295 Open ACL per knowledge base di dalam satu workspace: visibility workspace / restricted / private, tabel grant per user/role, list difilter, 404 bukan 403.
    Belum ada respons maintainer. Ini issue paling matang dari sisi desain, dan yang paling dekat sama kebutuhan kita.
  • #4216 Open Role custom + autorisasi per knowledge base di dalam workspace.
    Berlabel needs-triage. Menyebut role masih 4 hardcoded, viewer bisa baca semua KB, dan tag bukan batas autorisasi.
  • #3626 Open Usul “Section”: di dalam satu shared space, KB bisa dibatasi ke sekelompok anggota saja.
    Berlabel needs-triage. Ada user lain yang mendukung, minta section bisa berisi user (bukan cuma space) dan hierarki bertingkat.
  • #4878 Open Share KB: batch, delegated share permission, dan pengelolaan dari sisi space.
    Berlabel needs-triage. Sekarang share cuma bisa dari workspace pemilik dan wajib key full-access, jadi admin platform gak bisa kelola.
  • #4338 Open Editor di dalam workspace gagal ngedit KB yang dibuat orang lain, padahal lewat shared space bisa.
    Berlabel needs-triage. Sudah di-ping ke maintainer, belum dijawab.
  • #4511 Closed Sudut pandang scope gak konsisten: satu key bisa search shared KB (200) tapi gagal list-nya (403).
    Sudah ditutup. Tetap relevan kalau kita pakai key ter-scope.
  • #2709 Closed Penerima grant admin via organization share gak dapat tombol Settings di UI.
    Cuma frontend. Fix-nya tidak pernah di-PR kan ke upstream menurut thread-nya.

Layer 2 · Dokumen & chunk

  • #2024 Open ACL level dokumen plus filter di retrieval (dicek di chunk, bukan disembunyikan di UI).
    Maintainer mengarahkan #2809 ke sini sebagai tempat konvergensi. Komentar terakhir (9 Nov) soal menekan visible set ke query sebelum top-k.
  • #2090 Open Metadata KB/file, parameter metadata_filter di knowledge_search / grep_chunks, plus search level file.
    Fondasi buat filter ACL di #2024. Ini juga yang nutup kasus “KB gak kelihatan tapi tetap jadi sumber”.
  • #2809 Closed Izin per dokumen: siapa yang boleh edit, delete, dan siapa yang boleh nge-RAG dokumen itu.
    Ditutup sebagai duplikat, diarahkan ke #2024.
  • #2266 Merged PR Guest / read-only gak punya batasan operasi dokumen (download, delete, rebuild).
    Sebagian sudah jalan: download butuh Editor+, operasi lain disembunyikan di UI (PR #2250).
  • #4779 Open Semua backend retriever gak menyimpan dimensi tenant; isolasi murni di application layer.
    Pertanyaan, belum dijawab maintainer. Penting kalau mau enforcement fail-closed.

Layer 3 · Konsumsi lewat agent & MCP

  • #5420 Open Izin level pemakaian untuk agent, skill, dan MCP di dalam satu tenant, plus siapa yang boleh memasang MCP ke agent.
    Berlabel needs-triage. Tanpa ini, KB private yang dipasang ke agent tetap bocor lewat jawaban dan citation.
  • #5284 Open MCP endpoint personal yang bertindak sebagai ownernya, bukan token statis milik tim.
    Lubang paling konkret: Viewer bisa nulis KB lewat MCP, aturan “cuma creator/admin yang boleh ubah dokumen” gak berlaku di jalur MCP, audit masuk sebagai user sintetis mcp-<endpoint_id>.
  • #5157 Open Whitelist tool MCP per sesi IM (tool-level, hanya mengurangi).
    Sekarang policy tool diset global per (tenant, service, tool), jadi begitu satu tool diaktifkan, semua entry point bisa memanggilnya.
  • #3598 Open MCP dynamic header dari konteks user yang sedang memakai.
    Berlabel needs-triage. Pasangan dari #2951: identitas per user, bukan header bersama.
  • #3479 Open Pola integrasi agent-native: mode read-only untuk agent pemakai, audit trail, deteksi stale.
    Belum ada respons maintainer.
  • #5079 Open Minta IM boleh membuka kemampuan agent untuk update wiki, dengan kontrol admin.
    Berlabel needs-triage. Arahnya kebalikan dari least privilege, tapi ini issue tempat jalur wiki-write dibahas.
  • #2951 Open MCP dengan static header di shared agent seharusnya gak pakai header si pemilik.
    Kalau server MCP-nya bikin keputusan izin dari header, semua pemakai shared agent jadi punya izin si pemilik.
  • #5193 Closed Mode read-only: enforcement-nya benar, pesan asisten ke user yang salah.
    Sudah ditutup. Bukti bahwa enforcement read-only memang jalan untuk operasi tulis.

Layer 4 · Kredensial mesin

  • #3276 Open API key bisa diatur per KB: retrieve / ingest / manage_kbs, plus field permission di response list.
    Diusulkan ditegakkan di RequireKBAccess, jadi Admin dari KB-nya sendiri pun gak bisa nge-bypass batas key.
  • #5561 Open KB-scoped API key ditolak 403 waktu memilih dokumen eksplisit (knowledge_ids) di agent-chat.
    Berlabel needs-triage. Jalur scope-nya belum konsisten.
  • #3572 Open Identitas end-user dipindah dari level workspace ke level per API key.
    Berlabel needs-triage. Masih tahap diskusi boundary.
  • #3351 Merged PR MCP server dengan banyak API key, masing-masing dengan cakupan KB berbeda.
    Selesai lewat PR #3371: MCP server bawaan backend Go, tiap workspace bisa bikin endpoint sendiri dengan token dan daftar KB sendiri. MCP server Python-nya deprecated.
  • #2413 Merged PR API key per request buat isolasi multi-tenant di MCP server.
    Sama, selesai lewat PR #3371.
  • #2603 Closed Endpoint buat update daftar KB dari API key ter-scope yang sudah ada.
    Sudah ditutup (owner-only). Kita gak perlu bikin key baru tiap nambah KB.
  • #3402 Closed Audit gak bisa membedakan key mana yang memicu sebuah aksi.
    Sudah ditutup.
  • #4228 Closed OAuth MCP gak bisa melayani user dari aplikasi yang dibikin di depan WeKnora: gak ada browser, gak ada pre-registered client.
    Ditutup, PR #4229. Relevan cuma kalau kita naruh WeKnora di belakang aplikasi lain.

Layer 5 · Lintas layer

  • #3747 Open Masking di semua tahap (masuk, retrieval, output), label klasifikasi dokumen, larangan copy/download/export, audit, lifecycle, dan rule library.
    Berlabel needs-triage. Paling luas, paling mahal. Masuk akal dikerjakan setelah ACL-nya ada.
  • #3317 Open Long-term memory belum punya operator surface, padahal dipakai untuk principal yang gak punya akun (user IM, pengunjung embed, user API).
    Fase 1 sudah merge (PR #4954), follow-up-nya ditawarkan kontributor.
  • #4958 Open Extension point policy deny-only untuk akses KB: cuma bisa memveto, gak pernah memberi izin.
    Diusulkan dengan patch siap pakai. Gak menutup celah ACL, tapi berguna sebagai jaring pengaman di luarnya.
  • #3426 Closed Laporan audit keamanan: 76 temuan plus 11 cacat fungsional.
    PR #3425 ditutup tanpa merge; maintainer minta sisa temuan dipecah jadi issue terpisah. Gak ketemu evidence-nya dijalankan.

Workaround yang didukung sekarang

Kalau ACL per resource belum ada, yang bisa dipakai hari ini adalah memindahkan granularitas ke workspace dan memanfaatkan scope yang sudah disediakan platform. Semua di bawah ini diambil dari CHANGELOG upstream dan teks issue, belum diuji runtime di deployment kita. Sebagian merujuk item di luar 42 issue di atas, dan itu dipakai sebagai bukti kapabilitas, bukan bagian dari peta.

Memisahkan siapa yang boleh melihat knowledge base mana

Cara yang jalan sekarang: Pecah KB ke workspace terpisah: workspace berperan seperti folder, dan KB yang ada di workspace lain tidak muncul di daftar. Untuk memberi akses tanpa memindahkan orang, share KB ke shared space (organization) dengan permission viewer atau editor, dan beri role Viewer di workspace tujuan untuk yang cuma perlu bertanya.

Yang masih bocor: Granularitasnya jadi per workspace, bukan per orang per KB. Satu share berlaku untuk seluruh anggota space, dan orang yang butuh akses harus pindah workspace. Jejak audit ikut terpecah per workspace.

Issue terkait: #5295 #4216 #3626

Boleh dipakai lewat agent, tapi tidak boleh dilihat

Cara yang jalan sekarang: Share agent-nya saja, KB-nya tetap di workspace pemilik. Penerima hanya bisa bertanya lewat agent itu, dan KB-nya tidak ikut muncul di workspace penerima.

Yang masih bocor: Ini batas antarmuka, bukan batas keamanan. Isi KB tetap bisa dipancing lewat jawaban, citation, dan preview file, dan belum ada mekanisme yang membatasi siapa yang boleh menjalankan agent tersebut.

Issue terkait: #5420 #5284

Kredensial mesin dengan scope paling sempit

Cara yang jalan sekarang: Tenant API key sekarang capability-scoped dan bisa dibatasi ke daftar KB tertentu, dengan guard di level route (DenyAPIKeyPrincipal, api_key_gate). Lebih rapi: pakai MCP endpoint bawaan per workspace, satu endpoint punya token sendiri, KB scope sendiri, rate limit sendiri, dan tool write mati secara default. Tokennya bisa dirotasi.

Yang masih bocor: Capability key masih global per key, jadi pola “KB A read-only, KB B writable” dengan satu key belum bisa. Di jalur knowledge_ids, key yang di-scope KB masih ditolak 403. Dan token endpoint adalah identitas endpoint, bukan orang: siapa pun yang memegangnya mendapat semua yang endpoint itu izinkan.

Issue terkait: #3276 #5561 #5284

Membatasi apa yang boleh ditulis agent

Cara yang jalan sekarang: Agent punya level akses read-only, confirm-before-change, dan automatic-write, plus HITL approval, run yang disuspend, dan scoped grant (PR #4250, #4490). Di MCP endpoint, tool group write mati secara default, dan di IM tool write memang sudah dicabut.

Yang masih bocor: Level itu milik satu sesi percakapan, bukan grant organisasi, jadi tidak bisa dipakai sebagai kebijakan tetap. Dan jalur wiki-write lewat tool agent lokal masih tidak memeriksa siapa pemilik KB-nya.

Issue terkait: #5420 #5079

Tahu siapa yang mengubah apa

Cara yang jalan sekarang: Wiki page revision dan chunk revision menyimpan last_edit_source (pipeline, agent, user, atau revert) dan last_editor_id. Ada activity audit trail per KB, audit log per tenant, dan audit log platform.

Yang masih bocor: Aksi yang dijalankan agent di dalam satu workspace tidak bisa diatribusikan ke anggota tertentu. Lewat MCP endpoint, auditnya mencatat user sintetis, jadi penelusurannya berhenti di endpoint.

Issue terkait: #5284

Onboarding dan registrasi yang terkendali

Cara yang jalan sekarang: Mode registrasi bisa dipilih (invite_only, invite_register, DISABLE_REGISTRATION), ada tenantless provisioning dengan self-service workspace yang dikunci flag, OIDC SSO, akun yang dibuat admin, sampai reset password dengan pencabutan sesi.

Yang masih bocor: Batch invite dan panel manajemen user belum ada, jadi provisioning massal tetap manual atau lewat API sendiri. System admin pertama juga masih butuh restart app.

Issue terkait: #1037 #4873 #5001 #5092

Menegakkan kebijakan sendiri (compliance, deny rule)

Cara yang jalan sekarang: Ada extension point policy deny-only dengan patch siap pakai yang bisa didaftarkan di choke point autorisasi yang sudah ada (16 file, +506/−3). Alternatif lebih kasar: jalankan RBAC dalam mode audit-only lewat tenant.enable_rbac=false saat mau migrasi.

Yang masih bocor: Deny-only: hanya bisa memveto, tidak bisa memberi izin, dan belum upstream, jadi harus dipakai di fork. Mode audit-only bukan penegakan.

Issue terkait: #4958 #4216

Satu MCP OAuth server dipakai di banyak workspace

Cara yang jalan sekarang: Bikin satu row mcp_services dengan is_builtin=true langsung di database. Row itu muncul di semua workspace, dan token OAuth disimpan per (tenant, principal, service), jadi setiap user tetap memakai token miliknya di workspace masing-masing.

Yang masih bocor: Belum ada cara resmi provisioning-nya (config, env, atau API system admin), rotasi secret harus lewat SQL, tombol Authorize tidak muncul untuk row builtin, dan agent baru default-nya tidak memasang MCP apa pun.

Issue terkait: #5618

Pola multi-workspace memindahkan granularitas dari resource ke workspace: biaya admin naik dan jejak audit pecah. Itu juga alasan yang membuat pengusul #5420 menolak split workspace, jadi pakai workaround ini untuk menahan sementara, bukan sebagai desain akhir.

Celah yang belum punya issue

  • Jalur wiki-write lewat agent lokal gak dicek kepemilikannya. Tool wiki di agent gak memvalidasi siapa pemilik KB sebelum menulis. Gak ada issue yang mencatat ini, dan #5079 justru minta arah sebaliknya, membuka write di IM.
  • Enforcement “boleh dipakai lewat agent, gak boleh kelihatan” belum lengkap. Sisi list dan 404 sudah ada di proposal #5295, tapi kebocoran lewat jawaban, citation, preview file, dan scope KB milik shared agent belum punya issue khusus.
  • Attribusi audit untuk aksi yang dijalankan agent. Audit per API key sudah ditutup di #3402 dan #5284 menyebut user sintetis untuk MCP, tapi belum ada yang mengusulkan audit per anggota untuk run agent di dalam satu workspace.
  • Belum ada satu choke point autorisasi. #4958 mendekati, tapi bentuknya veto per deployment. Semua jalur (list, IM, MCP, agent, wiki) masih memutuskan sendiri-sendiri, jadi tiap fitur baru berpotensi bikin jalur bocor baru.

Urutan kontribusi yang disarankan

  1. #5295 — fondasi ACL per knowledge base. Desainnya paling lengkap dan paling dekat sama kebutuhan kita. Kalau maintainer tetap diam, nilai sendiri apakah mau kirim patch ke issue itu atau maintain fork dengan risiko drift di bagian access, session, IM, dan MCP.
  2. #3276 dan #5284 — lubang akses mesin. Dua-duanya kecil dan berdiri sendiri. #3276 menyelaraskan scope API key dengan per-KB permission, #5284 menutup tulis lewat MCP dan attribusi audit-nya.
  3. #5420 lalu #2024 + #2090 — level pemakaian dan dokumen. Urutannya penting: ACL KB harus ada dulu, baru izin pemakaian agent/MCP, baru filter level dokumen yang butuh metadata.

Batasan

  • Status issue diambil langsung dari GitHub API pada 17 November 2026 (WIB), bukan dari ingatan atau ringkasan.
  • Ini pembacaan tracker dan kode read-only. Belum ada pengujian runtime, jadi klaim soal perilaku (misal jalur MCP yang bisa ditulis Viewer) disimpulkan dari kode dan deskripsi issue, bukan dari reproduksi.
  • Sweep kata kunci cakupannya luas tapi tidak dijamin lengkap. Issue baru yang muncul setelah tanggal itu belum masuk.
  • Estimasi effort, kalau ada, adalah taksiran dari membaca kode, bukan hasil pengukuran.
  • Bagian workaround disusun dari CHANGELOG upstream dan teks issue. Kami belum menjalankan WeKnora untuk membuktikan tiap langkahnya di deployment sendiri, jadi anggap itu arah, bukan instruksi yang sudah teruji.
