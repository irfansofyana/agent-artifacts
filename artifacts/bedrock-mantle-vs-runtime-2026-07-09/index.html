Amazon Bedrock Mantle vs Runtime

A technical comparison of AWS Bedrock's classic runtime endpoint and the newer Mantle endpoint, with practical guidance for IAM, API keys, model availability, quotas, data residency, Projects, model-level app access, and LiteLLM.

Research date: 2026-07-09Author: JaxSource-first technical brief

Amazon Bedrock Mantle vs Bedrock Runtime

Research date: 2026-07-09
Scope: endpoint differences, access patterns, IAM/API-key implications, model availability, limits, data residency, Projects, LiteLLM support, and deprecation risk.

Executive Summary

AWS now documents two Bedrock inference planes:

  • bedrock-runtime.{region}.amazonaws.com: the classic Bedrock data plane for InvokeModel, Converse, OpenAI Chat Completions compatibility, and Anthropic Messages compatibility.
  • bedrock-mantle.{region}.api.aws: the newer Mantle-powered data plane for OpenAI-compatible Responses, Chat Completions, and Anthropic-compatible Messages.

The practical takeaway: for new OpenAI-compatible and agentic workloads, AWS explicitly recommends bedrock-mantle. For existing Bedrock-native workloads, guardrail-heavy flows, Converse-specific features, provisioned throughput, batch inference, and models not yet on Mantle, bedrock-runtime remains the right tool.

There is no evidence that bedrock-runtime is being deprecated. AWS says it remains fully supported. But product momentum is clearly moving toward Mantle: new console UX, Projects, OpenAI-compatible Responses, GPT-5.x access, separate IAM namespace, CloudWatch namespace, service quotas, and the "next-generation inference engine" language all point there.

Terminology

AWS uses "Mantle" in two related but distinct ways:

  • Engine: Mantle is the distributed inference engine AWS describes as large-scale model serving infrastructure with zero operator access design.
  • Endpoint: bedrock-mantle.{region}.api.aws is the HTTPS API surface exposed to customers for Mantle-backed inference.

This distinction matters because a model can be hosted on Mantle, but the application still integrates with a specific public API surface: OpenAI Responses, OpenAI Chat Completions, or Anthropic Messages.

Sources: - AWS endpoints page: https://docs.aws.amazon.com/bedrock/latest/userguide/endpoints.html - AWS Responses/Mantle page: https://docs.aws.amazon.com/bedrock/latest/userguide/bedrock-mantle.html - AWS zero operator access blog: https://aws.amazon.com/blogs/machine-learning/exploring-the-zero-operator-access-design-of-mantle/

How People Access Each Endpoint

Bedrock Runtime

Common access patterns:

  • AWS SDKs with bedrock-runtime client.
  • SigV4-signed HTTP requests.
  • Bedrock API key via AWS_BEARER_TOKEN_BEDROCK or Authorization: Bearer.
  • OpenAI-compatible Chat Completions path at <https://bedrock-runtime.{region}.amazonaws.com/v1/chat/completions.>

Typical boto3 shape:

import boto3

client = boto3.client("bedrock-runtime", region_name="us-east-1")

response = client.converse(
    modelId="us.anthropic.claude-sonnet-4-6",
    messages=[{"role": "user", "content": [{"text": "Hello"}]}],
)

Bedrock Mantle

Common access patterns:

  • OpenAI SDK with OPENAI_BASE_URL=<https://bedrock-mantle.<region>>.api.aws/v1.
  • OpenAI SDK with special OpenAI model path, for example GPT-5.5 uses <https://bedrock-mantle.us-east-2.api.aws/openai/v1.>
  • Bedrock API key as OPENAI_API_KEY.
  • Direct HTTP with Authorization: Bearer.
  • AWS credentials/SigV4 for HTTP requests where supported.

Typical OpenAI SDK shape:

from openai import OpenAI

client = OpenAI(
    api_key="<bedrock-api-key>",
    base_url="https://bedrock-mantle.us-east-1.api.aws/v1",
)

response = client.chat.completions.create(
    model="openai.gpt-oss-120b",
    messages=[{"role": "user", "content": "Hello"}],
)

GPT-5.5 uses the OpenAI-specific path:

export OPENAI_API_KEY="<bedrock-api-key>"
export OPENAI_BASE_URL="https://bedrock-mantle.us-east-2.api.aws/openai/v1"

Sources: - https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys-use.html - https://docs.aws.amazon.com/bedrock/latest/userguide/inference-chat-completions-mantle.html - https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-openai-gpt-55.html

Why Bedrock Has bedrock-runtime

bedrock-runtime is the original Bedrock model invocation data plane. It exists because Bedrock originally exposed model access through AWS-native APIs:

  • InvokeModel / InvokeModelWithResponseStream for direct provider-specific payloads.
  • Converse / ConverseStream for a normalized chat interface across supported models.
  • Runtime-specific integration with inference profiles, provisioned throughput, custom model invocation, batch-style capabilities, and many existing Bedrock ecosystem features.

Mantle does not erase that. It adds a newer, OpenAI/Anthropic-compatible inference plane optimized for modern API compatibility and agentic workflows.

Source: - https://docs.aws.amazon.com/bedrock/latest/userguide/apis.html - https://docs.aws.amazon.com/bedrock/latest/userguide/endpoints.html

What Models Are Inside One Endpoint vs Another

AWS now maintains an "Endpoint availability by models" page that shows whether each model is available on bedrock-runtime, bedrock-mantle, or both.

Important observations:

  • Many mainstream model families are listed on both endpoints.
  • Some models and features are endpoint-specific.
  • GPT-5.5 and GPT-5.4 are explicitly documented on bedrock-mantle via the Responses API; GPT-5.5 uses openai.gpt-5.5 and the endpoint URL <https://bedrock-mantle.{region}.api.aws/openai/v1.>
  • Some older/native models still matter through bedrock-runtime, especially when the app depends on InvokeModel or Converse.
  • Region availability is still separate from endpoint availability. A model can support Mantle but still not exist in the region you need.

For Jakarta specifically, the Mantle endpoint exists: bedrock-mantle.ap-southeast-3.api.aws. But that does not mean every Mantle model is available in Jakarta. Model-level regional compatibility still decides.

IAM, API Keys, Roles, and Policies

API Key Model

Amazon Bedrock API keys are bearer tokens for Bedrock. AWS documents two types:

  • Short-term keys: up to 12 hours, inherit the IAM principal's permissions, recommended for production.
  • Long-term keys: expiration-based, create an IAM user with attached policies, recommended only for exploration.

API keys can be passed as:

  • AWS_BEARER_TOKEN_BEDROCK
  • Authorization: Bearer <token>
  • api_key when using OpenAI-compatible SDK clients.

API keys are limited to Bedrock and Bedrock Runtime actions, not all Bedrock-adjacent services.

Sources: - https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys.html - https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys-generate.html - https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys-use.html

Separate IAM Namespaces

This is the part to be careful with:

  • Classic Bedrock/Runtime actions live under the bedrock: IAM prefix.
  • Mantle actions live under the bedrock-mantle: IAM prefix.

AWS documents bedrock-mantle as its own service authorization namespace with resources like:

  • arn:${Partition}:bedrock-mantle:${Region}:${Account}:project/${ResourceId}
  • arn:${Partition}:bedrock-mantle:${Region}:${Account}:customized-model/${ResourceId}
  • arn:${Partition}:bedrock-mantle:${Region}:${Account}:reservation/${ResourceId}

Mantle also has its own condition keys, including:

  • bedrock-mantle:BearerTokenType
  • bedrock-mantle:DataRetentionMode
  • bedrock-mantle:Model
  • bedrock-mantle:ProjectArn
  • bedrock-mantle:ServiceTier

Sources: - https://docs.aws.amazon.com/service-authorization/latest/reference/list_amazonbedrock.html - https://docs.aws.amazon.com/service-authorization/latest/reference/list_amazonbedrockpoweredbyawsmantle.html

Giving an App Access to Runtime vs Mantle

For a classic Bedrock app using InvokeModel or Converse, grant Bedrock runtime actions and model resources, for example:

{
  "Effect": "Allow",
  "Action": [
    "bedrock:InvokeModel",
    "bedrock:InvokeModelWithResponseStream"
  ],
  "Resource": [
    "arn:aws:bedrock:us-east-1::foundation-model/anthropic.claude-3-haiku-20240307-v1:0"
  ]
}

For API-key usage against the runtime endpoint, also account for:

{
  "Effect": "Allow",
  "Action": "bedrock:CallWithBearerToken",
  "Resource": "*"
}

For Mantle, policies must include Mantle actions. For bearer-token usage:

{
  "Effect": "Allow",
  "Action": "bedrock-mantle:CallWithBearerToken",
  "Resource": "*"
}

For project-scoped Mantle usage, also control project resources and conditions:

{
  "Effect": "Allow",
  "Action": [
    "bedrock-mantle:CreateInference",
    "bedrock-mantle:GetInference",
    "bedrock-mantle:ListModels"
  ],
  "Resource": "arn:aws:bedrock-mantle:us-east-1:123456789012:project/proj_example"
}

Exact actions should be validated against the live AWS service authorization page because Mantle is actively expanding.

Sources: - https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys-permissions.html - https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys-modify.html - https://docs.aws.amazon.com/service-authorization/latest/reference/list_amazonbedrockpoweredbyawsmantle.html

Giving One App Access to Specific Mantle Models

Short answer: yes, it is possible, but it should be designed as "app identity + Mantle IAM policy + optional Project boundary", not as a magic per-app toggle in the model catalog.

There are three layers:

  1. App identity: the application should run as its own IAM principal, such as an ECS task role, EKS Pod Identity role, IRSA role, EC2 instance profile, or a dedicated IAM user only when API-key exploration is acceptable.
  2. Mantle authorization: that principal must have bedrock-mantle permissions, not only bedrock permissions.
  3. Model/project constraints: restrict which models and projects the principal can use through Mantle resource ARNs and condition keys.

The most important Mantle condition key for model-level gating is:

  • bedrock-mantle:Model

The most important project-level condition key is:

  • bedrock-mantle:ProjectArn

That means an internal platform can give App A access to only a subset of Mantle models by attaching a policy to App A's role that allows Mantle inference only when bedrock-mantle:Model matches the approved model IDs.

Example shape:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowSpecificMantleModels",
      "Effect": "Allow",
      "Action": [
        "bedrock-mantle:CreateInference",
        "bedrock-mantle:GetInference",
        "bedrock-mantle:ListModels"
      ],
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "bedrock-mantle:Model": [
            "openai.gpt-oss-120b",
            "anthropic.claude-sonnet-4-6"
          ]
        }
      }
    }
  ]
}

If the app must be isolated to one Project as well:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowSpecificMantleProjectAndModels",
      "Effect": "Allow",
      "Action": [
        "bedrock-mantle:CreateInference",
        "bedrock-mantle:GetInference"
      ],
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "bedrock-mantle:ProjectArn": "arn:aws:bedrock-mantle:us-east-1:123456789012:project/proj_example",
          "bedrock-mantle:Model": [
            "openai.gpt-oss-120b"
          ]
        }
      }
    }
  ]
}

For bearer-token use, the principal also needs Mantle bearer token permission:

{
  "Effect": "Allow",
  "Action": "bedrock-mantle:CallWithBearerToken",
  "Resource": "*"
}

Production recommendation: prefer short-term Bedrock API keys or SigV4 IAM role access. Long-term API keys create a hidden IAM user and are acceptable for exploration, but they are awkward for tightly controlled app access because the credential lifecycle can drift away from the app's workload identity.

Sources: - https://docs.aws.amazon.com/service-authorization/latest/reference/list_amazonbedrockpoweredbyawsmantle.html - https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys.html - https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys-permissions.html

Is Per-App Per-Model Mantle Access Perfect?

Not fully.

What works:

  • Separate IAM principal per app.
  • Allow/deny by Mantle IAM action.
  • Restrict by bedrock-mantle:Model.
  • Restrict by bedrock-mantle:ProjectArn.
  • Use Projects for cost isolation and stored-response scope.
  • Use separate API keys per app if you intentionally choose bearer-token access.

What does not appear to exist as a first-class Mantle product feature yet:

  • A Bedrock console "App X can use only models A/B/C" toggle.
  • A Project-native model allowlist that replaces IAM.
  • A LiteLLM-native guarantee that every Mantle Project/Workspace header edge case is already correct across all APIs.

So the clean internal platform design is:

  1. Define model groups in your platform catalog.
  2. Map each app to an IAM role.
  3. Generate IAM policy from the app's approved model group.
  4. Optionally create one Mantle Project per app/team/environment for cost and observability.
  5. Route app calls through LiteLLM or your gateway with explicit provider strings and project headers.
  6. Validate with real deny tests, because IAM condition behavior is the source of truth.

For example:

App IAM principal Mantle Project Allowed models Auth path
aml-case-assistant-prod role/aml-case-assistant-prod proj_aml_prod openai.gpt-oss-120b, anthropic.claude-sonnet-4-6 SigV4 preferred
devex-copilot-dev role/devex-copilot-dev proj_devex_dev openai.gpt-oss-20b short-term API key acceptable
finance-sandbox role/finance-sandbox proj_finance_sandbox low-cost models only short-term API key

Projects in Bedrock Mantle

Projects are application-level boundaries for OpenAI-compatible workloads on Mantle.

Use Projects when you need:

  • Cost tracking by app/team/environment/cost center.
  • Access isolation at project level.
  • Operational observability per workload.
  • A single AWS account that still has multiple logical app boundaries.

AWS says Projects can only be used with models using OpenAI-compatible APIs against bedrock-mantle. If using bedrock-runtime, use Inference Profiles instead for tagging and observability.

Each AWS account has a default project; additional projects can be created through the Projects API. Requests can be associated with a project using OpenAI-compatible project headers.

Important operational consequence: stored Responses API data is scoped by Project. A stored response from one Project cannot be used as previous_response_id in another Project.

Source: - https://docs.aws.amazon.com/bedrock/latest/userguide/projects.html - https://docs.aws.amazon.com/bedrock/latest/userguide/bedrock-mantle.html

Limits, Quotas, and Throughput

Runtime Quotas

bedrock-runtime uses the classic quota model:

  • Per-model RPM.
  • Per-model TPM.
  • TPM counts input and output together.
  • Quotas apply across Converse, ConverseStream, InvokeModel, and InvokeModelWithResponseStream.

Mantle Quotas

bedrock-mantle uses a different quota model:

  • Separate input tokens per minute.
  • Separate output tokens per minute.
  • No RPM quota documented for Mantle.
  • Prompt-cache reads do not count against input TPM.
  • Some Mantle models do not yet expose per-account TPM quotas in Service Quotas; AWS says throughput is governed by internal service capacity.
  • Mantle quotas are independent from runtime quotas, even when calling the same underlying model.

Important: custom inference profile quotas, batch inference quotas, and provisioned throughput allocations apply only to bedrock-runtime, not Mantle.

Sources: - https://docs.aws.amazon.com/bedrock/latest/userguide/quotas-runtime.html - https://docs.aws.amazon.com/bedrock/latest/userguide/quotas-mantle.html - https://docs.aws.amazon.com/bedrock/latest/userguide/scaling-throughput-best-practices.html

Data Residency and Retention

Data residency is controlled by region selection and inference routing mode:

  • In-Region keeps requests within a single region.
  • Geo cross-region routes within a geography.
  • Global cross-region can route globally.

For Mantle Responses API, storage behavior matters:

  • store=true is the default to match OpenAI Responses semantics.
  • When stored, response data including input and output is retained for 30 days in the source region.
  • Stored data is encrypted at rest and scoped to the AWS account's Project resource.
  • store=false disables retention for that request, but then previous_response_id cannot be used.

AWS also added explicit data retention controls at account/project level. If the account/project is configured for zero data retention and a model requires retention, Bedrock blocks the request rather than silently retaining data.

Zero operator access is a separate but related design claim: AWS says Mantle is designed so no AWS operator, customer operator, or model provider operator can access prompts/completions during service operation.

Sources: - https://docs.aws.amazon.com/bedrock/latest/userguide/bedrock-mantle.html - https://docs.aws.amazon.com/bedrock/latest/userguide/data-retention.html - https://docs.aws.amazon.com/bedrock/latest/userguide/models-region-compatibility.html - https://aws.amazon.com/blogs/machine-learning/exploring-the-zero-operator-access-design-of-mantle/

LiteLLM Integration

LiteLLM currently documents a dedicated bedrock_mantle/ provider prefix:

from litellm import completion
import os

os.environ["BEDROCK_MANTLE_API_KEY"] = "your-bedrock-api-key"

response = completion(
    model="bedrock_mantle/openai.gpt-oss-120b",
    messages=[{"role": "user", "content": "hello from litellm"}],
)

Proxy config example:

model_list:
  - model_name: gpt-oss-120b
    litellm_params:
      model: bedrock_mantle/openai.gpt-oss-120b
      api_key: os.environ/BEDROCK_MANTLE_API_KEY
      api_base: https://bedrock-mantle.us-east-1.api.aws/v1

LiteLLM docs say:

  • Use bedrock_mantle/<model-id>.
  • BEDROCK_MANTLE_REGION controls region, falling back to AWS_REGION, then us-east-1.
  • For GPT-5.4/GPT-5.5, use LiteLLM's /v1/responses flow and bedrock_mantle/openai.gpt-5.5.

Version Timeline

Based on Git history:

  • Initial Bedrock Mantle support for Claude Mythos / Mantle route landed around commit a302613eb5 on 2026-04-21. The earliest stable tag containing it appears to be v1.83.14-stable.
  • Native OpenAI Responses routing for Mantle landed around 2026-06-02 and appears in v1.88.2.
  • SigV4/IAM auth support for the Mantle Responses route landed around 2026-06-08 and appears in v1.89.1.

Interpretation:

  • If you only need early Mantle Anthropic/Chat Completions paths, start from v1.83.14-stable or newer.
  • If you need OpenAI GPT-5.x Responses on Mantle, use at least v1.88.2.
  • If you need IAM/SigV4 for Mantle Responses, use at least v1.89.1.
  • For production today, prefer the newest stable LiteLLM version because open issues still exist around Mantle project headers and SigV4 details.

Why We Should Pay Attention to Bedrock Mantle

Short version: Mantle is where AWS is putting the new abstraction layer.

Reasons:

  1. AWS explicitly recommends Mantle for new applications.
  2. Mantle is the path for OpenAI-compatible Responses API on Bedrock.
  3. Some latest/frontier models are Mantle-first or Mantle-only.
  4. Projects give app-level isolation and cost tracking that maps better to internal platform use cases than raw IAM-only attribution.
  5. Mantle has a separate IAM namespace, CloudWatch namespace, endpoint shape, quotas, and service-auth model, so treating it as "just another runtime path" will cause access and observability mistakes.
  6. LiteLLM support is moving quickly but still has edge-case gaps; platform teams need to pin versions and test auth/project/data-retention behavior before exposing it broadly.

Is bedrock-runtime Going Away?

Current answer: no evidence.

AWS says:

  • bedrock-runtime "remains fully supported".
  • Use it when you need Bedrock-native InvokeModel or Converse.
  • Use it when your target model is not available on Mantle.
  • Provisioned throughput, batch inference, and custom inference profile quota semantics remain runtime-only.

But the strategic direction is obvious: new OpenAI-compatible, project-scoped, agentic, stateful, and latest-model experiences are being oriented around Mantle. The correct platform posture is not "runtime is deprecated"; it is "support both, but make Mantle a first-class integration path now."

Source: - https://docs.aws.amazon.com/bedrock/latest/userguide/endpoints.html - https://docs.aws.amazon.com/bedrock/latest/userguide/quotas-mantle.html

Recommendations for an Internal AI Platform

  1. Treat bedrock-runtime and bedrock-mantle as separate providers internally.

Do not hide them behind a single "Bedrock" checkbox. They have different endpoints, IAM actions, quotas, project/isolation models, data-retention behavior, and model availability.

  1. Default new OpenAI-compatible apps to Mantle.

If an app already speaks OpenAI SDK semantics, Mantle reduces glue code and unlocks Responses API and Projects.

  1. Keep runtime for Converse/Invoke workloads.

Runtime is still the right path for existing Bedrock-native code, structured outputs through Converse/Invoke where Mantle lacks parity, provisioned throughput, batch inference, and models not on Mantle.

  1. Build a model catalog that tracks endpoint + region + API compatibility.

Columns should include:

  • Model ID.
  • Provider.
  • Endpoint support: runtime, Mantle, both.
  • API support: Invoke, Converse, Chat Completions, Responses, Messages.
  • Region support.
  • In-region / geo / global availability.
  • Quota model.
  • Data-retention requirement.

  • LiteLLM provider string.

  • Pin LiteLLM and test the exact route.

For Mantle:

  • Test bearer-token auth.
  • Test IAM/SigV4 auth if required.
  • Test OpenAI-Project / Anthropic workspace headers.
  • Test data-retention mode behavior.
  • Test streaming.

  • Test cost mapping.

  • Add policy templates for both endpoints.

Runtime policy templates should cover bedrock:InvokeModel*, inference profile ARNs, and bedrock:CallWithBearerToken where API keys are allowed.

Mantle policy templates should cover bedrock-mantle:* actions required for inference, bedrock-mantle:CallWithBearerToken, project resources, and project/data-retention condition keys.

  1. Monitor both namespaces separately.

Runtime metrics and Mantle metrics do not land under the same assumptions. Mantle uses AWS/BedrockMantle for metrics and has project/model dimensions.

Source: - https://docs.aws.amazon.com/bedrock/latest/userguide/monitoring-mantle-metrics.html

Open Questions / Things to Validate in a Real AWS Account

  • Exact IAM action minimum for Mantle inference per API surface: Responses vs Chat Completions vs Messages.
  • Whether your organization's SCPs or permission boundaries already deny bedrock-mantle:*.
  • Whether Bedrock API keys are acceptable in your app security model, or whether all app access must use role-based SigV4.
  • Whether LiteLLM's current stable version correctly handles project headers for both OpenAI and Anthropic Mantle surfaces.
  • Whether Jakarta (ap-southeast-3) has the specific model you need, not merely the Mantle endpoint.
  • Whether desired data-retention mode is compatible with each model.
  • Whether workload needs provisioned throughput/batch inference, which currently pushes you back to runtime.
