Codex Security untuk GitLab: yang benar-benar bisa dipakai, dan di mana batasnya

Catatan riset atas Codex Security dari OpenAI untuk alur kerja GitLab: apa yang sudah bisa dipakai hari ini, fakta yang menentukan desainnya, batasan yang jangan diklaim, dan asumsi yang belum diverifikasi.

Bahasa Indonesia·English

Ringkasan

Codex Security itu agen application security dari OpenAI, masih tahap research preview. Bentuknya CLI (@openai/codex-security, binary cs dan codex-security), SDK TypeScript, satu GitHub Action, dan plugin Codex. Yang membuatnya beda dari scanner biasa: dia menalar atas source code, bukan mencocokkan signature, jadi di kode platform internal jumlah noise-nya jauh lebih sedikit.

Tapi bagian yang benar-benar berguna hari ini lebih sempit dari itu. validate, patch, dan verify-fix menerima temuan sebagai teks biasa atau path file, jadi temuan dari GitLab SAST/DAST bisa diserahkan ke agen tanpa menjalankan scanner Codex Security sama sekali. Itu yang membuat urutannya berubah: backlog temuan yang sudah ada di GitLab adalah masalah mendesak, sedangkan scanning untuk temuan baru bisa menyusul setelah loop perbaikannya dipercaya.

Prioritasnya fix-first. Ambil temuan yang sudah dilaporkan, nilai dulu, baru patch. Scanning untuk temuan yang belum pernah dilaporkan siapa pun tetap penting, tapi dia bergantung pada dua hal yang belum terbukti: alias gateway yang Responses-native dan model di belakangnya yang sanggup mengikuti schema. Keduanya harus ditutup lebih dulu.

Keputusan, 19 November 2026

Yang dicek ulang terhadap dokumentasi CLI saat ini, bukan dari menjalankan job-nya.

  • Pipeline GitLab resmi tidak bisa dipakai tanpa akses Codex Security. Job yang kita tulis sendiri tetap bisa memanggil CLI.
  • scan --patch --create-pr adalah loop yang berakhir di draft MR. Flag itu tidak terkunci di YAML resmi. LiteLLM bukan nilai --provider. Jangkau lewat override --codex dan wire_api = "responses". Alias harus melayani /v1/responses secara native.
  • MR muncul hanya kalau patch-nya verified. Tanpa Trusted Access, model Daybreak tidak tersedia, dan sebagian kelas temuan bisa ditolak. Belum dijalankan di runner sungguhan.
  • Perbandingan dengan proyek open-source ada di halaman pendamping.

Dua pekerjaan yang berbeda

Dua hal ini gampang dicampur, dan mencampurnya bikin rencana kerja melenceng berminggu-minggu: satu pekerjaan memindai repo untuk mencari kerentanan yang belum pernah dilaporkan, satu lagi menilai dan memperbaiki temuan yang sudah dilaporkan orang lain. Yang kedua tidak butuh yang pertama jalan.

Pekerjaan Isinya
Scan Mencari kerentanan yang belum pernah dilaporkan siapa pun. Butuh threat model untuk repo itu, analisis, lalu validasi di sandbox.
Assess & fix Menilai dan memperbaiki temuan yang sudah dilaporkan scanner lain. Tidak butuh scanner-nya ikut jalan: temuan masuk sebagai teks biasa atau path file.

Peta kemampuan CLI

Ada 7 entri perintah yang relevan. Empat teratas yang dipakai di alur fix-first, sisanya operasi workbench atas hasil yang sudah tersimpan.

Perintah Kegunaan

validate Menilai satu kandidat temuan terhadap source, di sandbox read-only.

findings, scans, export,

Alur fix-first

  1. Ambil temuan dari sumber mana pun. GitLab SAST/DAST, vulnerability report, GitHub code scanning, Sonar, Snyk, Semgrep, semuanya bisa.
  2. Tulis satu statement per temuan yang menyebut rule, lokasi, dan apa yang terlihat, misalnya [sast 101, severity high] SQL injection in report filter at src/reports/query.py:42.
  3. validate dulu. Read-only: tidak build, tidak menjalankan test, tidak mengeksekusi aplikasi, tidak menghubungi service. Gate langkah berikutnya di verdict-nya.
  4. patch --create-pr --assess-patch-risk cuma untuk temuan yang lolos validate.
  5. verify-fix kalau perbaikannya sudah landing dan butuh pembacaan independen.

Jaga assess dan patch sebagai dua tahap yang bisa direview orang. Validate biayanya cuma model call; patch menyentuh branch. Yang memutuskan apa yang di-patch tetap manusia.

Fakta yang menentukan desain

  • validate tidak punya --json. Supaya output-nya bisa digate mesin, paksa struktur dengan --output-schema plus satu JSON Schema kecil. Kalau output model tidak sesuai schema, command keluar dengan code 2 dan tidak menulis apa pun. Tanpa ini pipeline tidak bisa memutuskan secara mekanis, cuma bisa menebak.
  • patch mengembalikan verified, no_change, blocked, atau failed. Hanya hasil verified yang di-commit. SANDBOX_UNAVAILABLE dan NO_PATCH_APPLIED itu kejadian operasional, bukan penilaian keamanan. Perubahan file saja juga bukan bukti perbaikannya benar.
  • Patching temuan yang kita suplai butuh working tree bersih. Kerjakan di direktori temp di luar checkout dan copy artefaknya setelah proses patch selesai. Kalau file yang mau di-patch sudah punya edit lokal, CLI-nya meninggalkan patch di working tree buat kita review, bukan mempublish-nya.
  • --create-pr membuka draft PR atau MR lewat gh atau glab, dan tidak pernah merge. Kalau push-nya gagal, CLI mencetak perintah patch --resume-pr BRANCH untuk mengulang dari checkout yang sama.
  • Exit code: 0 lolos, 1 ada temuan, 2 error, 130 / 143 terinterupsi. Gate yang menganggap setiap non-zero sebagai temuan akan melaporkan error sebagai kerentanan.
Exit code Artinya
0 Lolos, tidak ada temuan di atas threshold.
1 Ada temuan di atau di atas threshold.
2 Error input, runtime, atau integritas hasil.
130 / 143 Proses terinterupsi.
  • --provider itu enum tertutup (openai, openrouter, fireworks, amazon-bedrock, plus satu jalur cheaper-inference). Tidak ada opsi OpenAI-compatible generik, jadi gateway self-hosted hanya bisa dijangkau lewat override config Codex native.
  • Routing inference lewat gateway sendiri tidak memberi entitlement. Run yang memakai inference OpenAI tetap butuh akses Codex Security di akun pemilik key-nya.
  • Supplied-issue patching butuh tree yang bersih, dan artefak GitLab harus berada di dalam direktori project. Dua batasan itu bertabrakan, jadi urutannya harus: kerja di luar checkout, patch dulu, baru copy artefak masuk.

Batasan yang jangan diklaim

  • Jangan pernah menjanjikan auto-fix untuk DAST. validate menalar dari bukti di source dan tidak menjalankan aplikasi, jadi temuan runtime tanpa lokasi source tidak bisa dinilai sampai ada orang yang memetakan endpoint-nya ke handler. Validasi dinamis memang ada lewat --validation-prompt-file, lengkap dengan setup, target yang diizinkan, hasil yang diharapkan, dan cleanup, tapi itu proyek sendiri.
  • --max-cost itu guardrail estimasi, bukan batas tagihan. Request yang sudah jalan bisa melewatinya.
  • --external-sandbox mematikan enforcement filesystem dan network milik agennya sendiri. Pakai hanya di dalam container yang menyediakan isolasi itu, jangan sebagai jalan pintas untuk runner yang tidak bisa sandbox.
  • Sebagian kelas kerentanan dan protected finding butuh Trusted Access for Cyber. Cek dulu sebelum menjanjikan cakupannya, jangan setelah.
  • Research preview: pin versi CLI-nya secara sadar, jangan ikut latest. Setiap bump, tes ulang autentikasi, artefak, dan ingest laporan. Versi yang dipublish bergerak lebih cepat dari contoh di dokumentasi vendornya sendiri.
  • HTTP 200 di /responses tidak membuktikan apa pun soal route gateway. Deployment LiteLLM yang bridged menjawab path itu dan membuang field khusus Responses, termasuk deklarasi tool, dan gejalanya muncul sebagai kegagalan yang sulit dijelaskan di tengah run.
  • Baca coverage dan exclusion sebelum menyebut sesuatu bersih. Selesai bukan berarti tersertifikasi, dan diff scan tidak bilang apa pun soal sisa repo di luar diff itu.

Menyambung lewat gateway self-hosted

Agennya jalan dari Codex home yang terisolasi, jadi provider custom harus didefinisikan di dalamnya. Taruh setting-nya di file profile yang namanya sama dengan nama profile-nya, lalu pilih dengan --codex "profile='<profile>'".

# $CODEX_HOME/<profile>.config.toml
model = "<alias yang diekspos gateway>"
model_reasoning_effort = "high"
model_provider = "<provider-id>"

[model_providers.<provider-id>]
name = "<nama tampilan>"
base_url = "https://<gateway>/v1"
wire_api = "responses"           # wajib; agennya bicara lewat Responses API
env_key = "<ENV_VAR_YANG_ISI_KEY>"
requires_openai_auth = false     # jangan pernah coba auth akun ChatGPT atau OpenAI

Route-nya harus Responses-native. Deployment tanpa konfigurasi Responses native akan menjembatani /v1/responses lewat /v1/chat/completions, mengonversi request-nya, lalu mengaproksimasi atau membuang field khusus Responses. Verifikasi deployment-nya, bukan route-nya:

curl -s "$BASE/model/info" -H "Authorization: Bearer $ADMIN_KEY" \
| jq '.data[] | {name: .model_name, model: .litellm_params.model,
                 endpoints: .model_info.supported_endpoints}'

/v1/responses harus muncul di model_info.supported_endpoints. Opt-in itu dibaca per deployment, tidak tergantung prefix provider, dan berlaku untuk request baru tanpa restart. Untuk provider native custom, --auth auto dan --auth api-key memakai environment variable yang disebut model_providers.<id>.env_key, sedangkan --auth chatgpt memilih auth akun tersimpan dan mengabaikan provider key, jadi provider yang butuh key-nya sendiri tidak bisa memakai opsi itu.

Wiring ke GitLab CI

Pisahkan kredensial, dan jangan biarkan satu job bisa membaca secret job lain. Tiga secret, tiga scope:

Kredensial Scope Dipakai di
Model key Virtual key gateway Kedua tahap, lewat provider profile.
Read token read_api Cuma tahap validate, buat menarik daftar temuan.
Write token api, write_repository Cuma tahap publish, buat push branch dan bikin draft MR.
  • Tiap secret disalin ke shell variable, yang asli di-unset, lalu agen dijalankan dengan env -i plus environment minimal yang eksplisit (PATH, HOME, LANG, CI, CI_PROJECT_DIR, CODEX_HOME, CODEX_SECURITY_STATE_DIR, dan key provider-nya). Agen menjalankan command yang dikontrol repo dan tidak boleh mewarisi environment job.
  • Seluruh run di luar checkout (WORK_DIR=/tmp/...), hasilnya di-copy masuk ke direktori project di akhir. Menulis file kerja di bawah $CI_PROJECT_DIR mengotori tree dan bikin patch menolak jalan.
  • Job-nya butuh git, python3, ripgrep, util-linux untuk cek sandbox, curl, dan glab untuk --create-pr. Bake semuanya di image runner yang di-pin, jangan install saat job jalan.
  • Gagalkan lebih awal dan berisik: unshare -Ur true (agennya sandbox sendiri pakai user namespace), lalu --version, lalu satu pass --dry-run --verbose yang mencetak provider, model, dan effort yang resolve tanpa memulai run berbayar.
  • --setup-git-credential-helper di glab auth login bikin push branch-nya memakai token yang sama. CI_JOB_TOKEN tidak bisa membuat merge request, jadi jalur tulisnya perlu project access token khusus.
  • Findings API GitLab butuh scope=all, karena default-nya cuma temuan dismissed. Endpoint vulnerabilities dan vulnerability_findings ditandai deprecated ke arah GraphQL, dan responsnya dipaginasi (20 per halaman secara default), jadi backlog besar butuh paging sendiri.

Temuan dari mana di GitLab

Sumber Cara ambil Paling cocok untuk
Vulnerability report GET /projects/:id/vulnerability_findings dengan read token. Pandangan backlog: apa yang masih open sekarang, setelah triase manusia.
SAST artifact gl-sast-report.json dari job scanner. Output mentah seluruhnya, termasuk temuan yang GitLab tidak promosikan jadi record.
DAST artifact Artefak report dari job DAST. Temuan runtime. Sebagian besar butuh triase dulu sebelum bisa di-patch.

Payload scanner-nya sendiri datang sebagai string JSON di finding.raw_metadata. Untuk SAST, lokasinya ada di sana sebagai location.file dan location.start_line. Lokasi DAST mendeskripsikan request (hostname, path, method, param), dan itu sebabnya temuan DAST tidak bisa langsung diserahkan ke validate: tidak ada baris source yang bisa dinilai.

Risiko terbuka

Semua di bawah ini datang dari dokumentasi resmi OpenAI, LiteLLM, dan GitLab, bukan dari hasil eksekusi. Belum ada satu pun yang pernah dijalankan di runner sungguhan. Ada 8 item yang harus ditutup sebelum ini dipakai serius, dan yang pertama sengaja ditaruh paling atas karena itu titik paling mungkin desainnya perlu diubah.

Asumsi Cara menutupnya
--auth api-key menerima environment key milik provider custom. Run preflight. Ini titik paling mungkin di mana desainnya perlu diubah.
Alias gateway-nya Responses-native, bukan bridged. Cek model_info.supported_endpoints. Kalau bridged, ini jadi tiket gateway sebelum apa pun bisa mulai.
Model di belakang alias bisa menghasilkan JSON sesuai schema. Jalankan validate pada satu temuan dan periksa outputnya. Tanpa ini, gate confirm-then-patch butuh mekanisme lain.
Patching a supplied finding can run unattended in a CI checkout, and the files the CLI reports are the files that changed. One real run, then git status and git diff --stat in the clone. The branch is cut from exactly those reported paths.
Field path di respons vulnerability sesuai dengan yang diharapkan mapping script. Dump satu respons asli lalu bandingkan. Endpoint-nya ditandai deprecated ke arah GraphQL.
Temuan tanpa lokasi source bisa dipetakan dengan andal. Untuk DAST, anggap belum bisa di iterasi pertama dan rencanakan triase sebagai langkah terpisah.
Semantik entitlement tetap berlaku saat inference lewat gateway. Konfirmasi ke pemilik akun apakah akses Codex Security mengikuti key yang sampai ke model.
Kualitas perbaikan tetap bagus di model apa pun yang dipasang di belakang alias. Bandingkan beberapa fix buatan agen dengan fix dari model frontier. Kalau gateway-nya menyajikan model yang lebih kecil, perilaku validated-fix akan turun.

Status verifikasi

Yang sudah benar-benar diuji di mesin ini:

  • Pipeline CI-nya parse sebagai YAML, dan setiap blok shell di dalamnya lolos bash -n.
  • Tiga script helper dijalankan terhadap payload GitLab sintetis: temuan SAST dengan lokasi di raw_metadata berubah jadi statement, temuan DAST tanpa lokasi masuk daftar triage, temuan dengan metadata rusak ditangani tanpa crash, verdict confirmed menghasilkan kandidat patch, dan verdict not_applicable tidak.
  • Command yang dihasilkan script-nya juga lolos bash -n, termasuk patch --create-pr per temuan yang dikonfirmasi.

Yang belum, dan ini penting: pipeline-nya belum pernah jalan di runner GitLab milik siapa pun, belum pernah menyentuh alias gateway sungguhan, dan kualitas perbaikannya belum pernah dibandingkan dengan fix buatan manusia. Anggap bagian gateway dan CI di halaman ini sebagai rancangan yang sudah divalidasi sintaks, bukan resep yang sudah terbukti.
