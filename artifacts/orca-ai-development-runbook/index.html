1. The operating model

Orca is an agent development environment. It gives each task a real git worktree, agent terminals, editor state, browser tabs, and a diff against the task's start ref. You can run several tasks or several attempts at one task without making agents share a checkout. Orca keeps normal git and pull-request controls in the loop. (Orca overview, worktree model)

Use this production loop:

Ticket or problem
      ↓
Task brief with acceptance criteria
      ↓
Fresh Orca worktree from an explicit ref
      ↓
One primary implementation agent
      ↓
Tests + runtime evidence + self-review
      ↓
Human line-by-line diff review
      ↓
Independent agent review when risk warrants it
      ↓
Commit → push → draft PR → CI → merge
      ↓
Delete or archive the worktree

Orca removes checkout contention. It does not remove the engineering bottlenecks that follow: task ambiguity, review capacity, test quality, and integration risk. Optimize the full loop rather than the number of live agents.

Default limits

Start with these limits and adjust from evidence:

Item Default limit Reason
Active implementation worktrees 2 You can still review both with care.
Research or review worktrees 1 additional Read-only work has less integration cost.
Agents editing one worktree 1 Multiple writers create hidden coordination work.
Competing attempts for one task 2 Use 3 only for a hard or high-value decision.
Diff size before splitting 400 net changed lines Large AI diffs hide unrelated changes.
Review feedback rounds 2 Re-scope after the second failed revision.
Task duration before checkpoint 60 to 90 minutes Long sessions accumulate stale assumptions.

Treat these as control limits, not targets.

2. Choose the right execution pattern

Pattern A: One task, one agent

Use for routine features, tests, documentation, migrations with a known pattern, and contained bugs.

  1. Create one worktree.
  2. Give one agent a complete task contract.
  3. Review evidence and diff.
  4. Ask the same agent for one revision batch.
  5. Ship.

This should handle most work.

Pattern B: Race two agents

Use when uncertainty dominates implementation cost:

  • a bug has several plausible causes;
  • an unfamiliar subsystem needs investigation;
  • an architectural choice has two credible designs;
  • the first attempt failed and the cause remains unclear.

Create two worktrees from the same commit and use the same acceptance criteria. Ask each agent to record its diagnosis before changing code. Compare:

  1. correctness of the diagnosis;
  2. size and clarity of the diff;
  3. strength of tests;
  4. operational risk;
  5. ease of maintenance.

Pick one implementation. Delete the other branch after preserving any useful findings. Orca documents the three-agent version of this workflow, but two attempts give a better cost-to-signal ratio for daily work. (Parallel agents recipe)

Pattern C: Implementer plus independent reviewer

Use for security-sensitive code, money movement, authentication, authorization, concurrency, infrastructure, data migrations, or public APIs.

  • Writer: gets a worktree and can edit.
  • Reviewer: reads the task, plan, and final diff. It does not edit.
  • Owner: you decide which findings block the PR.

Keep the review independent. Do not paste the implementer's reasoning as the reviewer's conclusion. Give the reviewer the requirements and the diff, then ask it to find violations.

Pattern D: Parallel decomposition

Use only when tasks have clean file or service boundaries. Good examples:

  • service implementation and client SDK;
  • backend endpoint and independent load-test harness;
  • code change and documentation update;
  • migration code and rollback verification.

Create one worktree per deliverable. Name one owner for integration. Avoid parallel edits to shared schemas, generated files, dependency locks, root configuration, or the same tests.

Pattern E: UI feedback loop

Use a worktree browser for frontend work:

  1. Start the dev server in the worktree.
  2. Open it in that worktree's browser.
  3. Set desktop and mobile viewport sizes.
  4. Use Design Mode to attach DOM, computed styles, a screenshot, and source location to the active agent.
  5. Test behavior after the visual fix.
  6. Review the source diff and screenshots.

Orca's browser stays scoped to the worktree. Design Mode can send page elements and source-map locations to the agent. (Browser, Design Mode)

3. Agent routing

Agent choice matters less than task shape and verification, but stable defaults reduce decision overhead.

Work type First choice Second choice Notes
Normal implementation and repository work Pi Codex Keep Pi lean. Add repo skills and extensions only when they remove repeated work.
Large-codebase investigation and planning Claude Code Codex Claude supports plan mode and separate subagent contexts for research.
Focused debugging, test repair, refactors Codex Pi Use workspace-write sandboxing and approvals for commands outside the task boundary.
UI iteration with browser feedback Cursor CLI Claude Code Cursor offers Ask and Plan modes; Orca adds its scoped browser and Design Mode.
Independent correctness review Agent different from writer Same agent in a fresh session Cross-agent disagreement gives useful signal.
Cheap read-only reconnaissance Pi with read-only tools Cursor Ask mode Do not pay the edit-and-test overhead before the task is shaped.

Pi as the default worker

Orca ships Pi with auto-setup, hooks, and status support. Pi loads AGENTS.md, supports persistent sessions and tree navigation, and can run with a restricted tool list. Its small core works well when the repository carries clear instructions. (Orca supported agents, Pi coding agent)

Use Pi for:

  • scoped implementation;
  • repository maintenance;
  • test authoring;
  • small investigations;
  • custom workflows backed by Pi packages, prompts, or extensions.

Use a fresh Pi session when the task changes. Use a session branch when you want to try a different approach while preserving prior context. Keep project trust decisions explicit because project-level AGENTS.md, settings, skills, and extensions can influence tool behavior.

Claude Code

Use plan mode for changes that need approval before edits:

claude --permission-mode plan

Ask Claude to use subagents for codebase research or independent review so file exploration does not fill the implementation context. (Claude Code workflows, best practices)

Orca reads ~/.claude, attaches state hooks, tracks usage, and recognizes repo-level Claude hooks and memory. (Claude Code in Orca)

Codex

Use Codex for contained implementation and methodical debugging. Keep its standard boundary for work repositories:

codex --sandbox workspace-write --ask-for-approval on-request

Codex separates the sandbox boundary from the approval policy. Workspace-write plus on-request approval keeps routine edits inside the task checkout and asks before broader actions. (Codex sandboxing, agent approvals)

Orca reads ~/.codex, supports account selection, restores account identity on restart, and can show nested Codex tasks. (Codex in Orca)

Cursor CLI

Use Cursor's modes deliberately:

  • Ask: read-only exploration;
  • Plan: clarify and design before edits;
  • Agent: implement and run tools.

Cursor CLI exposes /ask, /plan, and matching command-line flags. Orca detects the CLI on PATH, opens it in the worktree, and reads its state events. (Cursor CLI modes, Cursor CLI in Orca)

4. Install and configure Orca

4.1 Install stable Orca

Download the desktop app for macOS, Windows, or Linux. macOS users can use:

brew install --cask stablyai/orca/orca

Use stable builds for work. Try release candidates only when a required fix or feature warrants the risk. Orca auto-updates on the stable channel. (Install guide)

4.2 Install and authenticate each agent outside Orca

Verify each CLI in a normal terminal before adding it to the daily workflow:

pi
claude
codex
agent   # Cursor CLI executable

Complete login once, quit, then launch the agent from Orca. If an agent fails inside Orca, run the same binary in Orca's blank terminal. This separates PATH and authentication failures from Orca failures.

4.3 Set Agent Permissions to Manual

Open Settings → Agents → Agent Permissions and choose Manual for work repositories.

Orca's default agent launch configuration uses each CLI's approval-bypass flag, including Claude's --dangerously-skip-permissions, Codex's --dangerously-bypass-approvals-and-sandbox, and Cursor's --yolo. A disposable worktree protects the checkout from file collisions. It does not protect SSH keys, cloud credentials, developer databases, network services, or files outside the checkout. (Supported agents and permission defaults)

Use YOLO mode only when all conditions hold:

  • the agent runs inside an ephemeral VM, container, or locked-down account;
  • the environment has task-scoped credentials;
  • the agent cannot reach production;
  • the worktree holds no untrusted repository instructions;
  • deletion restores the environment to a known state.

4.4 Register the Orca CLI

Open Settings → General → Orca CLI and install the shim. Verify:

orca status --json

Linux names the CLI orca-ide when required to avoid conflict with the GNOME screen reader. Follow the resolver exposed by the installed Orca skill rather than hard-coding a binary name. (CLI overview, install guide)

4.5 Add the repository

  1. Add the primary local checkout.
  2. Set the base ref to the team's integration branch, often origin/main.
  3. Connect GitHub or the team's review provider.
  4. Set a default agent. Start with Pi.
  5. Configure repo setup hooks.
  6. Add worktree shared paths only for files that must exist in each checkout.

Do not use a personal feature branch as the default base ref.

4.6 Install Orca skills into the agents

Orca publishes version-matched skills for its CLI, orchestration, browser/computer use, Linear, emulators, and per-workspace environments. The default agent setup often installs the core three. Verify with:

orca skills list
orca skills get orca-cli
orca skills get orchestration --full

Install or update through Orca's Skills page when possible. On a headless host:

orca skills install --skill orca-cli --skill orchestration
orca skills update --all

The live guide matches the running Orca version, so agents should query it instead of guessing flags. (Orca skills registry)

4.7 Configure notifications

Enable completion and needs-input notifications. A notification should pull you back for a decision, not announce each command. Turn off noisy events after one week of observation.

5. Prepare each repository for agent work

High throughput starts with a repository that answers routine questions without a human.

5.1 Add AGENTS.md

Keep one root file concise enough that every agent can follow it. Add nested files only when a subsystem needs different rules.

Recommended outline:

# Repository instructions

## Purpose and architecture
- What this repository owns
- Important boundaries and dependencies

## Commands
- Setup: `...`
- Fast tests: `...`
- Full tests: `...`
- Lint: `...`
- Typecheck: `...`
- Run locally: `...`

## Engineering rules
- Patterns to reuse
- Files or generated code not to edit
- Error, logging, and API conventions

## Task completion
- Required tests
- Required documentation
- PR and migration expectations

## Safety
- Never access production
- Never print or commit secrets
- Ask before schema changes or destructive commands

Claude Code also reads CLAUDE.md; Orca surfaces both files. Avoid copying the same long text into several memory files. Prefer one canonical instruction file with short agent-specific additions. (Agent hooks and memory)

5.2 Make setup deterministic

Commit an orca.yaml setup script at the repository root:

scripts:
  setup: |
    ./scripts/bootstrap-worktree.sh

The script should be idempotent. It may install dependencies, generate local code, and validate prerequisites. It must not write shared global state, alter production resources, or copy secrets into git-tracked paths. Orca runs setup after it creates the worktree. The Orca repository uses the same scripts.setup shape. (Orca's own orca.yaml, hooks and memory)

5.3 Handle ignored files

Use one of these mechanisms:

  • worktree.sharedDirectories in orca.yaml for repo-defined shared directories;
  • .worktreeinclude for ignored files that Orca should copy;
  • Repository Settings → Worktree Shared Paths for per-developer local paths.

Example:

worktree:
  sharedDirectories:
    - .cache

# .worktreeinclude
.env.local
.vscode/settings.json

Do not share mutable databases, socket files, build locks, or one dependency directory across worktrees unless the tool supports concurrent access. Shared node_modules can save setup time but can also produce cross-branch dependency drift. Prefer package-manager caches over shared installed trees.

5.4 Provide fast feedback commands

Each repository needs:

  • a test command that finishes in under two minutes;
  • focused test selection;
  • lint and typecheck commands;
  • a full validation command that matches CI;
  • a local service health check;
  • test fixtures or seed data that agents can reset.

Agents should run focused checks during implementation and the full relevant suite before handoff.

5.5 Protect secrets and external systems

  • Use development credentials with narrow permissions.
  • Block production network ranges from agent environments.
  • Use synthetic customer data.
  • keep .env files ignored;
  • scan staged changes for secrets;
  • require human approval for migrations, infrastructure changes, package publication, and writes to external services.

Git worktrees share the repository's git object database and configuration. They do not form a security sandbox.

6. Task intake and shaping

Do not launch an implementation agent from a one-line ticket unless the task is mechanical.

6.1 Classify the task

Class Example Execution
Mechanical rename, dependency update, generated client refresh One agent, narrow checks
Bounded endpoint, UI state, known bug One agent, normal review
Uncertain intermittent failure, unfamiliar subsystem Read-only investigation, then implementation
Risky auth, data, infra, concurrency Plan approval plus independent review
Cross-cutting several services or repositories Split into contracts and integration tasks

6.2 Write a task contract

Use this template in the issue or first agent prompt:

# Goal
<Observable outcome in one sentence>

## Context
- User or system problem:
- Relevant components:
- Linked issue/design/incident:

## Scope
- In:
- Out:

## Acceptance criteria
- [ ] Behavior ...
- [ ] Error case ...
- [ ] Compatibility or migration ...

## Constraints
- Reuse:
- Do not change:
- Security/performance limits:

## Verification
- Focused tests:
- Full checks:
- Manual or runtime proof:

## Handoff
Return: diagnosis, approach, files changed, commands run with results,
remaining risks, and follow-up work. Do not commit or push unless asked.

6.3 Require evidence

Replace vague instructions such as "make sure it works" with evidence:

  • failing test before the fix and passing test after it;
  • exact test, lint, and typecheck output;
  • API request and response;
  • screenshot at named viewport sizes;
  • benchmark before and after;
  • migration dry-run and rollback result;
  • logs showing the corrected state transition.

7. The standard task runbook

Step 1: Synchronize the base

Fetch the remote and confirm the base ref. Create from a commit that you can name in the PR.

Step 2: Create the workspace

Use a task name that matches the issue and outcome:

fintrust-412-fix-policy-cache

Link the GitHub, Linear, or Jira issue during creation. Orca associates the worktree with its review and can surface checks and issue state. (Hosted reviews)

Step 3: Wait for setup

Do not prompt the agent while dependency setup is half-finished. Confirm:

  • setup hook passed;
  • branch and start ref are correct;
  • ignored config exists;
  • baseline tests can run;
  • no unexpected local changes exist.

Step 4: Start in read-only or plan mode for uncertain work

Prompt:

Read AGENTS.md and the linked task. Investigate before editing.

Return:
1. current behavior and execution path;
2. root cause or remaining hypotheses;
3. smallest viable change;
4. tests that should fail before the change;
5. risks and open questions.

Do not edit files yet.

Approve the plan only when it names concrete files, behavior, tests, and trade-offs.

Step 5: Authorize implementation

Prompt:

Implement the approved plan.

Rules:
- keep the diff within the stated scope;
- add or update tests for the changed behavior;
- run focused checks after each coherent edit;
- do not weaken tests, lint rules, types, or security controls;
- do not commit, push, or modify external systems;
- stop and ask if a new schema, public API, dependency, or destructive action is required.

Before handoff, review the full diff and remove incidental changes.

Step 6: Observe by exception

Do not watch tokens scroll. Use Orca's state indicators and notifications. Intervene when:

  • the agent asks a product or architectural question;
  • it repeats the same failed command;
  • it expands scope;
  • it requests dangerous permissions;
  • tests reveal an invalid assumption;
  • the diff grows past the task's review budget.

Step 7: Require a structured handoff

Stop editing and provide a handoff:
- root cause or design decision;
- files changed and why;
- commands run and exact outcomes;
- acceptance criteria status;
- unresolved risks or skipped checks;
- recommended reviewer focus.

Step 8: Inspect the repository state yourself

Check:

git status --short
git diff --stat
git diff --check
git diff <start-ref>...HEAD

Look for untracked files, accidental generated output, permission changes, lockfile churn, debug logging, and unrelated formatting.

Step 9: Review the diff line by line

Use Orca's combined diff and keyboard navigation:

  • j / k: next or previous changed file;
  • n / p: next or previous hunk;
  • s: stage current hunk;
  • c: comment on the current line.

The diff viewer can stage by line or hunk, show whitespace, render image diffs, and compare against another ref. (Diff viewer)

Review in this order:

  1. Scope: Does each changed line support an acceptance criterion?
  2. Correctness: Are invariants, failure modes, and boundary cases handled?
  3. Tests: Would the tests fail against the old behavior? Do they assert outcomes rather than implementation details?
  4. Security: Did permissions, trust boundaries, inputs, secrets, or network access change?
  5. Operations: Are logging, metrics, rollback, migration, and compatibility adequate?
  6. Maintenance: Does the code follow the repository's patterns with less complexity than the alternatives?

Step 10: Batch feedback

Leave all line comments before sending them. Orca anchors comments to lines and sends one combined prompt to the selected agent. Batch feedback prevents several conflicting micro-revisions. (Annotate AI Diff)

Use comments like:

This cache key omits tenant_id. Two tenants with the same policy ID can share a value.
Add tenant_id to the key and a regression test that creates the collision.

Avoid comments like "clean this up" or "make this better."

Step 11: Run an independent review when required

Reviewer prompt:

Review the diff against the task contract and repository instructions.
Do not edit files.

Report only findings that affect correctness, security, reliability,
performance, compatibility, or missing acceptance criteria.
For each finding include severity, file and line, failure scenario,
and the smallest valid fix. State which checks you performed.

Step 12: Validate, stage, and commit

Run the required commands yourself or inspect their fresh output. Stage by hunk. Use a commit message that states the behavior change.

Repository pre-commit hooks still run through Orca. When a hook fails, Orca shows the output; its Fix with AI action gives the agent the failure without asking it to bypass the hook. (Commit and push)

Step 13: Push and open a draft PR

The PR should include:

  • problem and user impact;
  • approach and important trade-offs;
  • tests and runtime evidence;
  • risks, migration, and rollback;
  • screenshots or logs when useful;
  • linked issue.

Keep it draft until CI passes and the diff is review-ready. Never let AI-generated PR text claim tests that did not run.

Step 14: Clean up

After merge:

  1. confirm the remote branch state;
  2. preserve any reusable learning in repository docs;
  3. archive or delete the Orca worktree;
  4. close stale browser tabs and terminals;
  5. remove losing race branches.

Orca can remove the worktree directory and branch after confirmation. Review preserved branches when git detects unmerged commits. (Worktrees)

8. Prompt patterns

Bug diagnosis

Investigate <symptom>. Do not edit yet.

Reproduce it or identify why reproduction is blocked. Trace the execution
path with file and line references. Rank hypotheses by evidence. Propose a
regression test that isolates the root cause. Stop after the diagnosis.

Focused implementation

Implement <behavior> under these acceptance criteria: <criteria>.
Reuse <existing pattern>. Keep <interfaces> unchanged. Add a regression test.
Run <commands>. Return the diff summary and command results. Do not commit.

Test improvement

Review the changed behavior and tests. Identify branches or failure modes that
the tests miss. Add the smallest tests that would catch a plausible regression.
Do not change production code unless a test exposes a defect; report that first.

Refactor

Refactor <area> without changing observable behavior. Establish baseline tests
first. Preserve public interfaces and serialized formats. Keep mechanical moves
separate from semantic changes. Report any behavior you cannot preserve.

Security review

Review this diff as an adversarial security engineer. Focus on trust boundaries,
authorization, secrets, injection, path handling, network access, dependency risk,
and unsafe defaults. Do not edit. Give exploit scenarios and precise fixes.

Handoff between agents

Continue this task from a clean session. Read the task contract, PLAN.md if it
exists, and the current diff. Treat prior claims as unverified. Re-run the
smallest checks needed to establish state before editing. Preserve the agreed
scope and report any contradiction.

9. Context management

Keep source-of-truth artifacts in the repository

Use:

  • issue or ticket for the requested outcome;
  • AGENTS.md for stable repository rules;
  • PLAN.md for a complex task's approved implementation plan;
  • ADR or design document for durable decisions;
  • tests for executable behavior;
  • PR for review history.

Do not rely on one agent transcript as the only record of a decision.

Restart sessions at task boundaries

Start a fresh session when:

  • the task changes;
  • the agent has pursued two failed approaches;
  • the context contains outdated requirements;
  • you switch from implementation to independent review;
  • the agent starts referring to old assumptions.

Orca's Continue in New Session can inject a bounded handoff while leaving the original session intact. Treat that handoff as a summary, then verify it against files and tests. (Codex in Orca)

Use checkpoints

Create a git commit or Orca worktree checkpoint after a coherent, verified phase. Checkpoints give you a safe comparison point and limit the cost of an agent taking a wrong turn.

10. Multi-agent orchestration

Orca has an experimental orchestration layer with Runs, tasks, dispatches, worker messages, completion events, heartbeats, and decision gates. Enable it under Settings → Experimental only after the manual worktree loop feels routine. (Orchestration)

Use orchestration for a task DAG with clear ownership. Do not use it to automate an unclear ticket.

Basic supervised flow:

orca orchestration run-create \
  --objective "Implement and validate policy cache isolation" \
  --json

orca orchestration task-create \
  --task-title "Implement tenant-safe cache key" \
  --spec "Follow the approved task contract and return test evidence" \
  --json

orca orchestration worker-start \
  --task <taskId> \
  --worktree new-child \
  --name policy-cache-fix \
  --agent pi \
  --setup run \
  --json

orca orchestration check \
  --wait \
  --types worker_done,escalation,question \
  --timeout-ms 900000 \
  --json

Worker rules:

  • one task and one dispatch ID per worker attempt;
  • one worker_done message with an outcome;
  • heartbeat for long active work;
  • blocking questions through the coordinator;
  • release completed worker terminals after preserving output;
  • one integration owner for the run.

Run orca skills get orchestration --full before scripting because command flags evolve with the installed app.

11. Browser, API, and runtime verification

Browser loop

Use Orca's snapshot and interaction commands when the task needs reproducible UI checks:

orca goto --url http://localhost:3000 --json
orca snapshot --json
orca click --element @e3 --json
orca fill --element @e1 --value "test@example.com" --json
orca screenshot --json

Element refs can change after navigation. Snapshot again before the next action. Use separate browser profiles for roles or accounts. (CLI overview)

Verification matrix

Change Minimum evidence
Backend logic focused unit test plus relevant integration test
API contract request/response example, schema check, compatibility review
UI behavior automated test plus desktop and mobile manual check
Visual change screenshots at named viewports and interaction check
Database migration forward dry-run, rollback or recovery plan, data-size estimate
Infrastructure plan output, policy/security check, rollback command

Concurrency deterministic race test or load scenario plus invariant checks

12. Remote and mobile work

Use local worktrees for short tasks. Use SSH when builds need more CPU, a GPU, or a network location that the laptop lacks. Orca creates the worktree and runs agents on the SSH host while keeping its editor and diff workflow. Remote PTYs can survive a desktop app close and reconnect with scrollback. (SSH worktrees)

Remote checklist:

  • verify the SSH host fingerprint;
  • use a non-production account;
  • install Node and build tools required by the Orca relay;
  • forward only task-required ports;
  • keep credentials on the remote host narrow and revocable;
  • confirm whether browser traffic and DNS should traverse the SSH host;
  • clean abandoned worktrees and processes.

Use mobile for monitoring, answering questions, and resuming a blocked terminal. Do not approve a large diff or dangerous command from a phone screen.

13. Daily operating rhythm

Start of day, 10 minutes

  1. Pull and inspect the task queue.
  2. Select one primary task and one secondary task.
  3. Shape both into task contracts.
  4. Create worktrees and let setup run.
  5. Start one agent; start the second after the first has a stable plan.

Focus blocks

Run a 60-to-90-minute block:

  • one agent implements;
  • you review another completed task, write a design, or handle work that needs human judgment;
  • notifications pull you back for questions;
  • each completed worker enters the review queue before you start another writer.

End of day, 15 minutes

  • review all dirty worktrees;
  • stop or checkpoint unfinished work;
  • record blockers in the issue;
  • close unused browser tabs and terminals;
  • delete abandoned attempts;
  • leave at most one long-running remote worker, with a clear completion contract.

14. Quality gates

Gate 1: Ready for an agent

  • Goal names an observable outcome.
  • Scope and non-scope exist.
  • Acceptance criteria are testable.
  • Base ref is known.
  • Verification commands exist.
  • Risk level and review pattern are chosen.

Gate 2: Ready for human review

  • Agent inspected the full diff.
  • No unrelated files changed.
  • Focused tests pass.
  • Lint and typecheck pass where relevant.
  • Agent listed skipped checks.
  • Diff fits the review budget or has been split.

Gate 3: Ready for PR

  • Human reviewed each hunk.
  • Acceptance criteria map to evidence.
  • Security and operational impact were considered.
  • Generated files and lockfiles are intentional.
  • Commit history is understandable.
  • PR body reports facts, not assumptions.

Gate 4: Ready to merge

  • CI passes on the pushed commit.
  • Required review is complete.
  • Migration and rollback are ready.
  • Observability covers the changed behavior.
  • Follow-up work has tickets rather than TODO comments with no owner.

15. Metrics that improve the system

Measure weekly, not per engineer:

Metric Desired movement Warning
Lead time from ready to merged Down Tasks may be sliced poorly if flat.
Human review time per PR Stable or down Rising time means diffs are too large or noisy.
First-pass CI success Up Falling rate means agents hand off too early.
Review rounds per PR 1 to 2 More suggests weak task contracts or review prompts.
Rework within 14 days Down Fast merges may be shifting cost downstream.
Escaped defects Flat or down Stop increasing concurrency if it rises.
Agent attempts discarded Low but nonzero Zero may mean you never explore alternatives.
Active worktree age Short Old worktrees create integration drift.

Do not optimize token use or active-agent count in isolation. Optimize accepted changes per review hour while defect rate stays controlled.

16. Failure modes and recovery

Agent will not start

  1. Run the CLI inside an Orca blank terminal.
  2. Check PATH under Settings → Agents.
  3. Check the CLI's login state.
  4. Restart the agent tab.

Worktree creation fails

  1. Fetch the start ref.
  2. Check whether git already associates the branch with another worktree.
  3. Inspect the setup hook separately.
  4. Retry with a new branch name only after understanding the collision.

Diff looks stale

Refresh the diff. External rebase, reset, or file generation can race Orca's view. Confirm with plain git.

Agent loops

Stop after two repetitions. Ask for:

Stop executing commands. Summarize the failed attempts, evidence from each,
the assumption most likely to be wrong, and the next discriminating check.

Start a fresh investigator if the response repeats the same approach.

Diff explodes

  1. Stop the agent.
  2. inspect git diff --stat and generated files;
  3. revert only the agent's incidental changes;
  4. split mechanical changes from behavior changes;
  5. tighten the task contract before resuming.

Tests pass but confidence is low

Ask a reviewer to identify tests that would fail under plausible broken implementations. Add runtime evidence or property-based tests. Passing weak tests does not establish correct behavior.

Agents disagree

Treat disagreement as a map of the uncertainty. Compare assumptions and evidence. Run the smallest experiment that distinguishes the approaches. Do not vote by model count.

Orca performance degrades

Close inactive worktrees and browser tabs. Orca keeps file watchers per worktree, and browser-heavy split layouts consume memory. (Troubleshooting)

17. Adoption plan

Week 1: Controlled baseline

  • Install stable Orca and four CLIs.
  • Set manual permissions.
  • Add one repository and deterministic setup.
  • Use one active implementation agent.
  • Record lead time, CI success, review rounds, and defects.

Week 2: Parallel flow

  • Allow two active implementation worktrees.
  • Add notifications and task-linked worktrees.
  • Race two agents on one uncertain bug.
  • Add the independent reviewer pattern for one risky PR.

Week 3: Repository leverage

  • Tighten AGENTS.md from recurring review feedback.
  • Add fast validation commands.
  • Install Orca skills for Pi, Claude Code, and Codex.
  • Add Quick Commands for frequent checks and prompts.
  • Use browser profiles and Design Mode for one UI task.

Week 4: Automation with evidence

  • Automate one repeated, low-risk workflow.
  • Try orchestration for a small two-task DAG.
  • Review the metrics against Week 1.
  • Keep changes that cut accepted lead time without raising review burden or defects.

20. Rules worth keeping visible

  1. One writer owns a worktree.
  2. Agents receive acceptance criteria and verification commands.
  3. Plans precede edits when uncertainty or risk is high.
  4. Worktrees isolate files; sandboxes isolate machines.
  5. Human review covers each changed hunk.
  6. Another agent can challenge a risky change, but you own the decision.
  7. Test output counts only when it matches the final diff.
  8. New work stops when the review queue is full.
  9. Delete abandoned attempts before they become archaeology.
  10. Increase concurrency only when review time and defect rate stay controlled.
