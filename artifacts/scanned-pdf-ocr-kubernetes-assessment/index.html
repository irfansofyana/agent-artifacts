Scanned PDF OCR on CPU Kubernetes: Tool Assessment

Engineering assessment · 7 October 2026 · Documentation and source review, not a workload benchmark

Decision assessment of MarkItDown + OCR, PaddleOCR, and MinerU, with Docling as the baseline. Target: PDFs up to roughly 100 pages; external vision/LLM providers are allowed. Daily volume, scan quality, languages, provider/model, and latency SLO are unspecified. Recommendations below are conditional on those unknowns.

Executive decision

Pilot PaddleOCR PP-StructureV3 and Docling standard OCR first. Both avoid making an external vision call mandatory for every scanned page and can run on CPU. If preserving complex document structure is the priority, add MinerU Basic to the bake-off; its 4.x API and tier behavior need careful deployment. Use MarkItDown + OCR when a vision provider is already part of the architecture and simplicity matters more than strict completeness; its OCR error path can silently omit text. None of these repositories establishes a safe 100-page latency, peak RAM, or accuracy target for the intended host. Benchmark before selecting a pod size or SLA. PaddleOCR pipeline · Docling OCR · MinerU tiers · MarkItDown OCR source

What each tool actually does

  • MarkItDown + markitdown-ocr: PDF text extraction plus vision-model OCR for embedded images or scanned pages. The plugin calls a configured OpenAI-compatible Chat Completions vision endpoint with image data; no local OCR model is bundled into that path. Markdown output. An external model can be a hosted provider or a compatible self-hosted server, but vision-message support and response shape must be tested, not inferred from “OpenAI-compatible.” Its plugin guide describes the Python configuration.
  • PaddleOCR PP-StructureV3: local OCR, layout, tables, formulas and Markdown/JSON conversion; CPU supported, GPU optional. It does not require an external LLM to recognize text. Feed extracted content to a provider yourself for interpretation, retrieval, or structured extraction. Its MCP integration connects document extraction to agents, not an arbitrary hosted model to its OCR internals. PaddleOCR-VL is a separate VLM-based pipeline: its remote recognition backend expects a compatible PaddleOCR-VL model/service rather than any generic text LLM. VL guide.
  • MinerU 4.x: Basic uses small OCR/layout/table models on CPU; Standard/Advanced add a document VLM. A remote model.vlm.server_url can offload the VLM to a MinerU-compatible OpenAI-style endpoint, but Standard/Advanced still need local small-model processing. Separate optional llm_aided features use an OpenAI-compatible LLM for title leveling and table-cell continuation; they are not the core scanned-page OCR. Flash is a preview tier, not a substitute for OCR on a scan. Model-source configuration · tiers.
  • Docling baseline: the standard pipeline performs OCR/layout/table processing locally on CPU. Its separate VLM pipeline can call a configured remote vision model, including OpenAI-style endpoints, with remote services explicitly enabled. Remote VLM example · OCR overview.

The 100-page question: limits versus completion

Page-count admission and job reliability are different problems. A service accepting a 100-page PDF does not establish that every page was processed, the job fits in RAM, or it finishes before the ingress/job/provider timeout. Treat the following as implementation and documented defaults, not tested 100-page performance.

  • PaddleOCR PP-StructureV3 serving: POST /layout-parsing processes only the first 10 PDF pages by default when the PDF is longer. Configure Serving.extra.max_num_input_imgs or split the input; the VL service likewise has a configurable page cap. Check returned page indices rather than accepting HTTP success as proof of completeness. Higher caps increase timeout/memory exposure. PP-StructureV3 serving docs · VL serving docs.
  • MinerU 4.x CLI: mineru parse defaults to the first 10 PDF pages; pass --pages all. mineru-kit parse, Python SDK, and Gradio default to all. No documented hard 100-page ceiling was established; 100 pages still require memory and timing measurements. Quick usage · PDF memory.
  • Docling-serve: explicit DOCLING_SERVE_MAX_NUM_PAGES, max upload size, and max document timeout controls exist. Its synchronous wait ceiling is separate (documented default 120 seconds), so use the async submission/poll/result workflow for long scans and set a deliberate page cap. Current source defaults page/file caps very high unless configured. Configuration · REST API.
  • MarkItDown OCR: no plugin-enforced 100-page cap, checkpoint, or resumable page batch was found. Its PDF conversion accumulates output and invokes OCR synchronously per detected image, making provider latency/rate limits additive. Crucially, service exceptions can produce empty OCR text and conversion can continue without flagging a failed page. The README's automatic full-page fallback is not a reliable guarantee for a parseable PDF with no detected images: the converter adds page headings before testing whether output is empty. Confirm coverage with rendered-page samples and test this branch against your PDF types. PDF converter source · OCR service source.

Long pages are not the same as many pages. A large-format or unusually tall scanned page can expand into a large raster image; OCR pixel budgets, PDF rendering RAM, provider image limits and payload size can fail on one page even if page-count admission passes. None of the reviewed materials establishes a universal maximum page dimension across these tools. Record PDF dimensions and rendered pixel counts in the pilot; downscale or tile only with a quality check because small text and tables can disappear. For external VLM use, validate the exact provider/model’s image-size, request-size, token, and rate limits separately.

How to connect AI without confusing OCR and reasoning

  1. Default path: PDF → CPU OCR/layout (PaddleOCR PP-StructureV3 or Docling) → per-page Markdown/JSON → your external LLM for questions, summaries, or schema extraction. Chunk the text with page provenance; send page images only when OCR confidence/quality or layout needs vision. This avoids paying a vision call for every straightforward scan.
  2. Vision-first path: MarkItDown OCR sends images to a configured OpenAI-compatible vision model; Docling’s VLM pipeline sends full-page images; MinerU Standard can call a compatible remote MinerU VLM. These contracts differ. A text-only model, an endpoint that merely accepts OpenAI-shaped JSON, or a gateway that strips image blocks will not suffice. Test a real image message, output parsing, retry behavior, and provider error response against the exact route before committing.
  3. Boundary: hosted-vision paths send page pixels outside the cluster. Avoid confidential files unless policy permits; keep keys in Kubernetes Secrets, encrypt durable outputs, control egress, and retain the PDF/page identifier in extracted blocks. Redact or filter before sending provider-bound data where required.

MarkItDown's README CLI example for configuring an LLM does not match the current CLI parser inspected in source: use the documented Python object with llm_client/llm_model and pin/test the installed versions. The Python service uses chat.completions.create, not a provider-native arbitrary vision protocol. CLI source · plugin source.

Kubernetes deployment complexity

Recommended control plane: authenticated upload → object storage/PVC → durable queue and job metadata → bounded CPU workers → per-page outputs and final merged artifact. A short-lived API request should enqueue work rather than process a 100-page PDF behind an ingress. Use an idempotency key derived from file hash + converter version/config, bounded retries per failed page, and a terminal status distinguishing complete, partial, and failed. Persist the original, page count, processed-page set, model/config versions, and output checksums; garbage-collect temporary rendered images. This is an architecture recommendation, not a feature supplied by all four tools.

  • Docling-serve: medium. Official CPU image and async API reduce wrapper code. Preload model artifacts or mount them through a prepared volume; set CPU threads, scratch/result retention, page/file/time ceilings, and readiness/startup probes. Start with a single API process/replica; test polling across restarts/replicas before HPA. Published multi-replica examples and issue reports indicate possible task-registry/sticky-routing caveats, not a blanket claim about every release. Models · Deployment.
  • PaddleOCR PP-StructureV3: medium. CPU is supported, but its pipeline includes several modules/models; pin and warm models in an image or volume, choose modules deliberately, and wrap the Python API in a queued worker for 100-page jobs. Native basic service handles one request at a time; increasing the page cap alone is not horizontal scalability. The more elaborate PaddleOCR-VL high-performance reference stack involves Triton/vLLM and NVIDIA GPUs; do not assume it is the CPU K8s recipe. Pipeline/service docs · VL HPS stack.
  • MinerU 4.x: medium-high. Basic + ONNX is the initial CPU tier. Its self-hosted V1 API supports upload → submit → poll → download, but the upload/file/job index is in-process memory and does not survive restart even with a persistent upload directory. Put a durable queue and artifacts outside the API; constrain --concurrency and protect the service. The published Compose deployment favors NVIDIA/vLLM, so a CPU K8s deployment requires custom image/config and validation. V1 API · Docker.
  • MarkItDown OCR: small container, larger reliability wrapper. CPU worker plus outbound HTTPS is easy to containerize, but no durable job API or page checkpoint is provided. Add chunking, provider backoff/rate limiting, explicit failed-image accounting, and output verification outside the library; do not trust a success return alone. Tune SDK timeout/retries and enforce network egress and credential policy. Plugin guide · SDK behavior.

Memory guidance is not a request/limit: MinerU's tagged docs list roughly 2 GB minimum RAM for Basic ONNX and 8 GB for Standard/Advanced ONNX + llama.cpp, while recommending more for higher throughput. These are planning floors/model bundles, not measured peak RSS for a 100-page PDF. Document image dimensions, pipeline options, output retention, and parallel jobs can dominate. Benchmark peak RSS and CPU with one worker before setting Kubernetes requests/limits, then rerun at proposed concurrency. Tier requirements · Memory guide.

Failure modes worth designing for

  • Silent truncation: 10-page defaults in PaddleOCR serving and mineru parse. Check expected versus returned page numbers.
  • False success: OCR or provider failures can leave blank/partial pages, especially in MarkItDown. Check coverage and sample images, not only exit codes.
  • One giant request: ingress and synchronous server timeouts, remote model rate limits, expensive retries, and restart loss. Use bounded page windows (for example, begin with 10–20 pages as a pilot value, not a proven optimum), persist results, and merge in order.
  • Mixed layouts: tables, stamps, handwriting, multilingual text and rotated/low-resolution scans need a document-specific quality rubric; a polished Markdown page can still omit figures or transpose cells.
  • Licensing: MinerU 4.x uses an Apache-based license with extra terms, not plain Apache-2.0; inspect its commercial/service thresholds and model licenses before product use. Also inspect model weights when choosing alternatives. MinerU license.

A decision-grade pilot

Use the same representative 100-page PDF plus a few deliberately hard pages for all candidates. Choose at least one mixed-language, table-heavy, rotated, and low-quality sample if those occur in production. Run each tool on the intended CPU host, pin versions/models, and record: completed page numbers, missing text/table cells, wall time, peak pod RSS, CPU-seconds, rendered-pixel extremes, image egress bytes, provider calls/cost, retries, and behavior after a forced worker restart. Test the 10-page boundary, exact 100-page boundary, one oversized page, and a simulated provider timeout. Do not publish document contents or sample scans to this public report.

Decision gate: select the simplest pipeline that meets page completeness and an agreed accuracy/latency target. If CPU PP-StructureV3 or Docling meets it, keep the LLM downstream. If neither preserves difficult layouts, pilot MinerU Standard with a compatible remote VLM or Docling remote VLM, comparing accuracy against provider cost. If choosing MarkItDown, require a wrapper that fails closed on missing OCR pages.

Evidence and uncertainty

First-party documentation and repository source were reviewed on 7 October 2026, including MinerU's 4.0.10 tag. This report does not claim a live 100-page benchmark, a Kubernetes deployment, an external-provider contract test, or a universal maximum page count/dimension. Source links are embedded beside each consequential claim; version-specific behavior should be rechecked before production deployment.
