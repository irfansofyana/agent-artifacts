Evaluate first.
Route second.

A practical system for finding the cheapest model that reliably completes each real workload—and turning that evidence into a defensible auto-routing policy.

The central idea

An auto-router is not a model evaluator. It executes the model policy your evaluation creates.

01 / REALITY

Know which routing problem you are solving

“Routing” is overloaded. Separating its three jobs prevents a reliable gateway from being mistaken for a quality-selection system.

Infrastructure

Load balancing & fallback

Selects deployments using health, rate limits, latency, cost, retries, or availability. It does not determine which model gives the best answer.

Classification

Auto Router v2

Classifies requests into SIMPLE, MEDIUM, COMPLEX, or REASONING, then routes to the model or pool assigned to that tier.

Learning

Adaptive routing

Explores candidates within a tier using feedback. Enable it only after the reward signal represents real task success.

LiteLLM’s current Auto Router v2 ships in version 1.94.x and later. It supports heuristic, keyword, semantic, and LLM-based classification; tier pools; decision-cause logs; optional session affinity; and adaptive selection inside a pool.

The router can tell that a prompt looks difficult. Only your evaluation can tell which model is good enough for that difficulty.

02 / DATASET

Benchmark the work, not the model

Generic leaderboards answer generic questions. A useful evaluation dataset mirrors the actual application pipeline: system prompt, retrieval, tools, structured output, language, and conversation history included.

Start with workload families

01

Extraction

Classification, JSON, schema-constrained data, entity extraction.

02

Knowledge

Grounded Q&A, RAG, citations, summarization, synthesis.

03

Engineering

Code, debugging, architecture, cloud and infrastructure tasks.

04

Agents

Tool choice, argument validity, multi-step completion, recovery.

Add language and communication slices—especially Indonesian and English—when they represent production traffic.

Build a useful first dataset

SliceSharePurpose
Normal60%Representative production work and dominant happy paths.
Hard / edge25%Long context, ambiguity, subtle constraints, complex tools, and near-limit inputs.
Adversarial / malformed15%Conflicting instructions, missing data, bad formats, unsafe or impossible requests.

Begin with 50 carefully reviewed real cases. Expand to 150–250 after the first runs expose the failure modes worth preserving. Every production incident or surprising trace should become a regression case.

03 / SCORE

Measure quality, reliability, speed, and economics together

Use deterministic checks wherever possible, semantic judgment only where necessary, and humans to calibrate the judge. A smooth answer that calls the wrong tool is still a failed answer.

DimensionBest measurementExamples
CorrectnessCode evaluator or reference rubricExact match, field accuracy, calculation result, domain criteria.
ReliabilityHard pass/fail checksSchema validity, tool choice, argument validity, errors, timeouts.
GroundednessEvidence check plus judgeClaims supported by retrieved context; citation coverage.
Human qualityBlind pairwise reviewHelpfulness, clarity, completeness, tone, preference.
LatencyTrace telemetryTime to first token, p50 and p95 end-to-end latency.
EconomicsUsage and billing reconciliationCost/request, cost/success, cached and uncached token cost.
StabilityRepeated trialsRun stochastic, reasoning, and tool cases three times.
Selection rule Choose the cheapest model that clears the use-case quality gate and meets the p95 latency SLA.

This produces a cost–quality Pareto frontier. Avoid collapsing everything into one arbitrary weighted “model score”; weighted averages can hide hard failures and turn decision-making into spreadsheet astrology.

04 / LOOP

Run the evaluation as a repeatable experiment

Collect

Sample real traces across use cases, risk levels, languages, lengths, and failure history.

Label

Record expected behavior, deterministic constraints, difficulty, and unacceptable outcomes.

Replay

Send the identical application pipeline to every candidate model with controlled settings.

Score

Run hard checks first, then judges, then blind human review for ambiguous or high-risk cases.

Select

Find the cheapest passing model for every use-case and difficulty segment.

Regress

Store failures and production surprises in the versioned dataset, then rerun on changes.

Keep comparisons fair

  • Same system prompt and app pipeline
  • Same retrieval context and tool definitions
  • Same output and reasoning budget where comparable
  • Temperature zero where supported and appropriate
  • Separate cached and uncached measurements
  • Blind model identity during human review
  • Track errors, refusals, and empty outputs
  • Reconcile LiteLLM estimates with Bedrock billing
05 / ROUTER

Evaluate the routing decision, not only the response

Once each workload has a cheapest passing model, that result becomes the per-request oracle. Replay the dataset through Auto Router and compare its choice with the oracle.

Quality risk

Under-routing

The router chooses a cheap model that fails the task or violates a hard requirement.

Cost waste

Over-routing

The router chooses an expensive model when a cheaper candidate already passed.

System cost

Routing overhead

Classifier latency, classifier tokens, embedding cost, cache disruption, and extra failures.

Router scorecard

MetricQuestion answered
Task success rateDid the routed system preserve acceptable application quality?
Under-routing rateHow often did the policy sacrifice task success for a cheaper tier?
Over-routing rateHow often did the policy spend more than necessary?
Routing regretHow far was the chosen model from the cheapest passing model?
Cost per successWhat did each completed task cost after retries and failures?
Decision-cause coverageCan every route be explained by score, keyword, classifier, or session pin?
Session/cache impactDid switching models break continuity or reduce provider cache value?

Start with one pinned model per tier and adaptive routing disabled. Pools introduce exploration; exploration is useful only when task-success feedback reliably reaches the router.

06 / STACK

A small toolchain is enough

System of record

Langfuse

Store versioned datasets, run comparable experiments, attach code or judge scores, perform annotations, and promote production failures into regression cases.

Fast local matrix

Promptfoo

Call the LiteLLM proxy, compare multiple aliases, express assertions, export results, and add regression gates to CI.

Managed AWS option

Bedrock Evaluation

Useful for AWS-governed model, RAG, prompt-router, judge-model, and human evaluation jobs. Keep application-specific telemetry in Langfuse.

07 / SHIP

Roll out in gates, not faith

Baseline

Run 50 reviewed cases against 3–5 candidates and manually calibrate the rubric.

Tier

Assign the cheapest passing candidate to each workload and complexity tier.

Replay

Evaluate the router against the oracle and tune thresholds or keyword rules.

Shadow

Run routing decisions without serving them; compare chosen and production outputs.

Canary

Route 5–10% of eligible traffic with hard fallback and live quality monitoring.

Adapt

Enable adaptive pools only after reward quality, sample size, and rollback controls are proven.

Manual evaluation is not a primitive fallback. A blind review of 50 representative cases is often more valuable than thousands of irrelevant benchmark questions.
