How Morty's Grok Bot team works, and how to adopt it

Morty summarizes the Grok Bot setup of Lauren Tan (@poteto), one of the engineers building Grok Bot. There is a Chief of Staff in front, specialists behind it, and a human who approves anything that leaves the building. The roles are easy to copy. The handoff rules are what make the setup work.

Bahasa Indonesia: versi Indonesia.

The seven roles

Morty's post lists seven roles, and each one has a single job.

  • Chief of Staff plans the work and delegates it. It is the front door, and you talk to it when you do not know which bot owns a task.
  • Researcher finds and filters the facts.
  • Engineer builds and tests the solution.
  • Reviewer checks quality, accuracy, and risk.
  • Doc Writer turns finished work into reusable docs.
  • Operator keeps recurring workflows running.
  • Memory Manager keeps the useful context across sessions.

Names change between Morty's posts. Another one has Dr Eggbot as the reviewer and Crumb as the memory bot. Treat the names as labels for jobs, not a fixed org chart.

How a task moves through the team

Morty describes the flow as intake, delegate, execute, synthesize, deliver. A second post puts it as goal, plan, specialists, review, final result. Either way, the Chief of Staff turns a fuzzy request into a plan and sends each part to one specialist. A reviewer checks the result before it reaches you. Each bot has a narrow job, a clear trigger, and an expected output.

How the team runs day to day

  • Talk to one bot. Most of the time you only talk to the Chief of Staff, and it routes the request. Lauren's point is that you never have to remember which bot owns what.
  • Put standing rules in the bot's description, not in its memory. The description works as the bot's instructions. When you duplicate a bot, the instructions are copied but the memory starts empty.
  • Keep memory for facts about you, and skills for how to do a job. The 0chob guide makes this split explicit.
  • Run only a few routines: a weekday morning brief, an inbox sweep that drafts replies and never sends them, and a Friday review of what each bot did.
  • Sort actions into four tiers. Reversible work is done and logged. Anything another person sees, or anything that commits your time, is drafted and waits for a yes. Money, passwords, deletions, and posting as you are never done by the bot. When it is unsure, it asks.
  • Track a trust number. After week one, count how many drafts you sent without changing a word. Give the bot more autonomy only as that number grows.

The engineering side

Lauren's engineering setup adds three things. Engineer bots launch coding agents. Test bots check their own work before anything merges. "Done" has to be checkable, not just claimed. Morlex's list calls the bar "poteto-mode": one job, no slop, verified. Her pstack skill set is the most detailed public description of this layer. She says it helped her ship about 2,000 pull requests a month, and that figure is her own claim.

Team size

Sources disagree on how many agents she runs. A recap of her talk, quoted by smerkzz, says a Chief of Staff, 9 managers, and 21 workers, which is 30 or more agents. A Morty post quotes her at about ten. The count changes over time, so copy the structure, not the number.

How to adopt it

  1. Start with one bot. Make it the Chief of Staff and interview it about your work: what you do, your top priorities, the people who matter, and how fast each should hear back. Ask it to restate that in its own words, then save it.
  2. Write the four tiers before you give the bot any real access: reversible work, things others see, money and deletions, and anything unsure. Put them in the bot's standing instructions.
  3. Pick one task you repeat by hand every week. Do it with the bot while you watch, ask it to save the procedure as a skill, then run the skill without help. Only schedule it after it succeeds on the first try.
  4. Add a specialist only when a job is clearly separate, and only after the first bot has run for about a week. Give each specialist one job, one trigger, and one output format.
  5. Require evidence at every handoff. A handoff should say what was done, where the output lives, and what is still open. Done means the result was checked.
  6. Split memory three ways: facts about you, procedures as skills, and shared decisions in one place every bot can read, such as a Notion page or an Obsidian folder.
  7. When a bot gets something wrong, fix the rule, skill, or description that let it happen. Correcting the single output is not enough.

Pitfalls

  • Building six bots on day one. Then you manage six bots. Morlex, who copied the setup, said six bots meant reading six chats a day, so he added a boss bot.
  • Scheduled runs nobody needs anymore. Each one burns usage, so review the schedule every week.
  • Letting a bot send anything in your name before the trust number supports it.
