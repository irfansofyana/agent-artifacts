Codemode in Pi Coding Agent

A grounded guide to Pi’s first-party Codemode: tool composition, MCP exposure, safety boundaries, and community-package name collisions.

The short answer

Codemode is now a first-party Pi tool, introduced in Pi 0.99.0.[1] The model writes a JavaScript program that calls Pi tools; Pi runs it in a QuickJS sandbox and returns the script's selected output rather than feeding every intermediate tool result back to the model.[2] It is a way to compose tools and control context, not a new model, an autonomous agent, or a security boundary for the whole Pi process.[2]

This matters most for multi-step work: discover a tool, call several tools (possibly concurrently), filter or aggregate their results in code, and return only the useful slice.[2] It can reduce model-tool round trips and context volume; the documentation does not establish a universal percentage of token or latency savings, so benchmark your own workloads.[2][3]

What actually runs

The codemode tool accepts raw JavaScript source as the body of an async function—not JSON, a fenced block, or TypeScript.[2] Top-level await and return work.[2] Scripts have tools.<name>(args), text(), image(), console, discovery helpers (searchTools, describeTool, describeNamespace, ALL_TOOLS), small session-branch-aware store()/load() state, and a models API for classifier/image models; chat models cannot be run from scripts.[2]

const hits = await searchTools("search repository issues");
text(hits.map(({name, description}) => ({name, description})));
// On the next invocation, inspect a chosen tool with describeTool(name),
// then call tools.<exact_name>({ ...documented_arguments }).

Once the tool name and arguments are known, independent calls can use Promise.all(); use Promise.allSettled() when partial success matters.[2] An output-schema tool resolves to a structured value; MCP calls resolve to the full CallToolResult, including isError, so check the result instead of assuming a resolved promise means success.[2] The example above deliberately discovers rather than invents an MCP method name.

The sandbox has no direct Node APIs, filesystem, network, or timers.[2] It reaches those capabilities through registered tools; a tool call can still write files, run shell commands, or mutate a remote service.[2] A script failure does not roll back calls already completed.[2] Pending calls are cancelled when the script ends, and unawaited promises are discarded.[2] In other words, sandboxed JavaScript is not sandboxed effects.

How tools are exposed

Pi's four default active tools remain read, bash, edit, and write unless configured otherwise.[4] Add codemode for a run with pi --tools read,bash,edit,write,codemode, or add "defaultTools": ["+codemode"] in Pi settings without replacing the defaults.[4][1] The built-in tool is also auto-enabled when a default-exposure MCP server connects, unless autoEnableCodemode is disabled in mcp.json.[3]

With codemode.mode: "on" (the default), declared tools remain directly available to the model and can also be called from scripts.[2] With "only", they are hidden as direct model tools and reached through scripts instead.[2] The inline tool declarations have a configurable token budget (codemode.inlineBudget, default 3,000 estimated tokens); beyond it scripts can discover tools on demand.[2]

Pi 0.99.0 also introduced tool_search, a separate route that declares deferred tools to the model for later direct calls.[1] MCP servers can choose codemode (default), codemode-deferred, deferred, direct, or hidden exposure, with per-tool overrides.[3] This is not simply “all MCP tools become one tool”: visibility and access depend on configuration, and codemode can still call tools that are not declared directly to the model.[3]

To connect an MCP server, configure ~/.pi/agent/mcp.json or a trusted project's .pi/mcp.json, then check it with pi mcp list and reload the session.[3] Pi supports stdio and streamable HTTP; project config is trust-gated because a stdio server can launch a command.[3] Keep credentials in environment references, not plaintext config.[3]

Limits and safety

The QuickJS VM has a 256 MB memory limit.[2] The default script output cap is 10,000 tokens; // @options: {"max_output_tokens": 2000, "timeout_ms": 60000} can set an output cap and a hard deadline.[2] A script without a deadline can wait on a running tool; set one for bounded jobs, but allow long-running image generation enough time.[2]

Native tool calls still go through Pi's tool pipeline, including extension tool_call/tool_result handlers; nested calls carry their parent codemode call ID.[3] A permission gate can intercept them, but Pi does not thereby become a whole-process sandbox.[3][2] Treat untrusted extensions and MCP servers as executable dependencies, and protect destructive tools at the host/tool boundary rather than trusting JavaScript isolation alone.

Avoid the name collision

Before 0.99.0, community extensions already used “codemode.”[6][1] For example, @boozedog/pi-codemode provides a TypeScript execute_tools tool and /codemode on|off|yolo modes, root-scoped patch tools and its own policy files.[6] Those are that package's commands and guarantees, not Pi core's codemode JavaScript tool or codemode.mode: "on"|"only" settings.[6][2] Do not install a third-party package merely to get the first-party feature; also check for tool-name or /mcp command collisions if one is installed.[1][3]

Recommendation

Start with core Codemode only if you have a real workflow that chains several tools or needs to trim bulky MCP results. Leave mode at on first so ordinary tools remain easy to inspect; move to only only if you deliberately want all declared calls mediated by scripts.[2] For a one-file read or simple edit, direct tools are clearer. Measure cost and latency on a representative task, and keep approval/permission checks outside the script rather than treating Codemode as a safety upgrade.
