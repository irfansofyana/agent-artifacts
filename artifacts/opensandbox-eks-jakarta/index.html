OpenSandbox release-1.2.1, AWS ap-southeast-3

OpenSandbox on EKS Jakarta

OpenSandbox on one EKS cluster in Jakarta covers the AgentCore Code Interpreter job, which AWS does not offer in this region. It does not cover the rest of AgentCore. A small cluster, on the default container runtime, is about $777/month. A two-AZ layout is about $1,174/month, before PPN and traffic.

Bahasa Indonesia: versi Indonesia.

What it is

OpenSandbox gives an agent an isolated Linux environment to run commands, edit files, and, if you put the tools in the image, drive a browser or a desktop. Your application talks to one lifecycle API. The server can sit on Docker for a laptop, or on Kubernetes for a cluster. The API does not change.[1]

This page is pinned to release-1.2.1, published 13 Nov 2026. The docs site still shows release-1.1.0 as the example checkout. Use the stable tag, not main.[2][3]

It is Apache-2.0, and it is a project of the Agentic AI Foundation.[1]

What the API gives you

On release-1.2.1, the five language SDKs can create a sandbox, reconnect to it, renew it, pause and resume it, and kill it. They can run commands, read and write files, read metrics, set an egress policy, and use Credential Vault. Snapshots, templates, volumes, and pools are in the SDK too. Whether pause, snapshots, and templates actually work depends on the runtime behind the server, not on the client.[7]

  • Inbound traffic on Kubernetes goes through the ingress gateway. Sandbox pods are ClusterIP-only, so the gateway is required, not optional.[3]
  • Outbound access is a per-sandbox policy. Credential Vault can call an external service without putting the real secret in the sandbox.[1]
  • Pools and batch create are for running many trials at once. C# is the SDK that does not have Client Pool.[7]

Fast Sandbox is a separate runtime, not a second product. A create that names a template is routed to Firecracker microVMs inside pre-warmed pods, and the sandbox id starts with fsb-. Image-based creates stay on ordinary Kubernetes pods. The SDK does not change.[9]

How other apps use it

Anything that can call the lifecycle API can use the cluster. The server does not care that it is running on EKS.

  • Your own service uses a SDK: Python (opensandbox), TypeScript (@alibaba-group/opensandbox), Java or Kotlin, Go, or C# (Alibaba.OpenSandbox). Python is the quick-start language. Go is the one you would pick for a long-running backend.[1][7]
  • A person or a script uses the osb CLI. pip install opensandbox-cli.[1]
  • An agent that already speaks MCP uses opensandbox-mcp. Documented setups are Claude Code and Cursor, over stdio or HTTP. Any other MCP client can use the same server. The tools cover create, connect, kill, renew, run a command, and text files. Pools, snapshots, templates, and Credential Vault stay on the SDK or the CLI.[6]

A second, different use is running an agent inside the sandbox. The examples do that for Claude Code, Codex CLI, Gemini CLI, OpenCode, Qwen Code, Kimi CLI, OpenClaw, LangGraph, Google ADK, Playwright, Chrome, a desktop, and VS Code Web. Those are workloads. The client is still the SDK or MCP server that created the sandbox.[8]

Point the client at the lifecycle host and the API key. For the CLI that is osb config set connection.domain. For MCP it is --domain and --api-key.[1][6]

AgentCore, mapped

OpenSandbox is the sandbox, not the agent platform. The closest AgentCore product is Code Interpreter: an isolated environment where an agent runs code. Browser is a separate AgentCore product. OpenSandbox does that job only when the image is a browser. The Chrome and Playwright examples are that image.[20][8]

If the agent process itself is the sandbox, the next overlap is Runtime, and partly Harness. Runtime is where you host the agent, with session isolation. Harness is the managed agent loop. Each Harness session also gets a microVM with a filesystem and a shell. OpenSandbox can start that box. It does not pick the model, and it does not run the loop.[20]

Hermes or OpenClaw, left where they already run, map to Code Interpreter. They call the sandbox when they need a shell. A product that spawns an OpenClaw instance maps to the Runtime shape, because the agent process is the workload. The OpenClaw example does that: the Gateway runs inside the sandbox.[8][20]

AgentCore productOpenSandbox
Code InterpreterYes. This is the match.
BrowserOnly with a browser image. Not a separate product.
RuntimeOnly if the agent process is the sandbox workload. No managed session product around it.
HarnessNo. The box overlaps. The agent loop does not.
IdentityNo. Credential Vault injects an outbound secret. Identity is who the agent is, and how it gets a token from an IdP.
Memory, Gateway, Observability, PaymentsNo equivalent.
Policy, Evaluations, Optimization, RegistryNo equivalent. They are AgentCore features. OpenSandbox does not ship them.

Policy is the easy mix-up. OpenSandbox can restrict a sandbox's network. AgentCore Policy sits on Gateway and decides whether a tool call is allowed before it runs.[20][21]

The AgentCore region table has no Asia Pacific (Jakarta) column. Runtime, built-in tools (Code Interpreter and Browser), Memory, Gateway, and Identity are not listed for ap-southeast-3. Singapore is the nearest region in that table. This cluster can host the agent process, which is the Runtime-shaped use. It is not AgentCore Runtime: there is no built-in identity, and there is no Jakarta endpoint for the AWS service.[21]

The control plane you still build

Two patterns, and both already exist in the examples. A product where each person spawns an OpenClaw, a Hermes, or a coding agent is the second one. OpenSandbox does not become that product on its own.

Agent outside: one Hermes or OpenClaw stays running and calls OpenSandbox when it needs a shell, files, or a browser. That is the Code Interpreter shape. It does not give each person an instance. The code-interpreter example is this pattern.[8]

Agent inside: a spawn creates a sandbox whose image is the agent. The examples already do this for Claude Code, Codex CLI, and OpenClaw Gateway. Hermes is not in that list. You build that image. The user gets a URL to the sandbox. The client that created it is your service.[8]

One sandbox per user per agent type is still one EKS cluster and one OpenSandbox install. The shared pieces are the lifecycle server, the controller, and the ingress gateway. Each spawned agent is its own Pod, ClusterIP only, reached through that gateway. Isolation is the Pod and its egress sidecar. A second cluster is a later choice about blast radius, not the model.[3][22]

The control plane is what you ship. It authenticates the user, picks an image, creates or resumes one sandbox, routes ingress to it, injects credentials through Credential Vault instead of baking them into the image, and pauses or kills the sandbox when the user leaves. Users do not receive the platform API key. The server wants one key, and the chart default is one replica. Tenancy is yours.[1][3][4]

Put coding agents inside the sandbox. They need the shell on the same machine, which is what the Claude Code and Codex examples do. Hermes and OpenClaw go the same way when the product is "your instance." A child sandbox is the right extra only when that instance must run code you do not trust with its own credentials. That split is a product choice. OpenSandbox does not do it for you.

Ship the inside pattern first: one Pod per user per agent type, on the cluster in the diagram. The outside pattern is a later feature of the same control plane.

Architecture

The diagram is the small Jakarta layout: clients outside the region, a load balancer, the three control-plane pods, sandbox pods, ECR for images, and optional Postgres. EKS 1.35 or 1.36 is the cluster boundary. Fast Sandbox is not in this drawing. The control plane above is another client of the lifecycle server. It is not a second cluster.

Components

  • Lifecycle server, one replica, port 80. It refuses to start without an API key. Upgrades use Recreate, so the API blips.[3][4]
  • Controller, which reconciles BatchSandbox, Pool, and SandboxSnapshot. It is small. It is not what sizes the node.[3]
  • Ingress gateway, two replicas, each requesting 1 CPU and 4 GiB, limit 2 CPU and 8 GiB, listening on port 28888. The chart service is ClusterIP on port 80.[5]
  • Sandbox pods in the opensandbox namespace. execd is inside the sandbox image. An egress sidecar is added only when the create request sets networkPolicy.[4]

What you have to bring

  • EKS 1.35 or 1.36 in ap-southeast-3. OpenSandbox only needs Kubernetes 1.22+. Do not create 1.34: standard support ends 2 Dec 2026, and extended support is $0.50/hour, $365/month, instead of $73.00.[3][11][15]
  • Helm 3, from a git checkout of release-1.2.1. Charts are not published as standalone packages.[3]
  • ECR in Jakarta. The chart default registry is sandbox-registry.cn-zhangjiakou.cr.aliyuncs.com. Do not pull that from this region. Mirror server, controller, ingress, execd, and egress from Docker Hub or GHCR, and pin the digest. Current umbrella releases are not Cosign-signed the way the old per-component releases were.[1][4][13]
  • An API key secret, a DNS name for server.gateway.host, and a load balancer in front of the server and the gateway.
  • Optional RDS PostgreSQL in the same region, if a reschedule must not drop sandbox state. The chart default is one server and no database.[3]
  • EBS gp3 if a sandbox mounts a volume. The basic path does not need it beyond the node disks.

Example

Python, against a server you already started. The same calls work against the EKS host once the domain and API key point there.[1]

from opensandbox import Sandbox

sandbox = await Sandbox.create("alpine")
try:
    result = await sandbox.commands.run("echo 'Hello OpenSandbox!'")
finally:
    await sandbox.destroy()

The CLI form:

osb config set connection.domain <lifecycle-host>
osb config set connection.protocol https
osb config set connection.api_key <api-key>
osb sandbox create --image python:3.12 --timeout 30m
osb command run <sandbox-id> -- python -c "print(1 + 1)"

Deploy on EKS Jakarta

Leave fast-sandbox off. Their cloud guide wants bare-metal nodes with /dev/kvm, and every node in that pool has to be the same CPU model. One c7i.metal-24xl in Jakarta is about $3,606/month before disks. AWS nested virtualization can expose /dev/kvm on m7i, c7i, r7i, and i7i at no extra charge, and m8i / c8i are not in the Jakarta price list, but OpenSandbox has not published an EKS recipe for that path.[10][12][14]

  1. Create the cluster on 1.35 or 1.36, in ap-southeast-3, with a private subnet if you can accept a NAT.
  2. Two managed node groups. System nodes run the server, controller, and gateway. A pilot fits on one m7i.2xlarge, which matches the single server replica. Workers run sandbox pods only, tainted, starting at one c7i.2xlarge.
  3. Mirror the five images into ECR at release-1.2.1 and create a pull secret or a node role that can read that registry.
  4. Create namespaces opensandbox-system and opensandbox. The chart does not create the workload namespace.[3]
  5. Check out release-1.2.1, run helm dependency build in manifests/charts, and install the umbrella chart with ingress-gateway.enabled=true and the image repositories pointed at ECR. Store the API key in a Secret and reference it from the server values. Set server.gateway.host to the name clients will use.
  6. Put an ALB or NLB in front of the server and the gateway. Confirm /health before pointing a client at it.
  7. Add RDS only when you need state to survive a pod reschedule. Keep server.replicaCount at 1. A second replica is not general high availability.[3]

The three public IPv4 addresses on the 2-AZ row are an address-count assumption: one for the NAT, two for an internet-facing load balancer across two AZs. The hourly rates are from the offer files.

Each extra private c7i.2xlarge plus 50 GB gp3 is about $305/month. How many sandboxes fit depends on the CPU and memory in the create request, not on the chart.

The NAT hour is the line that surprises people, not the gigabytes. 100 GB through the NAT is $5.90. The gateway existing at all is $43.07/month before any sandbox traffic. EKS itself is $73.00 even with two nodes.

If you do not want to tune the chart's 8 GiB limits, replace the two m7i.xlarge system nodes with two m7i.2xlarge. That adds about $368/month. Kubernetes schedules on requests, so the cheaper pair fits if the server and the two gateway pods are spread.

If a cluster is left on 1.34 past 2 Dec 2026, the control plane moves to extended support and the $73.00 line becomes $365, a $292 increase, with no change in OpenSandbox.[11][15]
